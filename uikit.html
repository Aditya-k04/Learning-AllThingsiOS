    UIKit Foundations

    UIKit is Apple's original, hands-on toolkit for building screens. Where SwiftUI lets you describe what the UI should look like and lets the framework figure out the rest, UIKit hands you the raw building blocks — view objects you create, arrange, and mutate yourself, step by step. It is imperative, it is explicit, and once you understand it, a lot of the "magic" underneath SwiftUI and Core Animation stops being magic.

    This course teaches UIKit from zero, assuming you already know Swift and have poked at SwiftUI. We build up the mental model slowly: what a view is, how views nest into a tree, how Auto Layout positions them, what the everyday view catalog offers, how navigation and presentation work, and finally how to make things move and respond to touch. We target iOS 26/27 (2026), Swift 6.x, and Xcode 26, and we stick to modern APIs throughout — Auto Layout anchors, not the old springs-and-struts.

    Why still learn UIKit in 2026? Because it underlies everything. SwiftUI hosts itself inside UIKit view controllers. Core Animation is the layer system every UIView sits on top of. And plenty of real apps still have large, healthy UIKit codebases. Knowing UIKit makes you a stronger SwiftUI developer, not a nostalgic one.

    What you'll be able to do

    • Build real UIKit screens in code, from an empty view controller up.
    • Read and reason about the view tree — who owns whom, and what draws what.
    • Position anything with Auto Layout constraints, confidently.
    • Reach for the right view from the catalog: labels, images, buttons, text input, lists.
    • Wire up navigation stacks, bars, sheets, and alerts.
    • Animate views and respond to touches, gestures, and controls.

    01 — What UIKit Is

    Start here — the plain idea

    Imagine building a diorama out of a box of parts. You pick up each piece, you place it exactly where you want it, and if you want it to move later, you go back and move it yourself. Nobody arranges the scene for you. That is UIKit. You create view objects one by one, add them into a tree, set their properties, and change those properties over time. It is imperative: you give an ordered list of instructions, and the screen reflects whatever you last told it.

    Now contrast that with SwiftUI, which you have already seen. In SwiftUI you describe the finished scene — "a stack with a title, then an image, then a button" — and the framework builds and rebuilds it for you whenever your state changes. That is declarative. You never call addSubview; you never hold onto a label and mutate its text. You just say what should be true, and SwiftUI makes it so.

    Neither style is "better." UIKit gives you fine, direct control and decades of mature APIs. SwiftUI gives you brevity and automatic updates. The interesting part: SwiftUI runs inside UIKit — every SwiftUI screen is ultimately hosted by a UIKit view controller in a UIKit window. So learning UIKit is learning the floor that everything else stands on.

    How an app is actually put together

    A running iOS app is a nested set of objects, from the app itself down to the smallest button. Here is the chain, top to bottom:

    • UIApplication — the singleton representing your running app. One per process.
    • UIWindowScene — a scene is one instance of your UI (an app can have several on iPad or in Stage Manager). It manages windows.
    • UIWindow — the canvas everything is drawn into. Usually you have exactly one visible window per scene.
    • root UIViewController — the window's rootViewController. A view controller owns one screen's worth of UI and its logic.
    • the controller's view — every view controller has a top-level UIView (its .view).
    • subviews — inside that view sits your actual content: labels, images, buttons, stacks.
    // A minimal scene delegate wiring up the object tree by hand.
final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(_ scene: UIScene,
               willConnectTo session: UISceneSession,
               options connectionOptions: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }

        let window = UIWindow(windowScene: windowScene)   // the canvas
        window.rootViewController = HomeViewController()   // the first screen
        window.makeKeyAndVisible()                         // show it
        self.window = window
    }
}

    That is the whole skeleton. In SwiftUI you would just write WindowGroup { HomeView() } and never see these objects — but they are still there underneath.

    The object tree, drawn

    The run loop and events, at a glance

    Your app is not a script that runs top to bottom and exits. It sits inside a run loop — a tireless cycle managed by UIKit that waits for something to happen, handles it, redraws if needed, and waits again. When the user taps the screen, the system packages that into a UIEvent, hands it to your app, and UIKit figures out which view was touched (via hit-testing) and delivers the event through the responder chain. Your code reacts, maybe changes a property, and UIKit schedules a redraw on the next loop pass.

    You rarely touch the run loop directly. But knowing it is there explains why UIKit is event-driven: you set things up, then respond to callbacks (a button tap, a lifecycle method, a gesture) rather than driving everything yourself.

    When you still reach for UIKit in 2026

    SwiftUI is the default for new work now, but UIKit stays useful when you need:

    • Fine, imperative control — precise animation timing, custom drawing, or manipulating a view in ways SwiftUI does not expose.
    • Existing codebases — large apps built over the last decade are UIKit, and you will maintain and extend them.
    • Things SwiftUI can't yet do — every release closes gaps, but there are still edges (certain text interactions, some collection-view layouts, deep customization) where you drop down to UIKit.
    • Interop — hosting UIKit inside SwiftUI (UIViewRepresentable, UIViewControllerRepresentable) or SwiftUI inside UIKit (UIHostingController). Real apps mix both, and the seam is where UIKit knowledge pays off.

    iOS 26–27 / what Apple does today

    Apple positions SwiftUI as the front door for new apps, but UIKit is actively maintained, not deprecated. Recent releases keep adding UIKit APIs (updated appearance and adaptivity, the new material and "Liquid Glass" effects, modern collection layouts) and improving the SwiftUI↔UIKit bridge. In 2026, the healthy stance is both: SwiftUI for new screens, UIKit when you need depth or when the code you inherited lives there.

    The foundation

    • imperative = you issue step-by-step instructions and mutate objects yourself; UIKit's style.
    • declarative = you describe the desired result and let the framework build it; SwiftUI's style.
    • UIApplication = the single object representing your whole running app.
    • UIWindowScene = one instance of your app's UI, managing its windows.
    • UIWindow = the top-level canvas everything is drawn into.
    • rootViewController = the window's first screen; a view controller owning one screen of UI.
    • run loop = UIKit's wait-handle-redraw cycle that makes the app event-driven.
    • hit-testing = how UIKit decides which view a touch landed on.

    02 — UIView: The Universal Building Block

    Start here — the plain idea

    Picture a box of Lego bricks. Every brick is the same kind of thing — a brick — but some are wide baseplates, some are little studs, some are windows or wheels. You snap small bricks onto bigger bricks, those onto a baseplate, and out of one repeated part you build anything. UIKit works exactly like this, and the brick is called UIView.

    Here is the reveal that makes UIKit click: every visible thing on screen is a UIView or a subclass of it. A label is a UILabel (a UIView). A button is a UIButton (a UIView). An image is shown by a UIImageView (a UIView). A scrolling list is a UITableView (a UIView). They differ in what they draw and how they behave, but they are all bricks, and they all nest inside one another the same way.

    So when you learn UIView — how it nests, what it does, and what it sits on top of — you have learned the shape of the entire framework. Everything else in the catalog is "a UIView that also does X." In SwiftUI you compose View values; in UIKit you compose UIView objects, and you hold references to them so you can change them later.

    The view hierarchy: superviews and subviews

    Views form a tree. Each view has one superview (its parent, or nil if it is not in a tree) and an ordered array of subviews (its children). You build the tree by adding children to parents:

    let container = UIView()
let badge = UIView()

container.addSubview(badge)     // badge.superview is now container
print(container.subviews)       // [badge]

badge.removeFromSuperview()     // detaches badge from its parent
print(container.subviews)       // []

    addSubview(_:) puts the new view on top (last in the array, frontmost on screen). Order matters because later subviews draw over earlier ones — that array is the z-ordering, front to back. When you need finer control:

    container.insertSubview(badge, at: 0)                 // send to back
container.insertSubview(badge, aboveSubview: header)  // just in front of header
container.bringSubviewToFront(badge)
container.sendSubviewToBack(badge)

    A quick contrast: in SwiftUI, order in a ZStack decides layering and you never call these methods. In UIKit the subviews array is a real, mutable list you manipulate directly.

    UIView's three jobs

    Every UIView, whatever its subclass, is responsible for three things:

    1. Draw itself. It fills its area with content — a color, an image, text, or custom drawing you provide by overriding draw(_:). Most of the time you never override drawing; the built-in views handle it.
    2. Lay out its subviews. It positions its children, either via Auto Layout constraints (the modern way — see 04-auto-layout-and-constraints) or in layoutSubviews() for custom cases.
    3. Receive touches. It participates in hit-testing and can handle or forward touch events through the responder chain.
    final class HomeViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = .systemBackground

        // Job 1: a view that draws a colored, rounded card.
        let card = UIView()
        card.backgroundColor = .secondarySystemBackground
        card.layer.cornerRadius = 16
        card.translatesAutoresizingMaskIntoConstraints = false

        // A label brick living inside the card brick.
        let title = UILabel()
        title.text = "Hello, UIKit"
        title.font = .preferredFont(forTextStyle: .headline)
        title.translatesAutoresizingMaskIntoConstraints = false

        // Build the tree: view -> card -> title
        view.addSubview(card)
        card.addSubview(title)

        // Job 2: lay out with constraints (details in lesson 04).
        NSLayoutConstraint.activate([
            card.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            card.centerYAnchor.constraint(equalTo: view.centerYAnchor),
            card.widthAnchor.constraint(equalToConstant: 240),
            card.heightAnchor.constraint(equalToConstant: 120),

            title.centerXAnchor.constraint(equalTo: card.centerXAnchor),
            title.centerYAnchor.constraint(equalTo: card.centerYAnchor),
        ])
    }
}

    That is a real, correct hierarchy built entirely in code: a controller's view holds a card, the card holds a label. Three bricks, snapped together.

    The big reveal: every UIView is backed by a CALayer

    Here is what actually draws to the screen. A UIView does not paint pixels itself — it owns a CALayer (its .layer), and the layer does the real work. The view is a thin, touch-aware, Auto-Layout-aware wrapper; the layer is the rendering surface Core Animation composites to the display.

    This is why properties like corner radius, borders, shadows, and transforms live on the layer:

    let box = UIView()
box.backgroundColor = .systemBlue

// These are really layer properties, surfaced through the view.
box.layer.cornerRadius = 12
box.layer.borderWidth = 1
box.layer.borderColor = UIColor.separator.cgColor
box.layer.shadowOpacity = 0.2
box.layer.shadowRadius = 8

    Understanding this split is the bridge to Core Animation. When you want smooth animation, custom geometry, or GPU-composited effects, you are really talking to the layer. Learn the layer properly in CALayer.

    iOS 26–27 / what Apple does today

    The view-backs-a-layer model is unchanged and foundational — it is how UIKit, Core Animation, and even SwiftUI's renderer all reach the screen. In 2026, modern effects like Liquid Glass materials (see 10-uivisualeffectview-and-liquid-glass) are ultimately layer-level compositing work surfaced through friendly view APIs. Also note translatesAutoresizingMaskIntoConstraints = false: you set this on any view you position with Auto Layout in code, so UIKit does not synthesize conflicting old-style constraints for you.

    The foundation

    • UIView = the base class for every visible thing; the universal building block.
    • superview = a view's single parent in the tree (or nil if unattached).
    • subviews = a view's ordered array of children; the order is the z-order.
    • addSubview / removeFromSuperview = attach a child on top, or detach it from its parent.
    • z-ordering = front-to-back stacking, determined by position in the subviews array.
    • three jobs = a view draws itself, lays out its subviews, and receives touches.
    • CALayer = the layer each view owns that performs the actual drawing and compositing.

    03 — Frame, Bounds, Center & Coordinate Spaces

    Start here — the plain idea

    Think about a framed painting hanging on a wall. There are two different ways to describe it. One is where the frame sits on the wall — "start 30 cm from the left edge, 50 cm from the top, and it's 60 by 40." That is measured in the wall's coordinates. The other is the ruler printed along the inside edge of the canvas itself — which always starts at zero in its own corner, no matter where on the wall the painting hangs. That inner ruler is how the painting talks about its own contents.

    UIKit gives every view both descriptions. frame is where the view sits in its parent's world — its position and size measured in the superview's coordinate space. bounds is the view's own inner ruler — its size measured in its own coordinate space, with an origin that is usually (0, 0).

    Most of the time frame and bounds have the same size and differ only in origin, so beginners assume they are the same thing. They are not, and the moment you rotate a view or scroll its contents, the difference becomes very real. This lesson makes that difference intuitive so it never trips you up.

    Frame vs bounds vs center

    Three geometry properties, all CGRect/CGPoint values in points:

    • frame — a CGRect in the superview's coordinate space. "Where am I, and how big, from my parent's point of view?"
    • bounds — a CGRect in the view's own coordinate space. Its size matches the frame's size (normally); its origin is usually (0, 0) and defines what portion of the view's content is considered the top-left.
    • center — a CGPoint in the superview's coordinate space, equal to the midpoint of the frame. Setting it moves the view without changing its size.
    let parent = UIView(frame: CGRect(x: 0, y: 0, width: 400, height: 400))
let child  = UIView(frame: CGRect(x: 50, y: 80, width: 120, height: 60))
parent.addSubview(child)

child.frame   // (50, 80, 120, 60)  — position in PARENT's world
child.bounds  // (0,  0,  120, 60)  — same size, own ruler starts at 0
child.center  // (110, 110)         — midpoint of the frame, in PARENT's world

    Notice frame and bounds share the size 120×60 but differ in origin: (50, 80) versus (0, 0). Inside the child, you draw and lay your subviews out using bounds — because from the child's perspective, its own top-left is always zero.

    Turn up the heat: frame, bounds and transform together

    The clean rule "frame and bounds are the same size" holds only while the view is not transformed. Every view has a transform (a CGAffineTransform, or transform3D for 3D). Rotate, scale, or skew a view and its frame becomes the smallest axis-aligned rectangle that encloses the transformed view — its bounding box. The bounds and center, meanwhile, do not change.

    let v = UIView(frame: CGRect(x: 100, y: 100, width: 100, height: 100))
v.bounds   // (0, 0, 100, 100)
v.frame    // (100, 100, 100, 100)

v.transform = CGAffineTransform(rotationAngle: .pi / 4)   // rotate 45°
v.bounds   // (0, 0, 100, 100)   — unchanged
v.center   // unchanged
v.frame    // ~ (79, 79, 141, 141) — the enclosing bounding box grew

    This is why Apple's guidance is blunt: do not read or set frame on a transformed view. Once a transform is non-identity, frame is a derived, lossy value. Position via center and size via bounds (or, better, via Auto Layout constraints, which are transform-aware). This rule saves you from a whole category of "why is my rotated view in the wrong place" bugs.

    Why scrolling changes bounds.origin

    Here is the elegant trick behind every scroll view. Scrolling does not move the content views around — it moves the bounds origin of the scroll view itself. Since subviews are drawn relative to their superview's bounds, shifting bounds.origin shifts what part of the content is visible, as if you slid a window over a long page.

    // Conceptually, this is what a scroll view does under the hood:
scrollView.bounds.origin = CGPoint(x: 0, y: 200)   // "scrolled down" 200pt
// The subviews didn't move; the visible window into them did.
// UIScrollView.contentOffset is essentially this bounds.origin.

    So bounds.origin is not always (0, 0). In a scroll view it is the live scroll position. Understanding this demystifies scroll views: they are ordinary views whose bounds origin you (or the user's finger) move.

    Converting points between coordinate spaces

    Because each view has its own ruler, a point that means "top-left corner" in one view means something else in another. To translate, use the conversion methods — every UIView is a UICoordinateSpace:

    // A point in `child`'s coordinates, expressed in `otherView`'s coordinates:
let pInOther = child.convert(CGPoint(x: 10, y: 10), to: otherView)

// Bring a point from another view into this view's coordinates:
let pHere = child.convert(somePoint, from: otherView)

// Rectangles convert too — handy for "where is this view on screen?"
let rectInWindow = card.convert(card.bounds, to: nil)   // nil = the window

    Passing to: nil or from: nil means the window's coordinate space. This is how you answer questions like "did the user tap inside this subview?" or "where is this label relative to the whole screen?" without doing the arithmetic by hand.

    The classic gotcha: setting frame vs using Auto Layout

    You can position views by assigning frame directly (manual layout). It works, but it is brittle: you must recompute frames whenever the screen rotates, the size class changes, or Dynamic Type resizes text — and it fights with Auto Layout if you mix them.

    // Manual layout — you own every recalculation forever:
label.frame = CGRect(x: 20, y: 100, width: 200, height: 24)

// Auto Layout — you declare relationships once, UIKit maintains them:
label.translatesAutoresizingMaskIntoConstraints = false
NSLayoutConstraint.activate([
    label.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 20),
    label.topAnchor.constraint(equalTo: view.safeAreaLayoutGuide.topAnchor, constant: 80),
])

    The rule of thumb for modern UIKit: set frame only for throwaway or manual-layout cases; reach for Auto Layout for real screens. And crucially, do not mix them on the same view — if you constrain a view, do not also assign its frame. We build up Auto Layout properly next in 04-auto-layout-and-constraints.

    iOS 26–27 / what Apple does today

    Modern UIKit code is overwhelmingly Auto Layout, so you will read and set frame/bounds far less than developers did years ago — but you still reason about them constantly, because animations, hit-testing, and Core Animation all speak geometry. When you do custom layout, do it in layoutSubviews() using bounds, and remember safe-area and layout-margin guides exist so you rarely hardcode edge insets. The frame/bounds/transform relationship maps directly onto Core Animation's layer geometry — see layer geometry, where the same ideas reappear as frame, bounds, position, and anchorPoint.

    The foundation

    • frame = a view's position and size in its superview's coordinate space.
    • bounds = a view's size in its own coordinate space; origin is usually (0,0).
    • center = the frame's midpoint, in the superview's coordinate space.
    • transform = a rotation/scale/skew applied to a view; makes frame a derived bounding box.
    • bounds.origin = the scroll position when a view scrolls; not always (0,0).
    • convert(:to:) / convert(:from:) = translate points or rects between view coordinate spaces.
    • manual layout = positioning by setting frame yourself; brittle across size changes.
    • Auto Layout = declaring constraints once and letting UIKit maintain positions.

    04 — Auto Layout & Constraints

    Start here — the plain idea

    Imagine you hire a designer and, instead of handing them a ruler and saying "put the title exactly 47 points from the top," you hand them a short list of rules: "keep the title 16 points in from each edge," "let the image be as tall as it needs," "if space runs out, shrink the subtitle before the title." Now that designer can lay out your screen on a tiny phone, a giant tablet, in portrait, in landscape, with big accessibility text — because they understand the relationships, not one frozen set of numbers.

    Auto Layout is that designer. You stop computing frames yourself and instead declare constraints — statements like "this label's leading edge equals the container's leading edge plus 16." UIKit collects every rule you give it and solves the whole system at layout time, producing the actual frame for each view. When the screen changes, it re-solves. You describe intent once; it does the arithmetic forever.

    If you've written SwiftUI, you already think this way — SwiftUI's stacks and padding are a declarative layer built on the same idea. UIKit just makes the relationships explicit and hands you the knobs directly. That's more typing, but also more control, and it's the vocabulary every older UIKit codebase is written in.

    Turning off the old system

    Every view is born believing its frame is set the old way — by translating its "autoresizing mask" into constraints. Before you attach your own constraints, you must tell it to stop:

    let card = UIView()
card.translatesAutoresizingMaskIntoConstraints = false

    Forget this one line and you'll get console spam about "unable to simultaneously satisfy constraints" — your hand-written rules fight the auto-generated ones. Set it to false on every view you constrain yourself. (Views you get from a storyboard/xib already have this handled.)

    The anchor API — the modern way

    Each view exposes anchors: leadingAnchor, trailingAnchor, topAnchor, bottomAnchor, widthAnchor, heightAnchor, centerXAnchor, centerYAnchor. You make a constraint by relating one anchor to another, then activate it.

    let container = UIView()
let label = UILabel()
label.translatesAutoresizingMaskIntoConstraints = false
container.addSubview(label)

NSLayoutConstraint.activate([
    label.leadingAnchor.constraint(equalTo: container.leadingAnchor, constant: 16),
    label.trailingAnchor.constraint(equalTo: container.trailingAnchor, constant: -16),
    label.topAnchor.constraint(equalTo: container.topAnchor, constant: 12),
])

    Two things worth noticing. First, trailing/bottom constants are negative — the constraint reads "label.trailing = container.trailing − 16," so you push inward with a minus. Second, NSLayoutConstraint.activate([...]) takes an array and turns them all on at once; it's cheaper and clearer than setting .isActive = true one at a time.

    You aren't limited to equalTo. Anchors also give you greaterThanOrEqualTo and lessThanOrEqualTo, which is how you say "at least 16 points of margin, but more is fine."

    // A width relation: the card is half the container's width.
card.widthAnchor.constraint(equalTo: container.widthAnchor, multiplier: 0.5).isActive = true

// A minimum height, not an exact one.
card.heightAnchor.constraint(greaterThanOrEqualToConstant: 44).isActive = true

    Older code you'll meet uses the Visual Format Language ("H:|-16-[label]-16-|") or manual NSLayoutConstraint(item:attribute:...) initializers. You can read them, but don't write them — anchors are type-checked, autocomplete-friendly, and the API Apple steers you toward.

    Intrinsic content size — views that know their own size

    A UILabel, UIButton, or UIImageView already knows how big it wants to be: a label's text at its font is, say, 180×21 points. That preferred size is its intrinsic content size. Because of it, you often only constrain position and let the view size itself — you never set a width or height on a label showing normal text.

    The catch: what happens when two self-sizing views compete for space, or there's extra room? That's decided by two priorities.

    Content hugging vs compression resistance

    Every view carries two resistances, one per axis:

    • Content hugging — how strongly the view resists growing larger than its intrinsic size. High hugging = "don't stretch me."
    • Compression resistance — how strongly the view resists shrinking smaller than its intrinsic size. High resistance = "don't clip my content."

    Picture two labels side by side in a row that's wider than both. Someone has to absorb the slack. Give one label lower hugging and it stretches; the other stays snug.

    titleLabel.setContentHuggingPriority(.defaultHigh, for: .horizontal)      // stay snug
detailLabel.setContentHuggingPriority(.defaultLow, for: .horizontal)      // absorb slack

// When space is TIGHT, protect the price from being truncated:
priceLabel.setContentCompressionResistancePriority(.required, for: .horizontal)
nameLabel.setContentCompressionResistancePriority(.defaultLow, for: .horizontal) // name truncates first

    Priorities — rules that bend

    A constraint has a priority from 1 to 1000. .required (1000) must hold. Anything below is optional — the solver satisfies it if it can, and breaks it (as gently as possible) if two rules conflict. This is how you express "prefer 20 points of spacing, but give it up before the layout becomes impossible."

    let spacing = detail.topAnchor.constraint(equalTo: title.bottomAnchor, constant: 20)
spacing.priority = .defaultHigh   // 750 — a strong preference, not a law
spacing.isActive = true

    The values are just numbers, so you can nudge with .defaultHigh - 1. The lesson: not every constraint deserves 1000. Reserve .required for things that must never break, and let the rest flex.

    The safe area — don't crash into the notch

    The screen has regions you shouldn't put content under: the Dynamic Island, the home indicator, rounded corners. Rather than hard-coding insets, constrain to the safe area layout guide, which UIKit sizes for you per device.

    let guide = view.safeAreaLayoutGuide
NSLayoutConstraint.activate([
    header.topAnchor.constraint(equalTo: guide.topAnchor),
    header.leadingAnchor.constraint(equalTo: guide.leadingAnchor),
    header.trailingAnchor.constraint(equalTo: guide.trailingAnchor),
])

    There's also layoutMarginsGuide for the standard readable side margins. As a rule: pin top and bottom content to the safe area, and pin side margins to the margins guide (or safe area) — never to the raw view edges.

    Under the hood — it's a solver

    Auto Layout is a real constraint solver. Apple's implementation descends from Cassowary, an algorithm for solving systems of linear equalities and inequalities with priorities. Your anchors become linear equations (label.leading − container.leading = 16); the solver finds frame values that satisfy the required ones and best-satisfy the optional ones. That's why "unable to simultaneously satisfy constraints" reads like a math error — because it is one: you asked for a system with no solution, and it broke a constraint to recover.

    If you're curious how a solver weighs competing linear rules with priorities, the constraint-solver aside in the math course covers the same machinery from the numbers side.

    iOS 26–27 note

    The anchor API is stable and remains the recommended approach on iOS 26/27 with Swift 6.x. Two things to keep current: constraint activation and view mutation must happen on the main actor (Swift 6 concurrency will flag stray calls off @MainActor), and with the refreshed system design language, prefer safeAreaLayoutGuide and layoutMarginsGuide over fixed insets so your layout tracks Apple's evolving edge treatments instead of guessing pixel values.

    The foundation

    • Constraint = a linear rule relating view attributes, e.g. a.leading = b.leading + 16.
    • Anchor = the modern, type-safe factory for constraints (leadingAnchor, widthAnchor, …).
    • translatesAutoresizingMaskIntoConstraints = false = turn off auto-generated frame constraints so yours can take over.
    • Intrinsic content size = the size a view (label, button, image) prefers based on its content.
    • Content hugging = resistance to growing past intrinsic size ("don't stretch me").
    • Compression resistance = resistance to shrinking below intrinsic size ("don't clip me").
    • Priority = 1–1000 weight; .required (1000) must hold, lower values bend when rules conflict.
    • Safe area layout guide = a UIKit-maintained region that avoids notches, islands, and home indicators.

    05 — UIStackView: The Layout Workhorse

    Start here — the plain idea

    You just spent a lesson wiring up constraints by hand. Now imagine a helper that does the boring 80% for you. You hand it a few views and say "stack these in a column," and it lays them out top to bottom, evenly spaced, sizing each one — no leading, trailing, or top constraints from you at all. That helper is UIStackView.

    If you've written SwiftUI, you already know its soul: a stack view is HStack and VStack from before SwiftUI existed. Same instinct — "put these in a row" or "put these in a column" — expressed the UIKit way. In fact SwiftUI's stacks are the idea, matured; UIStackView is the original engine, and it's still the fastest way to build most real screens.

    The trick to using it well is to stop thinking about individual constraints and start thinking about arrangement: an axis (row or column), how to fill the length, how to align the width, and how much air to leave between children. Get those four dials right and whole layouts fall into place with almost no explicit constraint code.

    The four dials

    A stack view is configured by four properties. Learn these and you've learned the tool.

    let stack = UIStackView(arrangedSubviews: [avatar, nameLabel, bioLabel])
stack.axis = .vertical            // 1. row (.horizontal) or column (.vertical)
stack.distribution = .fill        // 2. how to fill the axis (the long direction)
stack.alignment = .leading        // 3. how to align across the axis (the short direction)
stack.spacing = 8                 // 4. gap between arranged subviews
stack.translatesAutoresizingMaskIntoConstraints = false

    Axis is the direction of the stack — a column (.vertical) or a row (.horizontal).

    Distribution governs the long direction — how children share space along the axis:

    • .fill — one child stretches (the one with lowest hugging) to fill any slack.
    • .fillEqually — every child gets identical length; ignores intrinsic size.
    • .fillProportionally — children keep their intrinsic-size ratios while filling.
    • .equalSpacing — children keep their natural size; equal gaps between them.
    • .equalCentering — children's centers are evenly spaced.

    Alignment governs the short direction — how children line up across the axis. In a vertical stack that's horizontal alignment: .fill (all same width), .leading, .center, .trailing. In a horizontal stack it's vertical: .top, .center, .bottom, .firstBaseline, .lastBaseline.

    Spacing is simply the gap between adjacent children. (You can even vary it per-gap with setCustomSpacing(_:after:).)

    arrangedSubviews vs subviews — the one gotcha

    A stack view has two lists and they are not the same:

    • subviews — the normal view-hierarchy children (inherited from every UIView).
    • arrangedSubviews — the subset the stack actually lays out.

    Adding a view with addArrangedSubview(_:) puts it in both lists — it becomes a child and gets arranged. But calling plain addSubview(_:) adds it to the hierarchy without arranging it, and removeArrangedSubview(_:) stops arranging a view while leaving it in the hierarchy (usually not what you want — it'll float there unmanaged).

    stack.addArrangedSubview(button)          // added AND arranged — the usual call

// To truly remove a view, take it out of both:
someView.removeFromSuperview()            // this also drops it from arrangedSubviews

    Handy detail: setting a child's isHidden = true makes the stack instantly reclaim its space and re-flow — a clean way to show/hide rows without touching constraints.

    Nesting stacks — build a whole screen

    The real power shows when you nest. A row inside a column inside a row lets you compose an entire layout while writing only the outer stack's constraints.

    let title = UILabel()
let subtitle = UILabel()
let textColumn = UIStackView(arrangedSubviews: [title, subtitle])
textColumn.axis = .vertical
textColumn.spacing = 2

let avatar = UIImageView()
avatar.widthAnchor.constraint(equalToConstant: 44).isActive = true
avatar.heightAnchor.constraint(equalToConstant: 44).isActive = true

let row = UIStackView(arrangedSubviews: [avatar, textColumn])
row.axis = .horizontal
row.alignment = .center
row.spacing = 12
row.translatesAutoresizingMaskIntoConstraints = false

view.addSubview(row)
// The ONLY explicit constraints in the whole layout:
let guide = view.safeAreaLayoutGuide
NSLayoutConstraint.activate([
    row.topAnchor.constraint(equalTo: guide.topAnchor, constant: 16),
    row.leadingAnchor.constraint(equalTo: guide.leadingAnchor, constant: 16),
    row.trailingAnchor.constraint(equalTo: guide.trailingAnchor, constant: -16),
])

    That's a classic avatar-plus-two-lines cell built with four explicit constraints total — the two fixed sizes on the avatar and the three pinning the outer row. Everything else is arrangement. This is why stack views feel so close to SwiftUI: you describe structure, not coordinates.

    Margins inside the stack

    By default a stack packs children edge to edge. To add interior padding, turn on layout-margins-relative arrangement and set the insets:

    row.isLayoutMarginsRelativeArrangement = true
row.directionalLayoutMargins = NSDirectionalEdgeInsets(top: 12, leading: 16, bottom: 12, trailing: 16)

    isLayoutMarginsRelativeArrangement tells the stack to lay its children out inside its margins rather than its bare edges — the tidy way to give a stacked card breathing room without wrapping it in another container. Use directional insets (leading/trailing) so it mirrors correctly in right-to-left languages.

    When a stack is the right tool — and when it isn't

    Reach for a stack view when content flows in a line or column and you mostly care about order and spacing: forms, toolbars, list cells, settings rows, label-plus-value pairs. It's the default; start here.

    Reach for raw constraints when views overlap, when a view must be positioned relative to a non-sibling (something in another branch of the hierarchy), when you need one view a fixed fraction of another's size across the layout, or when you want precise control the stack's distributions can't express. And for large scrolling grids of cells, neither — that's compositional layout territory.

    iOS 26–27 note

    UIStackView is unchanged in spirit on iOS 26/27 and remains the recommended composition primitive in UIKit. Prefer directionalLayoutMargins over the older layoutMargins for correct RTL behavior, and keep all stack mutation (adding/removing arranged subviews, toggling isHidden) on the main actor — Swift 6.x concurrency checking treats these as @MainActor UI work.

    The foundation

    • UIStackView = a view that arranges its children in a row or column automatically.
    • axis = the stacking direction, .horizontal (row) or .vertical (column).
    • distribution = how children share space along the axis (.fill, .fillEqually, .equalSpacing, …).
    • alignment = how children line up across the axis (.leading/.center/.fill/baselines).
    • spacing = the gap between adjacent arranged subviews.
    • arrangedSubviews = the views the stack lays out; a managed subset of subviews.
    • addArrangedSubview / removeFromSuperview = add to both lists / remove from both lists.
    • isLayoutMarginsRelativeArrangement = lay children inside the stack's margins instead of its raw edges.

    06 — UILabel & Displaying Text

    Start here — the plain idea

    A UILabel is the simplest thing in UIKit: a piece of text sitting on the screen that the user can read but not edit. A price, a title, a caption, a name — if it's words the user looks at rather than types into, it's a label. That's the whole job.

    Because it's read-only, a label is refreshingly low-drama. You give it a string, a font, and a color; it figures out how big it needs to be (remember intrinsic content size?) and draws itself. In SwiftUI you'd write Text("Hello") and reach for .font() and .foregroundStyle(); a UILabel is the same picture with properties instead of modifiers.

    The heat rises when text meets reality: strings too long for their box, a single label that needs two colors, and — the part that actually matters for shipping — users who set their system text larger because they need to read it. The plain label handles the first two with a few properties; the third, Dynamic Type, is where a thoughtless label quietly fails people, and where a little care makes your app usable for everyone.

    The everyday properties

    let label = UILabel()
label.text = "Welcome back"
label.font = UIFont.systemFont(ofSize: 17, weight: .semibold)
label.textColor = .label                 // adapts to light/dark automatically
label.textAlignment = .center            // .left .center .right .natural .justified
label.translatesAutoresizingMaskIntoConstraints = false

    Use the semantic colors (.label, .secondaryLabel, .tertiaryLabel) rather than literal blacks and grays — they adapt to light and dark mode and to accessibility contrast settings for free. .natural alignment is worth knowing: it means "leading edge for this language," so it flips correctly in right-to-left locales.

    Wrapping and truncation

    By default a label is a single line and truncates with an ellipsis when the text overflows. Two properties control that behavior:

    label.numberOfLines = 0                   // 0 = as many lines as needed (wrap freely)
label.lineBreakMode = .byTruncatingTail   // …how to handle text that still doesn't fit

    numberOfLines is the one people forget. The default is 1; set it to 0 to let text wrap onto as many lines as the width allows. Any positive number caps it (e.g. 2 for a two-line subtitle that then truncates).

    lineBreakMode decides where the cut happens when text exceeds the allowed lines: .byTruncatingTail (default — "The quick brown…"), .byTruncatingHead, .byTruncatingMiddle (great for file paths — "/Users/…/report.pdf"), .byWordWrapping, and .byCharWrapping. For multi-line wrapping labels you usually leave word wrapping on and let truncation apply only at the final line.

    Attributed strings — mixed styling in one label

    A plain text string is uniform: one font, one color. When you need part of the text styled differently — a bold keyword, a colored total, a struck-through old price — you hand the label an attributed string via its attributedText property.

    Modern Swift gives you the value-type AttributedString, which is far more pleasant than the old NSMutableAttributedString bracket-pushing:

    var s = AttributedString("Total: $42.00")
if let range = s.range(of: "$42.00") {
    s[range].foregroundColor = .systemGreen
    s[range].font = .systemFont(ofSize: 17, weight: .bold)
}
label.attributedText = NSAttributedString(s)   // UILabel takes the NSAttributedString form

    Note the bridge on the last line: you build with the ergonomic AttributedString, then wrap it in NSAttributedString(_:) because UILabel.attributedText predates the value type. You'll also meet raw NSAttributedString with attribute dictionaries in older code:

    let old = NSMutableAttributedString(string: "was $60")
old.addAttribute(.strikethroughStyle,
                 value: NSUnderlineStyle.single.rawValue,
                 range: NSRange(location: 4, length: 3))

    Read it, but prefer AttributedString for anything new — it's Unicode-correct, Codable, and works the same way SwiftUI's Text consumes styled strings.

    Dynamic Type — the accessibility part that matters

    Here is the property most tutorials skip and every shipped app needs. Users can set their preferred text size system-wide (Settings → Display & Brightness → Text Size, and larger still under Accessibility). If you hard-code systemFont(ofSize: 17), your text ignores that choice — and for a user who bumped the size up because they can't comfortably read 17-point text, your app is now the one that won't cooperate.

    The fix is two lines. Use a text style instead of a fixed point size, and tell the label to update live when the setting changes:

    label.font = UIFont.preferredFont(forTextStyle: .body)   // scales with user setting
label.adjustsFontForContentSizeCategory = true           // update live, no relaunch

    preferredFont(forTextStyle:) returns a font already sized for the user's current setting. The styles are semantic — .largeTitle, .title1/2/3, .headline, .body, .callout, .subheadline, .footnote, .caption1/2 — so you pick by role, not by number, and the whole hierarchy scales together. adjustsFontForContentSizeCategory = true makes the label re-fetch its font when the user changes the setting while your app is running, so it updates without a relaunch.

    Want your own custom font to scale too? Wrap it in a UIFontMetrics:

    let base = UIFont(name: "SomeCustomFont-Regular", size: 17)!
label.font = UIFontMetrics(forTextStyle: .body).scaledFont(for: base)
label.adjustsFontForContentSizeCategory = true

    When you support Dynamic Type, remember to let labels wrap — pair it with numberOfLines = 0 so enlarged text has room to grow rather than truncating. The two features are partners.

    Contrast with SwiftUI

    SwiftUI's Text is Dynamic Type-aware and semantic by default — Text("Hi").font(.body) already scales, and you opt out with .fixedSize tricks. UILabel is the reverse: it defaults to a fixed size, and you opt in with preferredFont + adjustsFontForContentSizeCategory. Same capability, opposite defaults — which is exactly why it's easy to forget in UIKit and why it's worth making a habit.

    iOS 26–27 note

    On iOS 26/27, AttributedString is the preferred way to build styled text and interoperates cleanly with SwiftUI. Dynamic Type support is effectively expected in review-quality apps — the accessibility content-size categories go very large, so design and test at the biggest sizes. Keep label configuration on the main actor (Swift 6.x concurrency), and continue to favor semantic colors and text styles so labels track the system's evolving appearance automatically.

    The foundation

    • UILabel = a read-only view that displays a string (or attributed string) of text.
    • numberOfLines = max lines; 0 means wrap to as many as needed (default is 1).
    • lineBreakMode = how overflow is handled (.byTruncatingTail, .byTruncatingMiddle, .byWordWrapping, …).
    • Semantic color = .label/.secondaryLabel/… that adapt to light/dark and contrast settings.
    • attributedText / AttributedString = per-range styling (color, weight, strikethrough) within one label.
    • Dynamic Type = the user's system-wide text-size preference that accessible apps honor.
    • preferredFont(forTextStyle:) = a font sized to the current Dynamic Type setting, chosen by semantic role.
    • adjustsFontForContentSizeCategory = re-fetch the font live when the user changes text size.

    07 — UIImageView & Images

    Start here — the plain idea

    Think of a picture frame on your wall. The frame is one thing — a fixed rectangle of a certain size, hanging in a certain spot. The photo inside it is a separate thing — it might be a wide landscape, a tall portrait, or a tiny square. The frame doesn't care; it just holds whatever photo you slide into it. UIKit splits pictures the exact same way. UIImageView is the frame on the wall: a view with a position and a size that draws a picture. UIImage is the photo you slide in: the actual pixels (or vector, for symbols), with its own natural dimensions.

    This split is the whole game, and it's also where most beginners trip. The frame's size and the photo's size almost never match perfectly. So you have to tell the frame how to fit the photo — stretch it, crop it, or letterbox it. Get that wrong and your careful portrait comes out looking like it was run over. Get it right and it just looks correct everywhere, on every screen size.

    In SwiftUI you'd write Image("cat").resizable().scaledToFit(). UIKit gives you the same three ideas — a picture, a container, and a fitting rule — just spelled out as separate objects you set by hand. Once you see that mapping, UIKit images stop feeling foreign.

    Loading a picture

    A UIImage comes from somewhere. The three everyday sources:

    // 1. From the asset catalog (Assets.xcassets), by name.
let logo = UIImage(named: "CompanyLogo")   // optional: nil if not found

// 2. An SF Symbol — Apple's built-in vector icon library.
let star = UIImage(systemName: "star.fill")

// 3. A UIImageView can be created already holding an image.
let imageView = UIImageView(image: logo)

    UIImage(named:) looks in your asset catalog and caches the result, so asking for the same name twice is cheap. UIImage(systemName:) pulls from SF Symbols — thousands of scalable icons that ship with the system, match the current font size, and support Dynamic Type and dark mode for free. Reach for a symbol before you draw your own icon.

    To put an image into an existing view, just set the property:

    let imageView = UIImageView()
imageView.image = UIImage(systemName: "photo")
imageView.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(imageView)

    Content modes — the #1 source of squished images

    Here's the frame-and-photo problem made real. The view is one size; the image is another. contentMode is the rule that resolves the mismatch. Three you'll use constantly:

    imageView.contentMode = .scaleAspectFit   // whole image visible, letterboxed
imageView.contentMode = .scaleAspectFill  // fills the frame, edges cropped
imageView.contentMode = .scaleToFill      // stretches to fit — distorts! (this is the default)

    The default is .scaleToFill, which stretches the image to exactly match the view in both directions. If the aspect ratios differ, your image gets squished or stretched. That's the classic "why does my photo look fat" bug. Ninety percent of the time you actually want one of the aspect-preserving modes:

    • .scaleAspectFit shrinks the image until the whole thing fits, leaving empty bars (letterboxing) on the short sides. Nothing is cropped.
    • .scaleAspectFill grows the image until it covers the whole frame, spilling the excess outside the bounds. Nothing is distorted, but the edges get cut off.

    There's a catch with .scaleAspectFill: the overflow spills past the view's edges and, by default, keeps drawing. You have to clip it:

    imageView.contentMode = .scaleAspectFill
imageView.clipsToBounds = true   // crop the overflow to the frame — almost always what you want with aspectFill

    Symbols: rendering modes and configurations

    SF Symbols aren't just tiny pictures — they're a small styling system. A symbol can be drawn in several rendering modes, and you pick how many colors it uses:

    // Monochrome (default): one color, driven by tintColor.
let bell = UIImage(systemName: "bell.fill")

// Hierarchical: one color, but the symbol's layers get automatic opacity levels.
let cfg = UIImage.SymbolConfiguration(hierarchicalColor: .systemBlue)

// Palette: you supply an explicit color per layer.
let palette = UIImage.SymbolConfiguration(paletteColors: [.systemRed, .systemGray])

// Multicolor: the symbol's own built-in colors (e.g. a colorful flag).
let multi = UIImage.SymbolConfiguration(hierarchicalColor: .label)  // or .preferringMulticolor()

let icon = UIImage(systemName: "square.stack.3d.up.fill",
                   withConfiguration: cfg)

    You can also configure weight and scale, so an icon lines up with the text next to it:

    let config = UIImage.SymbolConfiguration(pointSize: 22, weight: .semibold, scale: .large)
imageView.image = UIImage(systemName: "heart.fill", withConfiguration: config)
imageView.tintColor = .systemPink   // monochrome symbols follow tintColor

    For a symbol drawn monochrome, tintColor colors it. That same tinting trick works for your own artwork too — mark an image as a template and it's drawn as a solid silhouette in the tint color, ignoring its original colors:

    let glyph = UIImage(named: "MyGlyph")?.withRenderingMode(.alwaysTemplate)
imageView.image = glyph
imageView.tintColor = .systemBlue   // now the glyph is drawn in blue

    Use .alwaysTemplate for single-color icons you want to recolor; use .alwaysOriginal to force full-color artwork to keep its own colors even where a template would normally apply.

    Performance: don't hand a 4000×3000 photo to a 120-point frame

    A UIImage loaded from a big photo carries all its pixels in memory, and decoding those pixels happens the first time the image is drawn — often mid-scroll, on the main thread, causing a stutter. Two habits fix almost all of it.

    First, downsample large images to roughly the size you'll actually display. Decoding a thumbnail-sized image uses a fraction of the memory:

    func downsampledImage(at url: URL, to pointSize: CGSize, scale: CGFloat) -> UIImage? {
    let sourceOpts = [kCGImageSourceShouldCache: false] as CFDictionary
    guard let src = CGImageSourceCreateWithURL(url as CFURL, sourceOpts) else { return nil }
    let maxPixels = max(pointSize.width, pointSize.height) * scale
    let opts = [
        kCGImageSourceCreateThumbnailFromImageAlways: true,
        kCGImageSourceCreateThumbnailWithTransform: true,
        kCGImageSourceShouldCacheImmediately: true,
        kCGImageSourceThumbnailMaxPixelSize: maxPixels
    ] as CFDictionary
    guard let cg = CGImageSourceCreateThumbnailAtIndex(src, 0, opts) else { return nil }
    return UIImage(cgImage: cg)
}

    Second, when you already have a UIImage and want to decode it off the main thread before it's shown, use preparingForDisplay:

    Task.detached {
    let ready = await bigImage.byPreparingForDisplay()
    await MainActor.run { imageView.image = ready }
}

    That moves the expensive decode off the main thread, so scrolling stays smooth. For deeper pixel work — filters, resizing pipelines, custom drawing — that's Core Graphics & Core Image territory.

    iOS 26–27 note. SF Symbols continues to gain animated symbols and richer variable-color support; UIImage(systemName:) picks these up automatically, and symbol effects (imageView.addSymbolEffect(.bounce)) let an icon react to events without any custom animation code. Prefer symbols over hand-drawn glyphs — they inherit the current system look, including the refreshed 2026 design, for free.

    The foundation

    • UIImageView = the view (the frame on the wall) that draws a picture at a position and size.
    • UIImage = the picture itself (pixels or vector) with its own natural dimensions.
    • contentMode = the rule for fitting a mismatched image into the view; default .scaleToFill distorts.
    • .scaleAspectFit = shrink until the whole image fits, letterboxing the extra space.
    • .scaleAspectFill + clipsToBounds = cover the whole frame, cropping the overflow (the usual choice for photos).
    • SF Symbols = Apple's scalable icon library loaded via UIImage(systemName:), styled by rendering mode, weight, and scale.
    • rendering modes = monochrome / hierarchical / palette / multicolor — how many colors a symbol draws with.
    • .alwaysTemplate = draw an image as a solid silhouette in tintColor; downsampling / preparingForDisplay keep big photos from stuttering.

    08 — UIButton (the Modern Way)

    Start here — the plain idea

    A button is the simplest promise in an interface: tap me, and something happens. Under the hood it's just a view — a rectangle that sits in your view tree like any other — with one extra talent: it notices touches and runs the code you attached to it. That's really all a button is. A view that listens for a tap and calls you back.

    Here's the thing worth un-learning, though. For years the way to build a UIKit button was to create it and then poke a dozen little properties one at a time: set the title here, set the title color for this state, set the image there, tweak the insets, fight with the layout. It worked, but it was fiddly and easy to get subtly wrong. Modern UIKit replaced all of that with a single description object — you fill out one form saying "filled style, this title, this icon, this spacing," hand it to the button, and the button figures out the rest. It's much closer to how you'd describe a button in SwiftUI.

    So this lesson teaches the current way first and treats the old way as history. If you've seen setTitle(_:for:)-heavy code in an old tutorial, that's the style we're moving past.

    The modern way: UIButton.Configuration

    You describe the button with a UIButton.Configuration, starting from one of the built-in base styles, then set your content on it:

    var config = UIButton.Configuration.filled()   // solid background, the "primary action" look
config.title = "Add to Cart"
config.image = UIImage(systemName: "cart.fill")
config.imagePadding = 8                          // space between image and title
config.baseBackgroundColor = .systemBlue         // the fill color
config.cornerStyle = .large                      // rounded corners
config.buttonSize = .large

let button = UIButton(configuration: config)
button.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(button)

    The four base styles cover almost everything:

    UIButton.Configuration.filled()   // solid fill — the prominent, primary action
UIButton.Configuration.tinted()   // translucent tinted fill — a softer secondary action
UIButton.Configuration.gray()     // subtle gray fill — a quiet tertiary action
UIButton.Configuration.plain()    // no background — text/icon only, like a link

    A configuration can hold a subtitle, an image with padding, and a corner style — the button lays it all out for you, respecting Dynamic Type and the current design:

    var config = UIButton.Configuration.tinted()
config.title = "Back Up Now"
config.subtitle = "Last backup: 3 days ago"
config.image = UIImage(systemName: "icloud.and.arrow.up")
config.imagePlacement = .leading
config.imagePadding = 10
config.cornerStyle = .medium
let backupButton = UIButton(configuration: config)

    Wiring the tap: UIAction

    Now the promise — do something when tapped. The modern way is a UIAction, a small closure-carrying object you add to the button:

    let action = UIAction(title: "Add") { _ in
    print("Tapped!")
    addItemToCart()
}
button.addAction(action, for: .primaryActionTriggered)

    .primaryActionTriggered is the "the user activated this control" event — for a button, that's a tap. You can even pass the action straight into the initializer:

    let button = UIButton(configuration: .filled(),
                      primaryAction: UIAction { _ in save() })

    The older mechanism, target/action, still works and you'll meet it in existing code. Instead of a closure, you name a method to call:

    button.addTarget(self, action: #selector(handleTap), for: .touchUpInside)

@objc func handleTap() { save() }

    Both hang off the same underlying control events system (.touchUpInside, .primaryActionTriggered, and friends) — see 15-touch-gestures-and-controls for the full picture. For new code, prefer UIAction: the logic lives right where you create the button, and there's no @objc selector to keep in sync.

    States and the configurationUpdateHandler

    A button isn't always in one look. It has states: normal (resting), highlighted (finger down), disabled (not tappable), selected (for toggles). The framework flips between them for you; your job is to say how each should look.

    The clean modern approach is a configurationUpdateHandler — a closure UIKit calls whenever the state changes, handing you a fresh configuration to tweak:

    button.configurationUpdateHandler = { button in
    var config = button.configuration
    switch button.state {
    case .disabled: config?.title = "Unavailable"
    case .highlighted: config?.baseBackgroundColor = .systemBlue.withAlphaComponent(0.7)
    default: config?.title = "Add to Cart"
    }
    button.configuration = config
}

button.isEnabled = false          // triggers the handler, shows "Unavailable"
button.setNeedsUpdateConfiguration()  // ask for a manual refresh anytime

    This replaces the old pattern of setting a different title and color for every UIControl.State by hand. You describe the rules; UIKit runs them at the right moments.

    Menus: turn a button into a pull-down

    Attach a UIMenu and the button becomes a pull-down menu — tap it and a list of choices appears, no extra plumbing:

    let menu = UIMenu(title: "Sort By", children: [
    UIAction(title: "Name", image: UIImage(systemName: "textformat")) { _ in sort(.name) },
    UIAction(title: "Date", image: UIImage(systemName: "calendar")) { _ in sort(.date) },
    UIAction(title: "Size", image: UIImage(systemName: "arrow.up.arrow.down")) { _ in sort(.size) }
])
button.menu = menu
button.showsMenuAsPrimaryAction = true   // one tap opens the menu (instead of long-press)

    That's the same UIMenu used by context menus and navigation bar buttons, so once you know it here you know it everywhere.

    iOS 26–27 note. On iOS 26, standard buttons automatically adopt the refreshed system design — new materials, shapes, and highlight behavior — with no code changes on your part, as long as you use UIButton.Configuration rather than hand-styling. That automatic adoption is a big reason the configuration API is the way forward: opt into the description-based style and your buttons stay current across OS releases.

    The foundation

    • UIButton = a view that watches for a tap and runs the code you attached.
    • UIButton.Configuration = the modern description object bundling style, title, subtitle, image, padding, and corners — the current way to build a button.
    • .filled() / .tinted() / .gray() / .plain() = the four base styles, from prominent primary action down to quiet link-like action.
    • UIAction = a closure-carrying object added with addAction(_:for:) — the clean way to wire a tap.
    • target/action = the older method-name mechanism (addTarget(_:action:for:)), still valid, common in existing code.
    • control events = the tap/change signals buttons fire, e.g. .primaryActionTriggered and .touchUpInside.
    • states = normal / highlighted / disabled / selected; configurationUpdateHandler describes how each looks.
    • UIMenu + showsMenuAsPrimaryAction = attach a menu to make the button a one-tap pull-down.

    09 — Text Input: UITextField & UITextView

    Start here — the plain idea

    Imagine two kinds of forms on paper. One has a single ruled line for your name — you write one line and stop. The other is a big blank box for your essay answer — you can write paragraphs, and if you run out of room the box scrolls. UIKit gives you exactly these two tools. UITextField is the single ruled line: one row of text, perfect for a name, an email, a search query. UITextView is the big box: multi-line, scrollable, for notes, comments, whole documents.

    They feel similar, but they're built for different jobs, and choosing wrong is a common first mistake. If you only need one line, use a text field — it gives you a Return key you can act on, easy placeholder text, and single-line behavior for free. The moment you need wrapping paragraphs and scrolling, switch to a text view.

    There's a second idea hiding underneath both, and it's the real star of this lesson: the keyboard doesn't just "appear." It appears because a specific view asked to become the thing keystrokes go to. Understanding that one concept — the first responder — is what turns text input from mysterious to obvious. In SwiftUI you'd bind a TextField to @State and toggle @FocusState; UIKit exposes the same machinery, just more directly.

    The single line: UITextField and its delegate

    A text field is quick to set up, and you talk to it through a delegate — an object it calls back as the user types, starts, and finishes:

    let field = UITextField()
field.placeholder = "Email address"
field.borderStyle = .roundedRect
field.keyboardType = .emailAddress   // shows the @ / .com-friendly keyboard
field.returnKeyType = .done          // labels the Return key "Done"
field.delegate = self
field.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(field)

    The delegate methods you'll reach for most:

    extension MyViewController: UITextFieldDelegate {
    // User tapped Return. Return true to accept it; here we dismiss the keyboard.
    func textFieldShouldReturn(_ textField: UITextField) -> Bool {
        textField.resignFirstResponder()
        return true
    }

    func textFieldDidBeginEditing(_ textField: UITextField) {
        // editing started — highlight the field, etc.
    }

    func textFieldDidEndEditing(_ textField: UITextField) {
        validate(textField.text)     // editing finished — validate, save
    }
}

    textFieldShouldReturn is where you decide what the Return key does — dismiss the keyboard, or jump focus to the next field in a form.

    First responder — why the keyboard shows up at all

    Here's the concept that ties it together. At any moment, at most one view is the first responder: the object currently receiving keyboard input. When a text field becomes first responder, the system slides the keyboard up. When it resigns, the keyboard slides away. Tapping a field makes it first responder automatically — but you can also drive it in code:

    field.becomeFirstResponder()   // programmatically focus → keyboard appears
field.resignFirstResponder()   // give up focus → keyboard dismisses

    First responder isn't only about keyboards — it's the entry point to UIKit's whole event-routing system, where unhandled events walk up a chain of objects looking for someone to handle them. That's the responder chain, and text input is your first real encounter with it.

    The classic pain point: keyboard avoidance

    Now the problem every UIKit app hits. The keyboard slides up and covers the very field the user is typing in. UIKit doesn't move your content out of the way automatically — you have to notice the keyboard's frame and shift your layout. The standard fix is to listen for the keyboard notifications and adjust a scroll view's insets:

    override func viewDidLoad() {
    super.viewDidLoad()
    let nc = NotificationCenter.default
    nc.addObserver(self, selector: #selector(keyboardWillShow),
                   name: UIResponder.keyboardWillShowNotification, object: nil)
    nc.addObserver(self, selector: #selector(keyboardWillHide),
                   name: UIResponder.keyboardWillHideNotification, object: nil)
}

@objc func keyboardWillShow(_ note: Notification) {
    guard let frame = note.userInfo?[UIResponder.keyboardFrameEndUserInfoKey] as? CGRect
    else { return }
    let overlap = frame.height - view.safeAreaInsets.bottom
    scrollView.contentInset.bottom = overlap        // push content up by the covered amount
    scrollView.verticalScrollIndicatorInsets.bottom = overlap
}

@objc func keyboardWillHide(_ note: Notification) {
    scrollView.contentInset.bottom = 0
    scrollView.verticalScrollIndicatorInsets.bottom = 0
}

    The keyboard's frame comes from the notification's userInfo because it varies — hardware keyboards, floating iPad keyboards, and different heights all report differently, so you read the actual frame rather than guessing. Put your fields inside a UIScrollView and adjusting contentInset.bottom lets the user scroll the covered field into view.

    The big box: UITextView

    For multi-line, scrollable editing, reach for UITextView. It has its own delegate, mirroring the text field's:

    let textView = UITextView()
textView.font = .preferredFont(forTextStyle: .body)   // Dynamic Type
textView.isScrollEnabled = true
textView.delegate = self
textView.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(textView)

extension MyViewController: UITextViewDelegate {
    func textViewDidChange(_ textView: UITextView) {
        characterCountLabel.text = "\(textView.text.count)"
    }
    func textViewDidEndEditing(_ textView: UITextView) {
        save(textView.text)
    }
}

    Note there's no shouldReturn here — in a multi-line editor, Return inserts a newline, which is exactly what you want. Dismissing the keyboard for a text view usually means adding a "Done" button to the keyboard's accessory view or handling a tap elsewhere on screen, then calling resignFirstResponder().

    iOS 26–27 note. Both controls fully support Genmoji and the system writing tools in the edit menu, and on iOS 26 the keyboard and text selection adopt the refreshed design automatically. If you build custom input accessory views, keep them anchored to the keyboard layout guide (view.keyboardLayoutGuide) rather than hard-coding heights — it tracks the live keyboard frame for you and removes most of the manual notification math above.

    The foundation

    • UITextField = a single-line text input (the ruled line) with a Return key you can act on.
    • UITextView = a multi-line, scrollable text editor (the big box) for paragraphs and documents.
    • delegate = the object a field or view calls back on editing events (textFieldShouldReturn, textFieldDidEndEditing, textViewDidChange).
    • first responder = the one object currently receiving keyboard input; becoming it shows the keyboard, resigning hides it.
    • becomeFirstResponder / resignFirstResponder = programmatically take or give up focus (and thus show/dismiss the keyboard).
    • keyboardType / returnKeyType = configure which keyboard layout and which Return-key label the user sees.
    • keyboard avoidance = shifting content so the keyboard doesn't cover the active field, via keyboard-frame notifications or keyboardLayoutGuide.
    • keyboard notifications = keyboardWillShow/Hide, whose userInfo carries the live keyboard frame to offset by.

    10 — UIVisualEffectView, Blur & Liquid Glass

    Start here — the plain idea

    Imagine you hold a pane of frosted bathroom glass in front of a busy poster. You still sense the poster — the colors, the bright and dark regions — but the details melt into a soft wash. Move the glass and the blur travels with it, always sampling whatever happens to be behind it right now. That is exactly what a UIVisualEffectView is: a live pane of frosted glass you lay over your content. It doesn't hold any content of its own by default; it samples the pixels behind it and blurs and tints them in real time.

    Because the blur is live, it feels like a physical material rather than a static image. Scroll a photo underneath and the frosted bar above it shimmers and shifts as new colors pass behind the glass. This is why iOS navigation bars, tab bars, notification banners, and Control Center all feel like they're floating just above your content — they are, quite literally, panes of system glass.

    The one catch with frosted glass is that anything you place on it — a label, an icon — can get lost against the busy, low-contrast wash behind it. So UIKit gives you a companion trick called vibrancy that re-tints your foreground content so it stays legible no matter what scrolls behind. Once you understand "glass pane plus vibrant content on top," the whole family of effects — old blur, new Liquid Glass — clicks into place.

    The classic blur: UIBlurEffect in a UIVisualEffectView

    The oldest and most common recipe is a blur. You create a UIVisualEffectView, hand it a UIBlurEffect with one of the system material styles, and add it to your view hierarchy on top of whatever you want frosted.

    let blur = UIBlurEffect(style: .systemMaterial)
let glass = UIVisualEffectView(effect: blur)
glass.frame = view.bounds
glass.autoresizingMask = [.flexibleWidth, .flexibleHeight]
view.addSubview(glass)   // sits ON TOP of content already added

    The style is not a fixed color — it is a material that adapts to light and dark mode automatically. The system material styles come in a thickness ladder, from barely-there to nearly opaque:

    UIBlurEffect(style: .systemUltraThinMaterial)  // most see-through
UIBlurEffect(style: .systemThinMaterial)
UIBlurEffect(style: .systemMaterial)           // the everyday default
UIBlurEffect(style: .systemThickMaterial)
UIBlurEffect(style: .systemChromeMaterial)     // for bars and chrome

    Pick a thicker material when you need the content behind to recede and your foreground to dominate; pick a thinner one when you want the background to stay present. Prefer these system…Material styles over the ancient .light / .dark / .extraLight cases — the material styles are the modern, adaptive ones.

    Putting content on the glass: contentView

    Here's the mistake everyone makes once: they add a label as a subview of the effect view directly. Don't. A UIVisualEffectView has a dedicated contentView that sits correctly above the blur layer. Anything you want to appear on the frosted pane goes there.

    let label = UILabel()
label.text = "Now Playing"
label.translatesAutoresizingMaskIntoConstraints = false
glass.contentView.addSubview(label)   // NOT glass.addSubview(...)

NSLayoutConstraint.activate([
    label.centerXAnchor.constraint(equalTo: glass.contentView.centerXAnchor),
    label.centerYAnchor.constraint(equalTo: glass.contentView.centerYAnchor),
])

    Vibrancy: making labels read against the blur

    Plain white or black text on a busy blur can wash out. UIVibrancyEffect fixes this by sampling the blurred background and adjusting your foreground content's color and contrast so it stays crisp. The pattern is a nested effect view: a vibrancy effect view lives inside the blur effect view's contentView, and your labels live inside the vibrancy view's contentView.

    let blur = UIBlurEffect(style: .systemMaterial)
let glass = UIVisualEffectView(effect: blur)

let vibrancy = UIVibrancyEffect(blurEffect: blur, style: .label)
let vibrantView = UIVisualEffectView(effect: vibrancy)
vibrantView.frame = glass.bounds
vibrantView.autoresizingMask = [.flexibleWidth, .flexibleHeight]
glass.contentView.addSubview(vibrantView)

let label = UILabel()
label.text = "Vibrant, legible text"
vibrantView.contentView.addSubview(label)   // reads cleanly over the blur

    The style: on UIVibrancyEffect (.label, .secondaryLabel, .fill, .separator, …) tells the system what role the content plays, so it can tune the vibrancy the same way the system tunes its own labels. Match the role and your UI feels native.

    iOS 26 Liquid Glass

    iOS 26 introduced Liquid Glass — a richer material that doesn't just blur, it bends and refracts light around its edges, catches specular highlights, and reacts to motion, so it behaves like a real slab of glass rather than a flat frost. There are two ways it reaches your app.

    The free way — rebuild against the latest SDK. System components (navigation bars, toolbars, tab bars, search bars, sheets) automatically adopt Liquid Glass when your app is compiled with the iOS 26 SDK. You often get the new look on standard bars with no code change at all — just adopt the SDK and let the system restyle its own chrome.

    The custom way — UIGlassEffect. For your own surfaces, there's a new effect you host in the same old UIVisualEffectView. It's the Liquid Glass sibling of UIBlurEffect.

    let glassEffect = UIGlassEffect()
let panel = UIVisualEffectView(effect: glassEffect)
panel.frame = CGRect(x: 40, y: 120, width: 300, height: 80)

let title = UILabel()
title.text = "Custom glass panel"
panel.contentView.addSubview(title)     // same contentView rule as before
view.addSubview(panel)

    When you have several glass elements near each other, you don't want them to look like a pile of separate panes. UIGlassContainerEffect groups them so they blend and merge — as two glass pieces approach, their edges flow together like droplets, and as they part they separate again. You host the container in one effect view and place the individual glass views inside it.

    let container = UIGlassContainerEffect()
let containerView = UIVisualEffectView(effect: container)

// Individual UIGlassEffect views added into containerView.contentView
// blend and merge as they move near each other.
containerView.contentView.addSubview(makeGlassChip(title: "One"))
containerView.contentView.addSubview(makeGlassChip(title: "Two"))
view.addSubview(containerView)

    The mental model stays identical to the classic blur: an effect goes into a UIVisualEffectView, and your content goes into its contentView. Only the effect object changed — UIBlurEffect became UIGlassEffect, and grouping became UIGlassContainerEffect.

    iOS 26–27 note

    iOS 26 shipped Liquid Glass fairly translucent, and some developers found busy backgrounds bled through system chrome and hurt legibility. At WWDC 2026, iOS 27 refined the material — the default transparency was reduced so glass surfaces read more solidly out of the box, with more consistent contrast. If you target iOS 27, expect your system bars to look a touch more opaque than the iOS 26 debut, and audit any custom UIGlassEffect surfaces where you leaned on heavy see-through.

    For how the effect actually works — the refraction, the edge highlights, the specular math that makes glass look like glass — see the shader decode.

    SwiftUI contrast

    In SwiftUI you rarely instantiate an effect view; you reach for modifiers. A blur behind content is .background(.ultraThinMaterial), and Liquid Glass is .glassEffect() with GlassEffectContainer playing the role of UIGlassContainerEffect. UIKit is more explicit — you build the effect view, choose its effect, and manage its contentView yourself — but the underlying materials are the same system materials SwiftUI draws from. Knowing the UIKit plumbing makes the SwiftUI one-liners far less mysterious.

    The foundation

    • UIVisualEffectView = a live pane that samples the content behind it and applies a visual effect (blur or glass) to it.
    • effect = the object plugged into the effect view that decides what it does — a UIBlurEffect, UIVibrancyEffect, UIGlassEffect, or UIGlassContainerEffect.
    • contentView = the subview of an effect view where your own labels and icons belong, so they sit above the effect layer.
    • system material styles = adaptive blur thicknesses (.systemUltraThinMaterial … .systemChromeMaterial) that respond to light and dark mode.
    • UIVibrancyEffect = re-tints foreground content sampled against the blur so labels stay legible; its style: matches a content role.
    • UIGlassEffect = the iOS 26 Liquid Glass effect for custom surfaces, hosted in a UIVisualEffectView just like a blur.
    • UIGlassContainerEffect = groups multiple glass elements so they blend and merge as they move near one another.
    • auto-adoption = system bars and toolbars take on Liquid Glass automatically when you build against the iOS 26+ SDK, no code change required.

    11 — Lists: UITableView & UICollectionView (Foundations)

    Start here — the plain idea

    Almost every app is, deep down, a scrolling list of things: messages, photos, settings, songs. UIKit has two workhorses for this. A UITableView is a list of rows stacked in a single column — think Settings, or a chat thread. A UICollectionView is the same idea set free from the single column: it can lay cells out in a grid, in flowing rows, in a mosaic, in whatever geometry you describe. A table is really just a collection view that only knows how to do one column.

    Now the trick that makes both of them fast, and it's a genuinely clever one. Imagine a list of ten thousand songs. If UIKit built ten thousand cell views up front, it would run out of memory before you scrolled an inch. So it cheats — beautifully. Only the cells you can actually see exist, plus a couple just off the edges. As a cell scrolls off the top, it isn't destroyed; it's rinsed clean and slid into a reuse queue, waiting to be handed back to you as a fresh cell appearing at the bottom. The same dozen or so cell objects get recycled over and over for the whole ten thousand rows.

    That single idea — cell reuse — is the beating heart of UIKit lists. Everything else (data sources, registration, layouts) exists to serve it. Get the recycling mental model in your bones and the rest of the API stops feeling arbitrary.

    The data source / delegate split

    UIKit lists don't hold your data. You hold your data; the list asks you about it. This is the classic two-role pattern:

    • The data source answers "what to show": how many sections, how many items, and — crucially — "give me a configured cell for this index path."
    • The delegate answers "what happens": the user tapped this row, this cell is about to appear, this one got highlighted.

    For a table, the historic form is your controller conforming to UITableViewDataSource and UITableViewDelegate:

    func tableView(_ tv: UITableView, numberOfRowsInSection s: Int) -> Int {
    songs.count
}

func tableView(_ tv: UITableView,
               cellForRowAt indexPath: IndexPath) -> UITableViewCell {
    // ... configure and return a cell (see reuse, below)
}

    The list calls cellForRowAt only for rows near the screen, and it calls it again every time a recycled cell needs new content. So this method runs constantly during scrolling — it must be cheap.

    dequeueReusableCell: the recycling in code

    You never make a cell with UITableViewCell() in the hot path. You dequeue one — asking the reuse queue for a recycled cell, or a brand-new one only if the queue is empty. Modern UIKit uses cell registration so the type and configuration are declared once, up front:

    let cellRegistration = UICollectionView.CellRegistration<UICollectionViewListCell, Song> {
    cell, indexPath, song in
    var config = cell.defaultContentConfiguration()
    config.text = song.title
    config.secondaryText = song.artist
    cell.contentConfiguration = config
}

    Then, when the list asks for a cell, you dequeue against that registration:

    let cell = collectionView.dequeueConfiguredReusableCell(
    using: cellRegistration, for: indexPath, item: song)

    The old table-view spelling of the same idea is dequeueReusableCell(withIdentifier:for:) after a register(_:forCellReuseIdentifier:). Same recycling, older ergonomics. Note the modern flow uses UIContentConfiguration (that defaultContentConfiguration()) instead of poking cell.textLabel?.text directly — the old cell subview properties are deprecated.

    Why reuse matters — the whole point

    Here is the consequence you must internalize: a cell you get back may still be wearing its previous row's data. Because it was recycled, its image view might hold the wrong photo, its label the wrong name, until you overwrite them. That's why the configuration block sets every field every time — you can't assume a fresh, blank cell. If you ever see a fast-scrolling list flash the wrong thumbnail for a split second, that's a reuse bug: someone forgot to reset a field, so the recycled cell showed stale content until the real image loaded.

    The payoff is enormous: constant memory no matter how long the list, and smooth 120Hz scrolling because UIKit is juggling a dozen cells instead of building thousands. This is the difference between a list that flies and one that stutters and crashes.

    Where this goes next

    This lesson is the foundation: the reuse mental model and a basic list on screen. Modern UIKit builds two big ideas on top, and each has its own deep dive.

    • Diffable data sources replace the "answer questions about my array" pattern with "hand me a snapshot of the current state, and I'll animate the difference." No more fragile manual insertRows/deleteRows bookkeeping. See diffable data sources.
    • Compositional layout lets you describe complex collection layouts — nested groups, orthogonal scrolling sections, self-sizing items — declaratively instead of subclassing layout objects. See compositional layout.
    • And under both of them, the scrolling itself — content offset, deceleration, prefetching — is UIScrollView machinery. See UIScrollView mechanics.

    iOS 26–27 note

    The list-cell APIs (CellRegistration, UICollectionViewListCell, UIContentConfiguration) are the sanctioned modern path — plain UITableView subclassing and cell.textLabel are legacy. On iOS 26+, list backgrounds and bars sit under Liquid Glass chrome, so give scrolling content sensible top/bottom content insets and let the system's glass bars float over your cells rather than fighting them.

    The foundation

    • cell reuse = only visible (plus nearby) cells exist; off-screen cells are recycled through a queue instead of destroyed.
    • reuse queue = the pool of clean, available cells the list draws from when a new row needs to appear.
    • data source = your object that answers how many items there are and returns a configured cell for an index path.
    • delegate = your object that reacts to events — selection, appearance, highlighting.
    • dequeueReusableCell = asking the queue for a recycled cell (or a new one only if none are free) rather than allocating per row.
    • cell registration = declaring a cell's type and configuration once, then dequeuing configured cells against it.
    • UIContentConfiguration = the modern, value-type way to fill a cell's content, replacing the old textLabel/imageView properties.
    • stale cell bug = forgetting to reset a field on a recycled cell, so it briefly shows the previous row's data.

    12 — UIViewController: The Unit of a Screen

    Start here — the plain idea

    Think of a play. Each scene has a stage full of props and actors — that's the visible stuff — and it has a stage manager standing in the wings who owns that scene: cueing entrances, managing what's on stage, deciding when the scene begins and ends. In UIKit, the stage is a view (a tree of UIViews), and the stage manager is a UIViewController. One view controller manages one screenful of UI — it owns a root view and all the logic wrapped around it.

    That word owns is the whole idea. A view controller isn't the pixels; it's the responsible adult for the pixels. It creates the view tree, holds references to the buttons and labels, responds when they're tapped, loads the data they display, and knows the lifecycle of the whole screen — when it's about to appear, when it's leaving, when memory is tight. If a screen is a self-contained little world, the view controller is the god of that world.

    Coming from SwiftUI this is a real mental gear-shift. A SwiftUI View is a lightweight value — a struct, cheap, thrown away and rebuilt constantly as state changes. A UIViewController is the opposite: a long-lived object (a class instance) that persists for as long as its screen is around, holding state and identity the entire time. You don't rebuild it every frame; you set it up once and it lives.

    The view and where it comes from

    Every view controller has a view property — the root of its view tree. You almost never create it eagerly. Instead the system creates it lazily, the first time someone actually asks for view (for instance, when the controller is about to go on screen). This is why touching controller.view too early can force an expensive load before you meant to.

    There are two ways the view gets built. If you want to build the whole hierarchy in code yourself, override loadView() and assign self.view:

    final class ProfileViewController: UIViewController {
    override func loadView() {
        let root = UIView()
        root.backgroundColor = .systemBackground
        view = root          // YOU supply the root view
    }
}

    Most of the time you don't override loadView() at all — you let UIKit make a plain root view for you, and you do your setup in viewDidLoad(), which runs exactly once, right after the view tree exists:

    final class ProfileViewController: UIViewController {
    private let nameLabel = UILabel()

    override func viewDidLoad() {
        super.viewDidLoad()          // always call super
        nameLabel.text = "Ada Lovelace"
        nameLabel.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(nameLabel)
        NSLayoutConstraint.activate([
            nameLabel.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            nameLabel.topAnchor.constraint(equalTo: view.safeAreaLayoutGuide.topAnchor, constant: 24),
        ])
    }
}

    Rule of thumb: loadView() is for creating the root view; viewDidLoad() is for populating and configuring it once it exists. One-time setup — subviews, constraints, initial data — belongs in viewDidLoad().

    The lifecycle at a glance

    viewDidLoad() fires once. But a screen can appear and disappear many times as the user navigates back and forth, so there's a second family of callbacks that fire on every appearance and departure:

    override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)   // about to become visible — refresh data, start timers
}
override func viewDidAppear(_ animated: Bool) {
    super.viewDidAppear(animated)    // now fully on screen — begin animations, analytics
}
override func viewWillDisappear(_ animated: Bool) {
    super.viewWillDisappear(animated) // leaving — save state, pause work
}

    The pairing is the thing to remember: viewDidLoad is once, at birth; viewWillAppear/viewWillDisappear are every time the screen comes and goes. Put "set up the furniture" work in viewDidLoad, and "the user is looking / no longer looking" work in the appear/disappear pair. The full sequence — including layout passes, viewWillLayoutSubviews, trait changes, and teardown order — is its own deep dive in VC lifecycle.

    Composition: view controller containment

    Here's the idea that saves you from thousand-line "mega controllers." A view controller can contain other view controllers. Instead of one controller doing everything on a complex screen, you break it into child controllers — a header controller, a list controller, a footer controller — and host them inside a parent. Each child stays a self-contained manager of its own patch of the screen.

    The system needs to know about this parent-child relationship so lifecycle events flow correctly to the children. There's a precise handshake:

    func embed(_ child: UIViewController, in container: UIView) {
    addChild(child)                       // 1. declare the relationship
    container.addSubview(child.view)      // 2. put the child's view on screen
    child.view.frame = container.bounds
    child.view.autoresizingMask = [.flexibleWidth, .flexibleHeight]
    child.didMove(toParent: self)         // 3. tell the child the move is done
}

    Removing a child is the same dance in reverse: child.willMove(toParent: nil), then child.view.removeFromSuperview(), then child.removeFromParent(). Skip the addChild/didMove bookkeeping and the child's viewWillAppear and friends silently stop firing — a classic "why isn't my child updating?" bug. Containment is how the big system containers (UINavigationController, UITabBarController) work too; you're using the same mechanism they do.

    SwiftUI contrast

    The gap is worth stating plainly. A SwiftUI View is a value — a struct that describes what the UI should look like right now, rebuilt from state every time state changes; you never hold onto one. A UIViewController is a long-lived object — a class instance with identity that persists across the whole life of its screen, owning mutable state, references, and a lifecycle. SwiftUI hides the appear/disappear machinery behind modifiers like .onAppear; UIKit hands it to you directly as overridable methods. When you bridge the two worlds (UIHostingController wraps a SwiftUI view in a view controller, and UIViewControllerRepresentable goes the other way), you're literally putting a value-world inside an object-world and vice versa.

    iOS 26–27 note

    On iOS 26+, view controllers presented as sheets and pushed onto navigation stacks pick up Liquid Glass chrome automatically, and the system leans harder on safeAreaLayoutGuide and viewIsAppearing(_:) (a slightly later, layout-ready cousin of viewWillAppear) for correct placement under floating glass bars. Pin subviews to the safe area rather than raw view bounds so your content doesn't slide under the glass.

    The foundation

    • UIViewController = a long-lived object that manages one screenful of UI, owning a root view and its logic.
    • view = the controller's root UIView, created lazily the first time it's needed.
    • loadView() = the hook for creating the root view yourself; skip it to get a plain system-supplied root.
    • viewDidLoad() = runs once after the view tree exists; the home for one-time subview and constraint setup.
    • viewWillAppear / viewDidAppear / viewWillDisappear = fire on every appearance and departure, for refresh/pause work.
    • containment = a view controller hosting child view controllers to compose a screen from smaller managers.
    • addChild / didMove(toParent:) = the handshake that wires a child in so its lifecycle events fire correctly.
    • value vs object = a SwiftUI View is a rebuilt struct; a UIViewController is a persistent class instance with identity and state.

    13 — Navigation & Bars

    Start here — the plain idea

    Think about how a web browser remembers where you've been. You click a link, a new page slides in on top of the old one, and the back button quietly holds the previous page for you. Click back and the top page falls away, revealing the one underneath, exactly as you left it. That's a stack — last in, first out — and it's the single most common way people move through an iOS app: tap a row, a detail screen pushes in; tap back, it pops away.

    A UINavigationController is that stack, made of whole screens. You hand it a starting screen (the "root"), and from then on you push new screens on and pop them off. It draws the bar across the top — with the back button, the title, and any buttons you add — and it animates the slide for you. You never manage the transition yourself; you just say "push this next."

    The other big organiser is side-by-side rather than stacked. A UITabBarController shows a row of tabs along the bottom — Home, Search, Profile — and each tab owns its own independent navigation stack. Switching tabs is like switching browser windows: nothing pops, each keeps its place. If you've used SwiftUI's NavigationStack and TabView, you already know the shapes; UIKit just hands you the controller objects directly.

    Pushing and popping — the navigation stack

    You rarely create a UINavigationController in isolation — you wrap it around your first screen and let it own the bar from there.

    let list = ProductListViewController()
let nav = UINavigationController(rootViewController: list)
// nav is now what you show; `list` is the bottom of its stack.

    From inside any screen that lives in a nav stack, self.navigationController is your handle to the controller. Pushing is one call:

    final class ProductListViewController: UIViewController {
    func openDetail(for product: Product) {
        let detail = ProductDetailViewController(product: product)
        navigationController?.pushViewController(detail, animated: true)
    }
}

    Popping usually happens for free — the user taps the back button. When you need to do it in code (say, after saving), you pop yourself:

    navigationController?.popViewController(animated: true)          // one level
navigationController?.popToRootViewController(animated: true)    // all the way home

    That's the whole mental model: push to go deeper, pop to come back. The stack is an array (navigationController?.viewControllers) you can even read or rewrite if you need to.

    The nav bar is configured per-screen, via navigationItem

    Here's the part that trips people up. The bar belongs to the navigation controller, but its contents — the title, the buttons — belong to whichever screen is on top. Each view controller carries a navigationItem describing what the bar should show while it is visible.

    override func viewDidLoad() {
    super.viewDidLoad()
    title = "Products"   // shortcut that sets navigationItem.title

    navigationItem.rightBarButtonItem = UIBarButtonItem(
        systemItem: .add,
        primaryAction: UIAction { [weak self] _ in self?.addProduct() }
    )
    navigationItem.leftBarButtonItem = UIBarButtonItem(
        title: "Edit", image: nil, primaryAction: UIAction { _ in }, menu: nil
    )
}

    Note the modern shape: UIBarButtonItem now takes a UIAction (or a UIMenu) directly, so you skip the old target:action: selector dance. Because the item lives on the screen, the bar updates automatically as screens push and pop — each one paints its own buttons and title.

    Large titles

    Since iOS 11 the bar can show a big, bold title that shrinks into the standard inline title as the user scrolls. It's a per-nav-controller opt-in, with a per-screen preference:

    nav.navigationBar.prefersLargeTitles = true

// On a specific screen that should stay inline (e.g. a deep detail page):
navigationItem.largeTitleDisplayMode = .never

    Turn large titles on at the top level; let leaf screens opt back to .never where a big title would feel heavy.

    The tab bar controller

    A UITabBarController holds an array of view controllers — often each one a UINavigationController — and shows a tab per section. Each child declares how it appears in the bar through its tabBarItem.

    let home = UINavigationController(rootViewController: HomeViewController())
home.tabBarItem = UITabBarItem(
    title: "Home", image: UIImage(systemName: "house"), tag: 0
)

let search = UINavigationController(rootViewController: SearchViewController())
search.tabBarItem = UITabBarItem(
    title: "Search", image: UIImage(systemName: "magnifyingglass"), tag: 1
)

let tabs = UITabBarController()
tabs.viewControllers = [home, search]
tabs.selectedIndex = 0

    Two composition rules worth remembering. First, the tab bar controller is almost always the outermost container, with a navigation controller inside each tab — that way each section keeps its own back stack. Second, set tabBarItem on the child controller, not on the tab bar controller; like navigationItem, appearance is described by the screen it belongs to.

    SwiftUI, for contrast

    In SwiftUI you describe the same structures declaratively — NavigationStack { … } with .navigationDestination, and TabView { … }.tabItem { … }. UIKit is the imperative underside: you allocate the controller, push and pop explicitly, and mutate navigationItem. The concepts map almost one-to-one, which is exactly why understanding the UIKit versions makes the SwiftUI ones stop feeling like magic. Under the hood, a SwiftUI NavigationStack is hosted inside a real UIKit navigation controller.

    iOS 26–27 note

    On iOS 26/27 the system bars adopt the Liquid Glass material automatically — the navigation bar, tab bar, and toolbar render as translucent, refractive glass that picks up the content scrolling beneath them. You don't opt in; standard UINavigationController and UITabBarController get the look for free, and content is expected to flow under the bars so the glass has something to refract (see 10-uivisualeffectview-and-liquid-glass). Two practical shifts: the tab bar can now shrink or collapse as the user scrolls to give content more room, and toolbars group their items into glass clusters, so lean on standard UIBarButtonItems and system symbols rather than custom backgrounds — custom opaque bar backgrounds fight the material. Configure bar appearance through UINavigationBarAppearance / UITabBarAppearance (standardAppearance, scrollEdgeAppearance) rather than the deprecated per-property setters, so your bars track Apple's evolving glass treatment instead of freezing an old look.

    The foundation

    • UINavigationController = a stack of full screens with a top bar; you push and pop.
    • pushViewController(_:animated:) / popViewController = go deeper / come back one level.
    • navigationItem = the per-screen description of the bar's title and buttons while that screen is on top.
    • UIBarButtonItem = a bar button; modern init takes a UIAction or UIMenu directly.
    • prefersLargeTitles = opt into big scroll-collapsing titles; largeTitleDisplayMode overrides per screen.
    • UITabBarController = side-by-side sections, each usually wrapping its own navigation stack.
    • tabBarItem = the per-child description of its tab's title and icon.
    • Liquid Glass bars = iOS 26/27 renders system bars as translucent glass automatically; configure via appearance objects.

    14 — Presenting: Sheets, Alerts & Popovers

    Start here — the plain idea

    Pushing (last lesson) is about going forward through a story — screen after screen, back button always available. But sometimes you don't want to advance the story; you want to interrupt it. A confirmation, a quick form, a share panel: something that appears on top, demands a moment of attention, and then goes away, leaving the screen underneath exactly where it was. That's modal presentation.

    Think of pushing as turning to the next page of a book, and presenting as sliding a sticky note over the page you're reading. The page didn't change — the note is just covering part of it, temporarily. When you peel the note off, there's your page, untouched. In UIKit you present a view controller with one call and dismiss it with another; the presenting screen waits underneath the whole time.

    Modern iOS leans hard on one particular kind of modal: the bottom sheet that slides up from the bottom edge and can rest at different heights — half-open or full. You've felt it everywhere: Maps, Music, the share sheet. UIKit gives you that behaviour through detents, and it's the workhorse of this lesson.

    Present and dismiss

    The two verbs mirror push/pop, but they're on any view controller, not a navigation controller:

    let compose = ComposeViewController()
present(compose, animated: true)

// From inside the presented screen, when it's done:
dismiss(animated: true)

    present shows the controller modally; dismiss removes the topmost thing you presented. There's an optional completion closure on both if you need to run code once the animation finishes. That's the entire lifecycle for a simple modal.

    Alerts and action sheets

    For the small stuff — "Are you sure?", "Delete this?" — you don't build a screen. You use UIAlertController, which comes in two styles. An alert is the centered box with a title and buttons; an action sheet slides choices up from the bottom (on iPhone) and is meant for "pick one of several actions."

    let alert = UIAlertController(
    title: "Delete draft?",
    message: "This can't be undone.",
    preferredStyle: .alert
)
alert.addAction(UIAlertAction(title: "Delete", style: .destructive) { _ in
    self.deleteDraft()
})
alert.addAction(UIAlertAction(title: "Cancel", style: .cancel))
present(alert, animated: true)

    The style on each action does visual work for you: .destructive renders red, .cancel is bolded and pinned to the bottom (and you get only one). For an action sheet, switch preferredStyle to .actionSheet:

    let sheet = UIAlertController(title: nil, message: nil, preferredStyle: .actionSheet)
sheet.addAction(UIAlertAction(title: "Take Photo", style: .default) { _ in })
sheet.addAction(UIAlertAction(title: "Choose from Library", style: .default) { _ in })
sheet.addAction(UIAlertAction(title: "Cancel", style: .cancel))
present(sheet, animated: true)

    One gotcha: on iPad an action sheet must be anchored to what triggered it (see popovers below), or UIKit will trap. Alerts, being centered, don't need anchoring.

    The modern bottom sheet — UISheetPresentationController and detents

    Here's the star. When you present a plain view controller, you can ask its presentation to behave as a resizable sheet with detents — the resting heights it snaps to. You reach the sheet controller through the presented view controller's sheetPresentationController.

    let editor = TagEditorViewController()

if let sheet = editor.sheetPresentationController {
    sheet.detents = [.medium(), .large()]     // half-height and full-height
    sheet.prefersGrabberVisible = true         // the little pull handle
    sheet.selectedDetentIdentifier = .medium
    sheet.prefersScrollingExpandsWhenScrolledToEdge = true
}

present(editor, animated: true)

    .medium() rests at roughly half the screen; .large() fills it like a normal modal. The user can drag between the detents you allow, and the grabber hints that it's draggable. This is how you build the "peek, then pull up for more" feeling without any custom animation code.

    You can also define custom detents by height, which is perfect for a compact panel:

    let small = UISheetPresentationController.Detent.custom(identifier: .init("small")) { context in
    context.maximumDetentValue * 0.3     // 30% of the available height
}
sheet.detents = [small, .large()]
sheet.largestUndimmedDetentIdentifier = small.identifier  // content below stays interactive at the small size

    largestUndimmedDetentIdentifier is a lovely touch: below that detent, the screen underneath isn't dimmed and stays tappable — so a small sheet can float over a still-usable map.

    Presentation style, and popovers on iPad

    modalPresentationStyle decides how a non-sheet modal covers the screen. The common values: .pageSheet (the default that gives you the detent-capable card), .formSheet (a smaller centered card), .fullScreen (opaque, covers everything — the old presenting screen stops rendering), and .overFullScreen (covers everything but keeps the screen behind visible, for translucency).

    editor.modalPresentationStyle = .fullScreen
present(editor, animated: true)

    On iPad, use .popover to attach a small floating panel to the control that opened it — a menu-like bubble with an arrow pointing at its source. Popovers require a source, or UIKit crashes:

    picker.modalPresentationStyle = .popover
picker.popoverPresentationController?.sourceView = sender          // a UIView
picker.popoverPresentationController?.sourceRect = sender.bounds
present(picker, animated: true)

    The same anchoring applies to an iPad action sheet: set alert.popoverPresentationController?.sourceView before presenting. On iPhone, popovers normally adapt into sheets automatically, which is exactly what you want.

    SwiftUI, for contrast

    SwiftUI wraps all of this behind view modifiers driven by state. A .sheet(isPresented:) gives you the same detent-capable card — and you tune it with .presentationDetents([.medium, .large]), which is a thin declarative skin over UISheetPresentationController. Alerts become .alert(_:isPresented:), action sheets .confirmationDialog, popovers .popover. You flip a @State boolean instead of calling present; the framework does the presenting and dismissing for you. Knowing the UIKit calls underneath tells you why the SwiftUI modifiers behave the way they do — including why detents look identical in both.

    iOS 26–27 note

    On iOS 26/27, presented sheets and popovers render with the Liquid Glass material and its refined depth and corner treatment, so they read as translucent glass floating over your content — another reason to prefer standard presentation over custom container views that would opt out of the material. Detents remain the recommended pattern, .custom detents can now resolve against the current context more smoothly, and Swift 6's concurrency checks mean present/dismiss and any sheetPresentationController mutation must run on the main actor. Configure the sheet through its properties rather than reaching for custom transition animations; the system's glass presentation is what users now expect.

    The foundation

    • present(_:animated:) / dismiss(animated:) = show a view controller modally on top / remove the one you presented.
    • UIAlertController = titled box of actions; .alert (centered) or .actionSheet (bottom choices).
    • UIAlertAction = one button; style .default / .destructive (red) / .cancel (bold, one only).
    • UISheetPresentationController = the controller that turns a modal into a resizable bottom sheet.
    • Detent = a resting height a sheet snaps to: .medium(), .large(), or .custom { … }.
    • largestUndimmedDetentIdentifier = below this detent, the screen underneath stays visible and interactive.
    • modalPresentationStyle = how a modal covers the screen: .pageSheet, .formSheet, .fullScreen, .overFullScreen, .popover.
    • Popover = an iPad floating panel anchored to a source view/rect; adapts to a sheet on iPhone.

    15 — Handling Touch: Gestures & Controls

    Start here — the plain idea

    A finger lands on the glass. Something has to decide: what did the user just touch, and what should happen? UIKit gives you two ways to answer, and the difference is worth getting straight from the start.

    The first way is a gesture recognizer: a small object you clip onto any view that watches the raw stream of touches and calls you when it recognises a pattern — a tap, a swipe, a pinch, a long press. The view itself can be a plain UIView; the recognizer is the brain you bolt on. Think of it like a motion sensor you stick on a wall: the wall does nothing special, the sensor notices "someone waved" and rings your bell.

    The second way is a UIControl — a view that already is a control, like a button, switch, or slider. It has touch handling baked in and emits tidy, semantic events ("I was tapped," "my value changed") rather than raw touches. You don't watch fingers; you subscribe to the meaningful moment. A light switch doesn't report "finger approaching, finger pressing, finger lifting" — it just tells you "I flipped."

    Both funnel into the same idea you'll use everywhere in UIKit: target-action, where you register "call this method (or closure) when that happens."

    Gesture recognizers with target-action

    You create a recognizer, point it at a method to call, and add it to a view. Here's a tap:

    final class CardViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        let tap = UITapGestureRecognizer(target: self, action: #selector(cardTapped))
        card.addGestureRecognizer(tap)
        card.isUserInteractionEnabled = true   // needed on views like UIImageView
    }

    @objc func cardTapped(_ recognizer: UITapGestureRecognizer) {
        let point = recognizer.location(in: card)   // where in the card it landed
        print("tapped at \(point)")
    }
}

    Three details that save headaches. The action method is @objc because target-action is built on the Objective-C runtime. The recognizer passes itself in, so you can ask it questions — location(in:), how many taps, etc. And some views (UIImageView notably) ship with isUserInteractionEnabled = false, so touches sail right past unless you turn it on.

    The family is broad: UITapGestureRecognizer, UIPanGestureRecognizer (drag), UIPinchGestureRecognizer, UIRotationGestureRecognizer, UILongPressGestureRecognizer, UISwipeGestureRecognizer. You configure them a little — a double-tap wants numberOfTapsRequired = 2; a long press wants minimumPressDuration.

    How a touch finds its recognizer — hit-testing and the responder chain

    Before any recognizer fires, UIKit has to figure out which view the touch is over. It does this by hit-testing: starting at the window, it walks down the view tree asking each view "does this point fall inside you, and are your subviews interested?" until it finds the deepest, front-most view under the finger. That view is the hit-test view, and the touch is delivered there.

    If nothing handles the touch at that view, it travels up the responder chain — view to superview to view controller and onward — until something responds or the touch is dropped. Gesture recognizers hook into this pipeline: they observe the touches heading to the hit-test view and can claim them. This is core UIKit machinery, and it's worth reading the full story in responder chain once these basics click.

    Continuous gestures and state

    A tap is instantaneous, but a pan or pinch unfolds over time — the finger keeps moving. Those recognizers report a state so you can react to the whole arc: .began, .changed (fires repeatedly as the finger moves), .ended, plus .cancelled / .failed. You almost always switch on it.

    @objc func handlePan(_ g: UIPanGestureRecognizer) {
    switch g.state {
    case .began:
        // remember the view's starting position
        startCenter = draggable.center
    case .changed:
        let t = g.translation(in: view)          // offset from where the finger started
        draggable.center = CGPoint(x: startCenter.x + t.x, y: startCenter.y + t.y)
    case .ended, .cancelled:
        let v = g.velocity(in: view)             // points/second — use it to fling
        settle(draggable, velocity: v)
    default:
        break
    }
}

    translation(in:) gives you how far the finger has moved since it landed, and velocity(in:) at .ended is what you feed into a spring so a flung view keeps its momentum. For the design side of that — rubber-banding, matching a spring to a throw — see Gestures & Haptics.

    Letting gestures cooperate

    By default two recognizers can compete, and only one wins. When you want both — say, pinch and rotate a photo at the same time — you become the recognizer's delegate and allow it:

    pinch.delegate = self
rotate.delegate = self

func gestureRecognizer(_ g: UIGestureRecognizer,
    shouldRecognizeSimultaneouslyWith other: UIGestureRecognizer) -> Bool {
    true
}

    There's also require(toFail:) to express ordering — the classic "only recognise a single tap after the double-tap has failed," so one tap doesn't fire on the way to two. Simultaneity and dependencies get their own deep treatment in Gestures & Haptics.

    UIControl and target-action

    Controls skip all the raw-touch bookkeeping. A UIButton, UISwitch, UISlider, or UISegmentedControl already interprets touches and emits a UIControl.Event. You attach handlers with addTarget (classic) or, better on modern UIKit, addAction with a closure:

    // Modern: a closure, no @objc selector needed.
let button = UIButton(configuration: .filled())
button.setTitle("Save", for: .normal)
button.addAction(UIAction { _ in self.save() }, for: .touchUpInside)

// A slider reporting live changes:
slider.addAction(UIAction { [weak self] action in
    let s = action.sender as! UISlider
    self?.brightness = s.value
}, for: .valueChanged)

// Classic target-action, which you'll still meet:
toggle.addTarget(self, action: #selector(toggleChanged), for: .valueChanged)

    The event names carry the meaning: .touchUpInside (the canonical "button tapped"), .valueChanged (slider/switch/segmented control moved), .editingChanged (text field text changed). Prefer addAction/UIAction in new code — it's closure-based, avoids the @objc selector, and is the direction the API is heading. UIAction is also the same currency you saw powering UIBarButtonItem and UIMenu back in the navigation lesson.

    SwiftUI, for contrast

    SwiftUI folds both paths into declarative modifiers and views: .onTapGesture, .gesture(DragGesture()), and controls like Button, Toggle, Slider that fire closures directly. There's no explicit target-action, no state switch — you get value bindings and gesture callbacks instead. But the machinery underneath is exactly what you're learning here: SwiftUI gestures are built over UIKit's recognizers and the same hit-test-then-respond pipeline, which is why their conflicts and priorities behave the way they do.

    iOS 26–27 note

    On iOS 26/27 the recognizer and control APIs are stable, and the guidance is firmly toward UIAction/addAction closures over @objc target-action selectors — cleaner under Swift 6, and it keeps your touch handling on the main actor where UIKit requires it. UIButton.Configuration (the .filled(), .tinted(), .plain() styles) is the modern way to build buttons that automatically adopt the current design language, including the Liquid Glass look on system-styled controls; avoid hand-rolling button backgrounds. Recognizer state, simultaneity, and velocity(in:) all work as before — the shift is stylistic (closures, configurations), not conceptual.

    The foundation

    • Gesture recognizer = an object clipped onto a view that recognises a touch pattern (tap, pan, pinch, long-press) and calls your action.
    • isUserInteractionEnabled = must be true for touches to reach a view; UIImageView defaults to false.
    • Hit-testing = walking down the view tree to find the deepest front-most view under the touch.
    • Responder chain = the view→superview→controller path a touch travels up until something handles it.
    • state = a continuous recognizer's phase: .began / .changed / .ended / .cancelled; switch on it.
    • translation(in:) / velocity(in:) = how far the finger moved / how fast — velocity feeds spring finishes.
    • Simultaneous recognition = allow two recognizers together via the delegate's shouldRecognizeSimultaneouslyWith.
    • UIControl / target-action = controls emit semantic UIControl.Events; wire them with addAction(_:for:) (modern) or addTarget(_:action:for:).

    16 — UIView Animation

    Start here — the plain idea

    Suppose you want a card to slide from the left edge into the center. The naive way would be to move it one pixel at a time, sixty times a second, doing the arithmetic yourself. That's exhausting and fragile. UIKit offers a far better deal: you don't describe the journey, you describe the destination. You say "its final position is the center, and I'd like that to take 0.3 seconds," and UIKit fills in every in-between frame for you.

    That's the whole idea of UIView animation — tweening. You change a view's properties to their end values inside an animation block, and instead of snapping there instantly, UIKit smoothly interpolates from the old values to the new ones over the duration you gave. You state the what; the framework computes the how.

    The catch, and it's an important one: only certain properties animate this way — the ones that are really just numbers UIKit can interpolate, like position, size, opacity, and transform. Change one of those inside the block and you get motion. Change something else (like the text of a label) and it just snaps. Learn which properties are animatable and this all becomes predictable.

    The classic block: UIView.animate

    The everyday tool is a class method that takes a duration and a closure. Inside the closure, you set the final state:

    card.alpha = 0
card.center.x = -100          // start off-screen left, invisible

UIView.animate(withDuration: 0.3) {
    card.alpha = 1
    card.center.x = self.view.bounds.midX   // slide to center, fade in
}

    UIKit snapshots the properties before the closure, runs the closure to learn the target values, then animates the difference. The animatable properties you'll reach for most: frame, bounds, center, alpha, transform, and backgroundColor. Note that frame and center don't play nicely together with transform — when you're using transforms, animate transform and leave frame alone.

    There's a fuller form with options, a delay, and a completion closure:

    UIView.animate(withDuration: 0.4, delay: 0.1,
    options: [.curveEaseInOut, .allowUserInteraction]) {
    self.panel.transform = CGAffineTransform(scaleX: 1.1, y: 1.1)
} completion: { finished in
    self.panel.transform = .identity   // settle back
}

    Curves — the shape of the motion

    Motion at a constant speed looks robotic; real things ease in and out. The options let you pick a timing curve: .curveEaseInOut (slow start, slow end — the natural default), .curveEaseIn, .curveEaseOut, and .curveLinear. The curve doesn't change where the view ends up or how long it takes — only the pacing along the way. If the vocabulary of easing feels fuzzy, the interaction-math course lays out exactly what these curves are as functions in springs & easing.

    UIViewPropertyAnimator — the modern, controllable tool

    UIView.animate is fire-and-forget: once it starts, you can't grab it. When you need to pause, reverse, or scrub an animation with a finger — think a swipe that drags a panel and follows the finger's position — you reach for UIViewPropertyAnimator. You build it, then start it, and you keep the object so you can control it.

    let animator = UIViewPropertyAnimator(duration: 0.4, curve: .easeInOut) {
    self.panel.transform = CGAffineTransform(translationX: 0, y: -200)
    self.panel.alpha = 1
}
animator.startAnimation()

// Later, driven by a pan gesture (0…1):
animator.pauseAnimation()
animator.fractionComplete = progress   // scrub to any point
// On release, let it finish or reverse:
animator.isReversed = shouldCancel
animator.continueAnimation(withTimingParameters: nil, durationFactor: 0)

    Because it's interruptible and scrubbable, UIViewPropertyAnimator is the natural partner to the pan gestures from the last lesson — you set fractionComplete from the finger's translation, and the view moves exactly as far as the drag. This is the modern default for anything interactive; keep UIView.animate for simple one-shot transitions.

    Springs — motion with weight

    Ease curves are smooth but a little lifeless. A spring overshoots slightly and settles, which reads as physical and alive — it's the feel of most iOS interactions. The classic API exposes damping and initial velocity:

    UIView.animate(withDuration: 0.5,
    delay: 0,
    usingSpringWithDamping: 0.7,       // <1 overshoots; closer to 1 = less bounce
    initialSpringVelocity: 0.5,        // hand off a gesture's velocity here
    options: []) {
    self.badge.transform = CGAffineTransform(scaleX: 1.2, y: 1.2)
}

    The newer, cleaner route describes the spring by feel with UISpringTimingParameters, which pairs perfectly with the property animator:

    let spring = UISpringTimingParameters(dampingRatio: 0.6,
    initialVelocity: CGVector(dx: 0, dy: velocity.y / 100))
let animator = UIViewPropertyAnimator(duration: 0, timingParameters: spring)
animator.addAnimations { self.sheet.center.y = self.restY }
animator.startAnimation()

    Passing a gesture's exit velocity into initialSpringVelocity (or the timing parameters) is what makes a flung view keep its momentum — the animation continues the throw rather than restarting from zero. The math of damping ratio, stiffness, and why a spring overshoots lives in springs & easing.

    It's all Core Animation underneath

    Here's the layer that ties everything together, literally. Every UIView is backed by a CALayer, and UIView animations don't move views frame-by-frame on the CPU — they configure Core Animation, which runs the interpolation on the render server. When you write UIView.animate, UIKit is really creating implicit CALayer animations for you. That's why the animatable UIView properties line up with animatable layer properties: they're the same properties. If you want to see the machinery directly, read implicit animations for the automatic case and CABasicAnimation for the explicit one. UIView animation is the friendly front door; Core Animation is the engine room.

    SwiftUI, for contrast

    SwiftUI expresses the same ideas as withAnimation { … } wrapping a state change, plus .animation(_:value:) and .transition(...), with .spring(...) and .easeInOut(...) as the curves. You mutate state and the framework diffs the before/after and tweens — conceptually identical to setting end values in a UIView block, just declarative. And it bottoms out in the very same Core Animation layer, which is why springs feel the same across UIKit and SwiftUI.

    iOS 26–27 note

    On iOS 26/27, UIViewPropertyAnimator with UISpringTimingParameters is the recommended path for interactive and interruptible motion, and the spring-by-feel initializers (damping ratio + velocity) are preferred over hand-tuned duration/damping numbers. Under Swift 6, all animation setup and the property mutations inside the block must run on the main actor. With the Liquid Glass design language, favor animating standard properties (transform, alpha, center) and let system controls animate their own material rather than cross-fading custom backgrounds; the system's motion is tuned to match the new depth and glass treatment.

    The foundation

    • Tweening = you set end values; UIKit interpolates every frame in between over a duration.
    • Animatable properties = the interpolatable ones: frame, bounds, center, alpha, transform, backgroundColor.
    • UIView.animate(withDuration:) = the simple fire-and-forget block for one-shot animations.
    • Timing curve = the pacing of the motion (.easeInOut, .easeIn, .easeOut, .linear); it shapes speed, not destination.
    • UIViewPropertyAnimator = the modern, interruptible, scrubbable animator; drive fractionComplete from a gesture.
    • Spring = overshoot-and-settle motion via damping ratio + initial velocity; feels physical.
    • initialSpringVelocity / UISpringTimingParameters = where you hand a gesture's exit velocity to a spring so a throw continues.
    • Core Animation = the CALayer-based engine UIView animations actually configure underneath.

    17 — Appearance & Adaptivity

    Start here — the plain idea

    Your app doesn't run in one fixed set of conditions. One person uses dark mode on a huge phone with tiny text; another uses light mode with the text cranked up for readability; a third has a bold accent color set system-wide. If you hardcode UIColor(white: 0.1, ...) and a 14-point font, you're building for exactly one of them and quietly failing the rest.

    The fix is to stop stating values and start stating intentions. Instead of "this text is dark gray," you say "this is the primary label color" — and let the system resolve what that actually means for the current mode, contrast setting, and device. Instead of "14-point system font," you say "this is body text" — and let it scale with the user's chosen text size. You describe the role; the system picks the pixels.

    This is the "make it feel native and accessible" capstone of the course. Almost none of it is extra work — it's mostly choosing the semantic option over the literal one. Do that, and your UI adapts to dark mode, Dynamic Type, high contrast, and the accent color for free, the way every first-party app does.

    Semantic and dynamic colors

    UIKit ships a palette of semantic colors named for their role, not their value. Each one automatically resolves to the right shade in light vs dark mode.

    view.backgroundColor = .systemBackground      // white in light, near-black in dark
label.textColor = .label                       // primary text, adapts automatically
subtitle.textColor = .secondaryLabel           // dimmer, still adaptive
divider.backgroundColor = .separator
button.tintColor = .systemBlue                 // adapts to the current appearance

    Reach for these before any literal color: .label, .secondaryLabel, .tertiaryLabel, .systemBackground, .secondarySystemBackground, .separator, and the .systemBlue/.systemRed/… family. When you genuinely need a custom brand color that also adapts, build one with UIColor(dynamicProvider:), which is handed the trait environment and returns the right color for it:

    let brand = UIColor { traits in
    traits.userInterfaceStyle == .dark
        ? UIColor(red: 0.40, green: 0.72, blue: 1.0, alpha: 1)   // lighter in dark
        : UIColor(red: 0.10, green: 0.35, blue: 0.9, alpha: 1)   // deeper in light
}
header.backgroundColor = brand

    The closure re-runs whenever the environment changes, so one brand constant is correct in every mode. Prefer defining adaptive colors in an asset catalog when you can — same effect, no code.

    The trait collection — the environment your view lives in

    How does a dynamic color know it's dark mode? Through the trait collection: a bundle of environmental facts attached to every view and view controller. It carries userInterfaceStyle (light/dark), size classes, preferredContentSizeCategory (the text-size setting), accessibilityContrast, display scale, and more.

    if traitCollection.userInterfaceStyle == .dark {
    // ... though you rarely branch like this — let semantic colors do it
}

    When the environment changes — the user flips to dark mode, rotates, or bumps text size — the trait collection changes and your views are told. The modern way to react is registerForTraitChanges, which replaces the old traitCollectionDidChange(_:) override (deprecated in recent SDKs):

    override func viewDidLoad() {
    super.viewDidLoad()
    registerForTraitChanges([UITraitUserInterfaceStyle.self]) { (self: Self, previous) in
        self.redrawCustomGraphics()   // only your hand-drawn stuff needs this
    }
}

    Note what needs this: standard views and semantic colors update themselves automatically. You only register when you're drawing something custom (a CGColor on a layer, a cached gradient) that the system can't refresh for you.

    Dynamic Type — text that scales

    The same "role, not value" idea governs fonts. Rather than a fixed point size, ask for a text style — .body, .headline, .title1, .caption1 — and the font scales with the user's text-size setting, including the large accessibility sizes.

    label.font = UIFont.preferredFont(forTextStyle: .body)
label.adjustsFontForContentSizeCategory = true   // update live when the setting changes
label.numberOfLines = 0                            // let it wrap when text grows

    That adjustsFontForContentSizeCategory = true is the line people forget — without it the font is picked once and never updates. For a custom font that should still scale, wrap it in a UIFontMetrics:

    let base = UIFont(name: "NewYork-Regular", size: 17)!
label.font = UIFontMetrics(forTextStyle: .body).scaledFont(for: base)

    SF Symbols — adaptive icons

    UIImage(systemName:) gives you a vector symbol from Apple's SF Symbols set. These aren't just icons — they're adaptive: they align to the text baseline, scale with Dynamic Type, pick up tintColor, and offer weights and rendering modes that match the surrounding text.

    let icon = UIImage(systemName: "bell.badge",
    withConfiguration: UIImage.SymbolConfiguration(textStyle: .body))
let iconView = UIImageView(image: icon)
iconView.tintColor = .systemBlue

// Multicolor / hierarchical rendering for depth:
let config = UIImage.SymbolConfiguration(hierarchicalColor: .systemIndigo)
button.setImage(UIImage(systemName: "square.stack.3d.up", withConfiguration: config), for: .normal)

    Because they respond to the text style and tint, symbols stay visually consistent with your labels in every mode and size — the opposite of shipping fixed-size bitmap icons.

    tintColor inheritance

    tintColor is the accent that flows down the view tree. Set it on a container (or the window) and every child that doesn't override it inherits — buttons, symbol images, switches, and controls all pick it up. Setting nil means "inherit from my superview."

    view.tintColor = .systemIndigo   // buttons and symbols below now tint indigo

    This is how you theme a whole screen with one line, and why individual controls usually look right without you touching each one. It mirrors how the system propagates the user's accent color from the top down.

    iOS 26–27 note

    On iOS 26/27, adaptivity matters more than ever because the Liquid Glass design language makes surfaces translucent — content and controls sit over refractive glass, so semantic colors and system materials (.systemBackground, UIBlurEffect, vibrancy) are what keep contrast correct as the background shifts; hardcoded colors look wrong against the moving glass. Use registerForTraitChanges rather than the deprecated traitCollectionDidChange, prefer asset-catalog or dynamic colors over literals, keep adjustsFontForContentSizeCategory = true, and lean on SF Symbols so icons track weight, scale, and tint automatically. Under Swift 6, trait-change handlers and appearance updates run on the main actor. The through-line: describe roles, let the system resolve values, and your UI adapts to appearance, contrast, text size, and the evolving design language without rework.

    The foundation

    • Semantic color = a color named for its role (.label, .systemBackground, .separator) that resolves per appearance.
    • UIColor(dynamicProvider:) = a custom color whose closure returns the right value for the current traits.
    • Trait collection = the environment bundle on every view/VC: userInterfaceStyle, size classes, content-size category, contrast.
    • registerForTraitChanges = the modern replacement for traitCollectionDidChange; react only for custom-drawn content.
    • Dynamic Type = fonts by text style (.body, .headline) that scale with the user's setting; needs adjustsFontForContentSizeCategory = true.
    • UIFontMetrics = scales a custom font in step with a text style.
    • SF Symbols = UIImage(systemName:) vector icons that adapt to text style, weight, scale, and tintColor.
    • tintColor inheritance = the accent flows down the view tree; children inherit unless they override.

    18 — Bridging, Part 1: UIKit Inside SwiftUI

    Start here — the plain idea

    First, a myth to clear up: when you write a SwiftUI Button, it is not secretly a UIButton. SwiftUI is its own rendering system — it draws its own controls from scratch. So there's no literal "this SwiftUI line becomes that UIKit line" translation. What there is, is a conceptual twin: a SwiftUI Button plays the same role a UIButton plays, a Text plays the role of a UILabel, a List the role of a UITableView. Same job, two separate implementations.

    That matters because 99% of the time you should just use the SwiftUI control — it's less code and it's native. You only reach across to UIKit when SwiftUI doesn't have the thing you need (a map, a camera picker, a mature text editor, precise scroll control). When that happens, you don't rewrite the UIKit view in SwiftUI — you wrap it in a little adapter so SwiftUI can place it like any other view.

    Think of the wrapper as a power adapter on a trip: the UIKit view is a perfectly good appliance, it just has the wrong plug for SwiftUI's sockets. UIViewRepresentable is the adapter that lets you plug it in.

    The conceptual map (SwiftUI ↔ UIKit twins)

    Before wrapping anything, it helps to know which UIKit class each SwiftUI element corresponds to — this is the "how would I write this in UIKit?" answer:

    SwiftUI UIKit twin
    Button UIButton
    Text UILabel
    Image UIImageView
    TextField UITextField
    TextEditor UITextView
    Toggle UISwitch
    Slider UISlider
    HStack / VStack UIStackView
    ScrollView UIScrollView
    List UITableView
    LazyVGrid / grids UICollectionView
    NavigationStack UINavigationController
    TabView UITabBarController
    .sheet / .alert present(_:animated:) / UIAlertController
    a View a UIView or UIViewController

    Same roles, different engines. The point of bridging is: when the SwiftUI twin can't do what you need, borrow the UIKit one.

    The adapter: UIViewRepresentable

    To place a UIView inside SwiftUI, you make a struct that conforms to UIViewRepresentable and implement two methods:

    struct BlurView: UIViewRepresentable {
    var style: UIBlurEffect.Style

    // 1. Build the UIKit view ONCE.
    func makeUIView(context: Context) -> UIVisualEffectView {
        UIVisualEffectView(effect: UIBlurEffect(style: style))
    }

    // 2. Sync SwiftUI state INTO the UIKit view — runs every time
    //    a piece of SwiftUI state this view reads has changed.
    func updateUIView(_ view: UIVisualEffectView, context: Context) {
        view.effect = UIBlurEffect(style: style)
    }
}

    Now BlurView(style: .systemMaterial) is a first-class SwiftUI view — you can put it in a ZStack, give it .frame, everything.

    The mental model is the two-phase life:

    • makeUIView = birth. Runs once. Create and configure the object.
    • updateUIView = news bulletin. Runs whenever relevant SwiftUI state changes. This is a one-way push — SwiftUI → UIKit. You copy the latest SwiftUI values onto the UIKit view here. (Don't create the view here; just update it.)

    This is exactly SwiftUI's own model — describe the desired state, let update reconcile it — just applied to a foreign object.

    Turning up the heat: talking back with a Coordinator

    updateUIView only goes one way (SwiftUI → UIKit). But UIKit views talk back through delegates and target-action — reference-based callbacks. SwiftUI structs are value types and can't be a delegate. The fix is the Coordinator: a companion object (usually an NSObject) that adopts the delegate protocols and forwards events into SwiftUI, typically by writing to a @Binding.

    struct SearchBar: UIViewRepresentable {
    @Binding var text: String

    func makeCoordinator() -> Coordinator { Coordinator(self) }

    func makeUIView(context: Context) -> UISearchBar {
        let bar = UISearchBar()
        bar.delegate = context.coordinator     // the Coordinator is the delegate
        return bar
    }
    func updateUIView(_ bar: UISearchBar, context: Context) {
        bar.text = text                        // SwiftUI → UIKit
    }

    class Coordinator: NSObject, UISearchBarDelegate {
        let parent: SearchBar
        init(_ parent: SearchBar) { self.parent = parent }
        func searchBar(_ bar: UISearchBar, textDidChange s: String) {
            parent.text = s                    // UIKit event → SwiftUI @Binding
        }
    }
}

    Now data flows both ways: updateUIView pushes the binding's value in; the Coordinator pushes user edits back out. context.coordinator is how makeUIView reaches the coordinator instance SwiftUI created for you via makeCoordinator.

    Wrapping a whole controller

    Some UIKit things are view controllers, not views — PHPickerViewController (photo picker), SFSafariViewController, AVPlayerViewController. For those, use the sibling protocol with the exact same shape:

    struct PhotoPicker: UIViewControllerRepresentable {
    @Binding var image: UIImage?
    func makeUIViewController(context: Context) -> PHPickerViewController { … }
    func updateUIViewController(_ vc: PHPickerViewController, context: Context) {}
    func makeCoordinator() -> Coordinator { Coordinator(self) }   // adopts PHPickerViewControllerDelegate
}

    Rule of thumb: wrap a UIView with UIViewRepresentable; wrap a UIViewController with UIViewControllerRepresentable.

    The sizing gotcha (the thing that bites everyone)

    SwiftUI needs to know how big your wrapped view wants to be. If your bridged view collapses to zero or blows up, implement sizeThatFits (iOS 16+) so SwiftUI's layout can measure it:

    func sizeThatFits(_ proposal: ProposedViewSize,
                  uiView: UIView, context: Context) -> CGSize? {
    uiView.systemLayoutSizeFitting(UIView.layoutFittingCompressedSize)
}

    Otherwise give it an explicit .frame. This is the same intrinsic-content-size idea from 04-auto-layout-and-constraints, now negotiated across the boundary.

    The foundation

    • SwiftUI ≠ UIKit under the hood = a SwiftUI Button is its own thing, not a wrapped UIButton; they're conceptual twins, not the same object.
    • conceptual map = every SwiftUI element has a UIKit twin (Button↔UIButton, List↔UITableView…) — that's "how you'd write it in UIKit."
    • UIViewRepresentable = the adapter that lets a real UIView live inside SwiftUI.
    • makeUIView = build once (birth); updateUIView = push SwiftUI state into UIKit on every change.
    • Coordinator = a reference-type companion that adopts delegates/target-action and pushes UIKit events back into SwiftUI (usually via @Binding).
    • UIViewControllerRepresentable = same pattern for wrapping a whole UIViewController (pickers, players, Safari).
    • sizeThatFits = tell SwiftUI how big the wrapped view wants to be, or it may size wrong.

    19 — Bridging, Part 2: SwiftUI Inside UIKit

    Start here — the plain idea

    Now the other direction. You have a UIKit app — storyboards, view controllers, the works — and you want to build one new screen (or one cell, or one panel) in SwiftUI without rewriting everything. The bridge is a single class: UIHostingController.

    Think of it as a shipping container. SwiftUI views can't be dropped into a UIKit navigation stack directly — they're the wrong shape (a UIViewController is what UIKit moves around). UIHostingController is a real UIViewController with a SwiftUI view sealed inside; UIKit handles the container, and SwiftUI runs happily within it. Anywhere UIKit expects a view controller, you can now hand it a screenful of SwiftUI.

    The two directions together give you the "islands" architecture: a mostly-UIKit app with SwiftUI islands (this lesson), or a mostly-SwiftUI app with UIKit islands (Part 1). Real apps in 2026 are almost always hybrids like this.

    The simplest bridge: push a SwiftUI screen

    UIHostingController(rootView:) wraps any SwiftUI view. Because the result is a UIViewController, every UIKit navigation API just works:

    let profile = UIHostingController(rootView: ProfileView(user: user))
navigationController?.pushViewController(profile, animated: true)   // pushes SwiftUI onto a UIKit stack
// or present it, or set it as a tab's root — all normal UIKit

    That's the whole "hello world." The SwiftUI view renders, gets safe areas, participates in the nav bar — it's a citizen of the UIKit app.

    Turning up the heat 1: embedding, not just pushing

    Often you don't want a whole screen — you want a SwiftUI panel inside an existing UIKit view controller (a chart in a dashboard, say). That's standard view-controller containment (the addChild dance from 12-uiviewcontroller):

    let chart = UIHostingController(rootView: ChartView(data: data))
addChild(chart)                                   // 1. register as a child
chart.view.translatesAutoresizingMaskIntoConstraints = false
containerView.addSubview(chart.view)              // 2. place its view
NSLayoutConstraint.activate([ /* pin chart.view */ ])
chart.didMove(toParent: self)                     // 3. tell it the move is done

    The three steps (addChild → add the view → didMove) are the containment contract; skip them and lifecycle events (viewDidAppear, etc.) won't fire correctly for the SwiftUI island.

    Turning up the heat 2: SwiftUI cells with UIHostingConfiguration

    The cleanest hybrid of all (iOS 16+): a UITableView/UICollectionView cell whose content is SwiftUI, with no hosting controller to manage. You hand a UIHostingConfiguration to the cell's contentConfiguration:

    cell.contentConfiguration = UIHostingConfiguration {
    HStack {
        Image(systemName: item.icon)
        Text(item.title).font(.headline)
        Spacer()
    }
}

    This is the sweet spot for modernizing a UIKit list one row at a time — you get SwiftUI's layout inside UIKit's battle-tested reuse machinery (the cell-reuse idea from 11-tableview-and-collectionview).

    Data across the boundary — the part people get wrong

    Getting data in and events out of a SwiftUI island needs a little care, because a UIHostingController's rootView is a value captured at creation.

    • Data in (simple): for one-shot values, just pass them: UIHostingController(rootView: ProfileView(user: user)).
    • Data in (live updates): if the data changes over time, don't keep recreating the root view — give the SwiftUI view an @Observable model (or ObservableObject) that UIKit holds and mutates; SwiftUI re-renders automatically when the model changes. You can also reassign host.rootView = ... to push a fresh value, but an observable model is cleaner.
    • Events out: to get taps/results back into UIKit, pass a closure into the SwiftUI view (ProfileView(onSave: { … })) — the SwiftUI side calls it, your UIKit code runs. (A shared observable works too.)
    let model = ProfileModel(user: user)             // @Observable, held by UIKit
let host = UIHostingController(
    rootView: ProfileView(model: model, onDone: { [weak self] in
        self?.navigationController?.popViewController(animated: true)  // event → UIKit
    })
)
model.user = updatedUser                          // later: SwiftUI re-renders itself

    The sizing gotcha (reverse of last lesson)

    A UIHostingController doesn't always report its SwiftUI content's size to UIKit Auto Layout, so an embedded island can come out zero-height. Fix it with:

    host.sizingOptions = .intrinsicContentSize        // iOS 16+: report SwiftUI's size to Auto Layout

    …or pin explicit constraints. (Mirror of Part 1's sizeThatFits — each side has to tell the other how big things are.)

    Which direction do I use?

    • Mostly SwiftUI app, need one UIKit thing (map, camera, UITextView) → wrap it with a Representable (Part 1).
    • Mostly UIKit app, adding new features → build them in SwiftUI and drop them in with UIHostingController / UIHostingConfiguration (this lesson).
    • Keep the boundary thin and one-directional per island — a clear owner on each side avoids update loops.

    The foundation

    • UIHostingController = a real UIViewController with a SwiftUI view inside — the bridge from SwiftUI into a UIKit app.
    • push/present/set as root = anywhere UIKit takes a view controller, a hosting controller works.
    • containment = addChild → add .view → didMove to embed a SwiftUI island inside an existing VC.
    • UIHostingConfiguration = make a table/collection cell's content be SwiftUI directly (iOS 16+) — the cleanest hybrid.
    • data in = pass values, or (for live updates) an @Observable model UIKit mutates; events out = a closure the SwiftUI view calls.
    • sizingOptions = .intrinsicContentSize = let the hosted SwiftUI report its size to UIKit Auto Layout.
    • islands architecture = real apps mix both directions; keep each boundary thin with one clear owner.

    20 — Building Custom Composite Views

    Start here — the plain idea

    A composite view is your OWN reusable brick, made of smaller bricks. Think of an AvatarBadge: it's really an image view, a name label, and a little online-status dot — three tiny pieces. But you don't want the rest of the app to know or care about those three pieces. You want to write AvatarBadge(), hand it a user, and be done.

    That's the whole idea. You take a cluster of subviews that always travel together, wrap them in a single UIView subclass, and seal the internals inside. The outside world sees one clean object with a small, friendly surface — a bit like buying a pre-assembled LEGO minifig instead of hunting for the head, torso, and legs every time. You assemble it once, name it, and reuse it everywhere.

    This is the same instinct you already have in SwiftUI, where you factor a chunk of body into its own View (see View Composition). In UIKit the mechanics are more manual — you build the pieces yourself and wire up their layout — but the payoff is identical: one name, one job, reused without copy-paste.

    The shape of the thing — subclass UIView

    Every custom composite view starts as a UIView subclass, and every UIView subclass has to reckon with two init paths: init(frame:) (created in code) and required init?(coder:) (created from a storyboard or nib). Both must end up in the same place, so you funnel them through a shared commonInit() that builds the internal subviews exactly once.

    final class AvatarBadge: UIView {
    override init(frame: CGRect) {
        super.init(frame: frame)
        commonInit()
    }

    required init?(coder: NSCoder) {
        super.init(coder: coder)
        commonInit()
    }

    private func commonInit() {
        // build internal subviews ONCE, here
    }
}

    The rule to internalize: commonInit() is where the view assembles itself, and it runs no matter how the view was created. If you build subviews anywhere else — like layoutSubviews, which runs repeatedly — you'll stack duplicates on every layout pass.

    Turning up the heat 1: build and lay out the internals

    Inside commonInit() you create the pieces and pin them with Auto Layout (see 04-auto-layout-and-constraints). Because the internals never escape the class, you're free to use whatever layout is cleanest — often a UIStackView (05-uistackview) to avoid hand-writing constraints between siblings.

    final class AvatarBadge: UIView {
    private let imageView = UIImageView()
    private let nameLabel = UILabel()
    private let statusDot = UIView()
    private lazy var stack = UIStackView(arrangedSubviews: [imageView, nameLabel])

    // ...inits funnel into commonInit()...

    private func commonInit() {
        imageView.contentMode = .scaleAspectFill
        imageView.clipsToBounds = true
        nameLabel.font = .preferredFont(forTextStyle: .headline)

        statusDot.backgroundColor = .systemGreen
        statusDot.layer.cornerRadius = 5

        stack.axis = .horizontal
        stack.spacing = 8
        stack.alignment = .center
        stack.translatesAutoresizingMaskIntoConstraints = false
        addSubview(stack)
        addSubview(statusDot)

        NSLayoutConstraint.activate([
            stack.leadingAnchor.constraint(equalTo: leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: trailingAnchor),
            stack.topAnchor.constraint(equalTo: topAnchor),
            stack.bottomAnchor.constraint(equalTo: bottomAnchor),

            imageView.widthAnchor.constraint(equalToConstant: 40),
            imageView.heightAnchor.constraint(equalTo: imageView.widthAnchor),

            statusDot.widthAnchor.constraint(equalToConstant: 10),
            statusDot.heightAnchor.constraint(equalTo: statusDot.widthAnchor),
            statusDot.trailingAnchor.constraint(equalTo: imageView.trailingAnchor),
            statusDot.bottomAnchor.constraint(equalTo: imageView.bottomAnchor),
        ])
    }
}

    Notice imageView.layer.cornerRadius isn't set to make it round — you'd do that in layoutSubviews once the width is known, or use a fixed radius. The important point is structural: everything the badge needs lives inside, pinned to self.

    Turning up the heat 2: a clean public API

    The internals are now private. What does the outside get? A small, deliberate surface — nothing more. There are two good shapes, and you'll mix them:

    Configure with a model. For anything with several fields, take a value type and update in one call:

    struct AvatarModel {
    let image: UIImage?
    let name: String
    let isOnline: Bool
}

extension AvatarBadge {
    func configure(with model: AvatarModel) {
        imageView.image = model.image
        nameLabel.text = model.name
        statusDot.isHidden = !model.isOnline
    }
}

    Settable properties with didSet. For one-off toggles, a property that pushes into the internals reads nicely at the call site:

    var name: String = "" {
    didSet { nameLabel.text = name }
}

    Events out via closures. The internals should never reach up and grab a view controller. Instead, expose a closure the owner sets, and call it when something happens inside:

    var onTap: (() -> Void)?

private func commonInit() {
    // ...
    let tap = UITapGestureRecognizer(target: self, action: #selector(handleTap))
    addGestureRecognizer(tap)
}

@objc private func handleTap() { onTap?() }

    Now the whole contract is: configure(with:), maybe a property or two, and onTap. That's the entire brick as far as the app is concerned.

    Turning up the heat 3: intrinsicContentSize

    Here's the piece people forget. Auto Layout wants to know how big your view wants to be when nothing else pins its size. A stack of internals often gives it that for free (the constraints propagate up), but when they don't — or when you want a guaranteed natural size — you override intrinsicContentSize:

    override var intrinsicContentSize: CGSize {
    let labelSize = nameLabel.intrinsicContentSize
    return CGSize(width: 40 + 8 + labelSize.width,
                  height: max(40, labelSize.height))
}

    And whenever the content changes in a way that changes that natural size, you must tell Auto Layout the old answer is stale:

    var name: String = "" {
    didSet {
        nameLabel.text = name
        invalidateIntrinsicContentSize()   // re-ask on the next layout pass
    }
}

    Skip invalidateIntrinsicContentSize() and your badge will keep reporting its old size after the name changes — the classic "why is my custom view the wrong width" bug.

    The key decision: composite UIView vs child UIViewController

    Everything above builds a plain UIView. Sometimes that's the wrong tool. The question to ask: does this thing need a lifecycle?

    • Reach for a composite UIView when the thing is just visuals plus local interaction — a badge, a card, a rating control, a custom slider. No screen appearance to track, no view-controller-only APIs. This is the common case, and it's lighter: no containment dance, no lifecycle overhead.
    • Reach for a child UIViewController (see 12-uiviewcontroller) when you genuinely need VC machinery: viewWillAppear/viewDidAppear callbacks, appearance transitions, trait/rotation handling you want delivered per-component, or a VC-only API (a UIPageViewController, a hosting controller, something that presents). Then you use view-controller containment — addChild → add the view → didMove(toParent:) — instead of a bare subview.

    A useful heuristic: if you find yourself wishing your UIView had viewDidAppear, that's the signal you actually wanted a child view controller. Don't fake lifecycle on a plain view; promote it.

    The foundation

    • composite view = a UIView subclass built from smaller subviews, sealed so the app uses it as one reusable brick.
    • commonInit() = the single shared setup both init(frame:) and required init?(coder:) funnel into, building subviews exactly once.
    • internal layout = pin the internals to self with Auto Layout or a UIStackView; they never escape the class.
    • public API = a small deliberate surface: configure(with:) for models, didSet properties for toggles.
    • events out = expose closures like var onTap: (() -> Void)? so the view reports up without knowing its owner.
    • intrinsicContentSize = override it so Auto Layout knows the view's natural size when nothing else pins it.
    • invalidateIntrinsicContentSize() = call it whenever content changes the natural size, so the stale value gets recomputed.
    • UIView vs child UIViewController = use a plain view for visuals+local interaction; promote to a child VC only when you need lifecycle or VC-only APIs.
