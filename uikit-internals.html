    UIKit Internals — Overview

    SwiftUI is the future, but it is a thin declarative skin over machinery that is still pure UIKit and Core Animation underneath. Every ScrollView, every navigation push, every gesture you write in SwiftUI ultimately becomes a UIScrollView, a UINavigationController transition, or a UIGestureRecognizer. When an interaction misbehaves — a scroll that fights your gesture, a cell that recycles wrong, a hit-test that misses — the answer is almost always one layer down, in UIKit.

    This course is the substrate. It explains how UIKit actually works so that the fluid interactions you build on top behave predictably.

    The mental model

    UIKit is built from three intertwined systems:

    The view hierarchy decides what is drawn and where. The responder chain decides who handles events. The run loop decides when any of it happens.

    Master those three and almost every UIKit mystery dissolves.

    View Controller Lifecycle

    A UIViewController is a coordinator between a chunk of screen (its view) and the rest of your app. Its lifecycle methods fire in a precise order, and the single most common UIKit bug is doing the right work in the wrong method.

    The order of events

    init(coder:) / init(nibName:bundle:)   // object created, view NOT loaded yet
loadView()                              // creates self.view (rarely overridden)
viewDidLoad()                           // view exists; runs ONCE
viewWillAppear(_:)                      // about to become visible; runs EVERY time
viewWillLayoutSubviews()                // before layout pass
viewDidLayoutSubviews()                 // after layout — frames are now valid
viewDidAppear(_:)                       // fully on screen; animations safe here
viewWillDisappear(_:) / viewDidDisappear(_:)

    The two distinctions that matter most:

    • viewDidLoad runs once; viewWillAppear runs every time the view appears. Set up subviews and one-time configuration in viewDidLoad. Refresh data that may have changed (e.g. after returning from a pushed screen) in viewWillAppear.
    • Frames are not valid until viewDidLayoutSubviews. In viewDidLoad, view.bounds is often still the size from the nib/storyboard, not the real device size. Never compute positions from bounds in viewDidLoad.

    Why "don't read frames in viewDidLoad" matters

    override func viewDidLoad() {
    super.viewDidLoad()
    // WRONG: bounds may be 0,0,0,0 or a placeholder size
    gradient.frame = view.bounds
}

override func viewDidLayoutSubviews() {
    super.viewDidLayoutSubviews()
    // RIGHT: bounds now reflects the actual laid-out size
    gradient.frame = view.bounds
}

    viewDidLayoutSubviews can fire many times (rotation, keyboard, trait changes), so keep it cheap and idempotent — assign frames, don't allocate.

    Appearance is not loading

    A controller's view can be loaded (in memory) without being visible. isViewLoaded tells you the first; viewIfLoaded lets you touch the view without forcing it to load. Accessing self.view triggers loadView immediately — a subtle cause of "why did my view load so early?"

    Containment

    Custom container controllers (carousels, custom tab bars) must keep the parent/child relationship correct or child lifecycle methods won't fire:

    addChild(child)
view.addSubview(child.view)
child.view.frame = containerFrame
child.didMove(toParent: self)
// removal mirrors this: willMove(toParent: nil); removeFromSuperview; removeFromParent()

    Skipping these calls is why a child's viewWillAppear or rotation callbacks silently never run.

    The Responder Chain

    Every interactive object in UIKit — views, view controllers, the app itself — is a UIResponder. Events (touches, presses, motion, remote-control) travel along a chain of responders until something handles them. Understanding the chain explains hit-testing, becomeFirstResponder, target/action with nil, and the keyboard.

    Two phases: find, then bubble

    Phase 1 — hit-testing (top down). When a touch lands, UIKit walks the view hierarchy from the window downward to find the deepest view that contains the point and is eligible:

    hitTest(_:with:) → recursively calls pointInside(_:with:) on subviews

    A view is skipped if isHidden, alpha < 0.01, or isUserInteractionEnabled == false. This is why a button "doesn't work" when an invisible overlay sits on top with interaction enabled, or why a subview drawn outside its parent's bounds can't be tapped (clipsToBounds doesn't matter — hit-testing does).

    Phase 2 — the responder chain (bottom up). Once the hit view is found, if it doesn't handle the event it passes it to its next responder:

    view → superview → … → view controller → window → UIApplication → AppDelegate

    The chain in practice

    // A view's next responder is usually its superview;
// the top view's next responder is its view controller.
override var next: UIResponder? { ... }  // UIKit wires this for you

    target: nil actions ride this chain. This is the trick behind UIMenuController, UIKeyCommand, and sendAction:

    // Sends up the chain until SOMEONE implements save(_:)
UIApplication.shared.sendAction(#selector(MyResponder.save(_:)), to: nil, from: self, for: nil)

    Any responder that implements save(_:) handles it. That's how the system "find" command or copy/paste reaches whatever is appropriate without hard wiring.

    First responder

    The first responder is the object that receives keyboard and text input. Calling becomeFirstResponder() on a text field is what shows the keyboard; resignFirstResponder() dismisses it. canBecomeFirstResponder gates it.

    textField.becomeFirstResponder()   // show keyboard, focus this field
view.endEditing(true)              // resign whoever is first responder

    Custom views can become first responder too — that's how you build a view that accepts key commands or shows an input accessory.

    Why this matters for fluid UI

    Hit-testing is where gesture conflicts begin. If a scroll view eats a touch your custom control wanted, you override hitTest or point(inside:) to expand/shrink the touch target, or use UIGestureRecognizerDelegate (next-level control, see Interaction Math for the geometry).

    UIScrollView Mechanics

    UIScrollView is the most important view in UIKit. UITableView, UICollectionView, UITextView, and SwiftUI's ScrollView are all built on it. Scroll-linked animations — parallax, sticky headers, the stretchy hero image, the wavy carousel — are all just functions of contentOffset.

    The core geometry

    contentSize    – the size of the scrollable content (bigger than the bounds)
contentOffset  – how far scrolled: the top-left of the visible window
contentInset   – padding around the content (safe areas, pull-to-refresh)
bounds.size    – the visible viewport

    A scroll view doesn't move its content. It moves its own bounds.origin — which is contentOffset. Subviews are drawn relative to bounds, so changing the origin slides everything. This is the same bounds-origin trick from Layer Geometry.

    contentOffset drives effects

    The key realization: a scroll effect is f(contentOffset), computed every frame the user scrolls — not an animation. This is category-1 from Who Drives Time.

    func scrollViewDidScroll(_ sv: UIScrollView) {
    let y = sv.contentOffset.y
    // Stretchy header: when pulled past the top (negative offset), grow the image.
    if y < 0 {
        let scale = 1 + (-y / header.bounds.height)
        header.transform = CGAffineTransform(scaleX: scale, y: scale)
    }
    // Parallax: move a background slower than the scroll.
    background.transform = CGAffineTransform(translationX: 0, y: y * 0.5)
}

    scrollViewDidScroll fires on every offset change — keep it cheap (no allocations, no layout).

    The delegate timeline of a swipe

    scrollViewWillBeginDragging
scrollViewDidScroll            // repeatedly, while finger moves
scrollViewWillEndDragging(_:withVelocity:targetContentOffset:)   // finger lifts
scrollViewDidEndDragging(_:willDecelerate:)
scrollViewDidScroll            // repeatedly, during deceleration
scrollViewDidEndDecelerating

    scrollViewWillEndDragging is the powerful one: you receive the velocity and a mutable targetContentOffset pointer. Rewrite that pointer to implement custom paging or snap-to-item:

    func scrollViewWillEndDragging(_ sv: UIScrollView, withVelocity v: CGPoint,
                               targetContentOffset t: UnsafeMutablePointer<CGPoint>) {
    let page = (t.pointee.x / itemWidth).rounded()
    t.pointee.x = page * itemWidth   // snap to the nearest card
}

    Paging, insets, and the safe area

    isPagingEnabled snaps in viewport-sized steps. For custom card widths, leave it off and snap via targetContentOffset above. contentInsetAdjustmentBehavior controls whether the system adds insets for the nav bar / safe area — a frequent source of "my content starts 100pt too low."

    Compositional Layout

    UICollectionViewCompositionalLayout (iOS 13+) replaced the pain of custom UICollectionViewLayout subclasses for 90% of cases. It is built from a strict, composable hierarchy — once you internalize it, almost any grid, list, carousel, or magazine layout becomes a few lines.

    The hierarchy: Item → Group → Section

    An item is one cell. A group arranges items along one axis. A section stacks groups. A layout holds sections.

    // Item: half the group's width, full height
let item = NSCollectionLayoutItem(layoutSize: .init(
    widthDimension: .fractionalWidth(0.5),
    heightDimension: .fractionalHeight(1.0)))
item.contentInsets = .init(top: 4, leading: 4, bottom: 4, trailing: 4)

// Group: full width, fixed height, lays items horizontally
let group = NSCollectionLayoutGroup.horizontal(layoutSize: .init(
    widthDimension: .fractionalWidth(1.0),
    heightDimension: .absolute(180)),
    subitems: [item])     // → two items per row

let section = NSCollectionLayoutSection(group: group)
let layout = UICollectionViewCompositionalLayout(section: section)

    Fractional sizing is the superpower

    Dimensions come in three flavors:

    • .fractionalWidth(0.5) / .fractionalHeight(1.0) — relative to the container (group or section).
    • .absolute(180) — fixed points.
    • .estimated(120) — a starting guess that self-sizes to Auto Layout content (great for text).

    Because items size fractionally to their group, the same layout reflows correctly across screen sizes and orientations with no math on your part.

    Per-section layouts

    The real power: each section can have a completely different layout via the section provider, so a single collection view can mix a horizontal carousel, a grid, and a list:

    let layout = UICollectionViewCompositionalLayout { sectionIndex, env in
    switch sectionIndex {
    case 0: return Self.carouselSection()   // orthogonal scrolling
    default: return Self.gridSection()
    }
}

    Orthogonal scrolling (carousels for free)

    Set the section's orthogonalScrollingBehavior and the section scrolls horizontally inside a vertical collection view — the App Store's shelves, with no nested scroll views:

    section.orthogonalScrollingBehavior = .groupPagingCentered

    Supplementary items

    Headers, footers, and badges are NSCollectionLayoutBoundarySupplementaryItem (pinned headers via pinToVisibleBounds = true) and NSCollectionLayoutSupplementaryItem (badges anchored to an item corner).

    Try it

    Adjust items-per-group, group count, spacing, and axis below to see how fractional sizing reflows the section.

    Diffable Data Sources

    The classic UICollectionViewDataSource / UITableViewDataSource API made you responsible for keeping your model and the view in sync via performBatchUpdates. Get the counts wrong and you crash: "invalid number of items." Diffable data sources (iOS 13+) flip the model: you describe the desired state as a snapshot, and UIKit computes the diff and animates it.

    Snapshots describe state, not changes

    enum Section { case main }

let dataSource = UICollectionViewDiffableDataSource<Section, Item.ID>(
    collectionView: cv) { cv, indexPath, id in
        let cell = cv.dequeueConfiguredReusableCell(using: reg, for: indexPath, item: id)
        return cell
    }

func apply(_ items: [Item], animate: Bool = true) {
    var snapshot = NSDiffableDataSourceSnapshot<Section, Item.ID>()
    snapshot.appendSections([.main])
    snapshot.appendItems(items.map(\.id))
    dataSource.apply(snapshot, animatingDifferences: animate)
}

    You never call insertItems / deleteItems. You hand over the new truth; UIKit figures out what moved, inserted, or deleted and animates each correctly.

    Identifiers must be Hashable and stable

    The diff is computed on identifiers, not objects. Use a stable ID (not array index), and make sure equality is meaningful:

    Store item identifiers in the snapshot, keep the full objects in your store, and look them up in the cell provider. This avoids re-rendering everything when one field changes.

    If two different items hash equal, the diff misbehaves (cells vanish or duplicate) — the single most common diffable bug.

    Cell registration replaces dequeue-by-string

    let reg = UICollectionView.CellRegistration<UICollectionViewListCell, Item.ID> { cell, _, id in
    var config = cell.defaultContentConfiguration()
    config.text = store[id]?.title
    cell.contentConfiguration = config
}

    No more reuse-identifier strings, no force casts. UIContentConfiguration is the modern, value-type way to fill a cell — the same configuration objects work for table and collection list cells.

    Reloading vs reconfiguring

    reconfigureItems (iOS 15+) updates a visible cell in place without replacing it — cheaper and flicker-free for content changes where identity is unchanged. Use it instead of reloadItems when only the data inside a cell changed.

    Why it matters

    Diffable data sources eliminate an entire class of crashes and give you correct, free animations — which is exactly the "describe the state, let the system interpolate" philosophy you see in SwiftUI and in the dependency graph.

    UIKit ↔ SwiftUI Interop

    You rarely rewrite an app wholesale. Real apps are hybrids: a SwiftUI screen hosting a MKMapView, or a UIKit app embedding a new SwiftUI feature. Three bridges connect the two worlds, and knowing which to reach for keeps the boundary clean.

    SwiftUI hosting UIKit: UIViewRepresentable

    Wrap any UIView so SwiftUI can place it:

    struct BlurView: UIViewRepresentable {
    func makeUIView(context: Context) -> UIVisualEffectView {
        UIVisualEffectView(effect: UIBlurEffect(style: .systemMaterial))
    }
    func updateUIView(_ view: UIVisualEffectView, context: Context) {
        // called whenever SwiftUI state this view depends on changes
    }
}
    • makeUIView runs once to create the view.
    • updateUIView runs every time relevant SwiftUI state changes — push new values into UIKit here.
    • For UIViewController, use UIViewControllerRepresentable (same shape: makeUIViewController / updateUIViewController).

    Talking back: the Coordinator

    UIKit communicates via delegates and target/action, which are reference-based. The Coordinator is the bridge object that adopts those delegates and forwards into SwiftUI:

    func makeCoordinator() -> Coordinator { Coordinator(self) }

class Coordinator: NSObject, UIScrollViewDelegate {
    let parent: MyRepresentable
    init(_ parent: MyRepresentable) { self.parent = parent }
    func scrollViewDidScroll(_ sv: UIScrollView) {
        parent.offset = sv.contentOffset.y   // push UIKit event → SwiftUI binding
    }
}

    UIKit hosting SwiftUI: UIHostingController

    The reverse bridge. UIHostingController is a UIViewController whose body is a SwiftUI view — drop it into a navigation stack, a container, or as a child:

    let host = UIHostingController(rootView: ProfileView(user: user))
navigationController?.pushViewController(host, animated: true)

    For embedding SwiftUI inside a UIKit cell or view, add host.view as a subview and wire up containment (see 01-view-controller-lifecycle). On iOS 16+, UIHostingConfiguration lets a collection/table cell be SwiftUI directly — the cleanest hybrid path.

    The sizing gotcha

    The classic friction is sizing: a UIHostingController doesn't always report its SwiftUI content's intrinsic size to UIKit Auto Layout. Set host.sizingOptions = .intrinsicContentSize (iOS 16+) or pin constraints explicitly. Conversely, a UIViewRepresentable should implement sizeThatFits (iOS 16+) so SwiftUI's layout system can measure it.

    When to drop down

    Reach for UIKit from SwiftUI when you need: precise scroll/gesture control SwiftUI doesn't expose, a mature UIKit-only view (MKMapView, PHPicker, AVPlayerViewController), or text editing power (UITextView/TextKit). Everything else stays SwiftUI.

    07 — Custom Gesture Recognizers

    A gesture recognizer is a tiny state machine that sits between raw touches and your code, quietly asking one question over and over: "is this MY gesture yet?" It watches fingers land, move, and lift, and at each step it decides whether what it's seeing still could be — or definitely is, or definitely isn't — the gesture it's looking for.

    Think of a bouncer reading a secret handshake. Each move either keeps the handshake alive, completes it, or blows it. The recognizer does the same with touches: it starts hopeful (.possible), commits when the pattern is unmistakable, drives updates as the gesture continues, and resolves to success or failure. UIKit's built-in recognizers (UITapGestureRecognizer, UIPanGestureRecognizer, and friends) are just prebuilt versions of this machine. When none of them fits, you build your own — which is nothing more exotic than a UIGestureRecognizer subclass that drives its own state.

    The states and their legal transitions

    The whole thing hinges on the state property, and its transitions aren't freeform — UIKit only accepts certain moves.

    • Continuous gestures (pan, pinch, rotate, your custom drags) walk: .possible → .began → .changed → .changed → … → .ended. Your action method fires on .began, on every .changed, and once on .ended.
    • Discrete gestures (tap, and tap-like custom gestures) jump straight: .possible → .recognized. The action fires once. (.recognized and .ended share the same raw value; "ended" is the continuous name, "recognized" the discrete one.)
    • Bailing out happens two ways: set .failed when the touches prove this can't be your gesture (wrong number of fingers, moved too far, too slow), or .cancelled when the system yanks the gesture away (e.g. an incoming call).
    • After .ended, .failed, .cancelled, or .recognized, UIKit calls reset() and the recognizer returns to .possible, ready for the next touch sequence.

    The mental model: you never ask to recognize — you assert state, and UIKit enforces that your assertions are legal and drives your target/action accordingly.

    Turning up the heat 1: driving state from touches

    To build one, subclass UIGestureRecognizer and override the touch callbacks. The catch: those overrides live in a separate header, so you must import the subclass module.

    import UIKit
import UIKit.UIGestureRecognizerSubclass   // exposes settable `state` + touch overrides

/// A gesture that recognizes a firm downward swipe of a single finger.
final class DownSwipeGestureRecognizer: UIGestureRecognizer {
    private var startPoint: CGPoint = .zero
    private let threshold: CGFloat = 40

    override func touchesBegan(_ touches: Set<UITouch>, with event: UIEvent) {
        super.touchesBegan(touches, with: event)
        guard touches.count == 1, let touch = touches.first else {
            state = .failed                 // wrong finger count → not our gesture
            return
        }
        startPoint = touch.location(in: view)
        // stay .possible; we don't commit until we see real downward motion
    }

    override func touchesMoved(_ touches: Set<UITouch>, with event: UIEvent) {
        super.touchesMoved(touches, with: event)
        guard let touch = touches.first else { return }
        let dy = touch.location(in: view).y - startPoint.y
        let dx = abs(touch.location(in: view).x - startPoint.x)

        if dx > dy {                        // more sideways than down
            state = .failed
        } else if dy > threshold, state == .possible {
            state = .began                  // commit
        } else if state == .began || state == .changed {
            state = .changed                // keep updating
        }
    }

    override func touchesEnded(_ touches: Set<UITouch>, with event: UIEvent) {
        super.touchesEnded(touches, with: event)
        state = (state == .began || state == .changed) ? .ended : .failed
    }

    override func touchesCancelled(_ touches: Set<UITouch>, with event: UIEvent) {
        super.touchesCancelled(touches, with: event)
        state = .cancelled
    }

    override func reset() {
        super.reset()
        startPoint = .zero                  // wipe per-gesture scratch state
    }
}

    Read it as narration of the state machine: touchesBegan sizes up the touch and either fails fast or waits; touchesMoved commits with .began, then keeps feeding .changed; touchesEnded resolves to .ended or .failed; reset() clears scratch state for next time. Setting state is what fires your target/action — you don't call the action yourself.

    Turning up the heat 2: delegate negotiation and competition

    A view rarely has just one recognizer. A cell might have a tap, a long-press, and be inside a scroll view — three machines watching the same touches. By default only one wins, and the UIGestureRecognizerDelegate is where you referee.

    • gestureRecognizer(_:shouldRecognizeSimultaneouslyWith:) — return true to let two recognizers both fire from the same touches (e.g. pinch + rotate together).
    • gestureRecognizer(_:shouldRequireFailureOf:) — dynamically say "I should wait for that other one to fail before I fire."
    • gestureRecognizer(_:shouldBeRequiredToFailBy:) — the mirror: "that other one should wait for me."
    • require(toFail:) — the static, direct version, set up once at construction. The classic case: a single-tap must wait for the double-tap to fail, so a double-tap doesn't also trigger the single.
    let singleTap = UITapGestureRecognizer(target: self, action: #selector(handleSingle))
let doubleTap = UITapGestureRecognizer(target: self, action: #selector(handleDouble))
doubleTap.numberOfTapsRequired = 2

singleTap.require(toFail: doubleTap)   // single fires only once double has failed
view.addGestureRecognizer(singleTap)
view.addGestureRecognizer(doubleTap)

    The trade-off to know: require(toFail:) adds latency. The single tap now can't fire until the double-tap's window elapses and it fails — a perceptible delay. Use it only where the ambiguity is real.

    Turning up the heat 3: competing with a scroll view

    The hardest arena is a custom pan living inside a UIScrollView, because the scroll view's own panGestureRecognizer is greedy and already watching every touch. You have three levers, roughly from most cooperative to most controlling:

    1. Recognize simultaneously. In your delegate, return true from shouldRecognizeSimultaneouslyWith when the other recognizer is the scroll view's pan. Both act — good when your gesture is genuinely orthogonal (e.g. a horizontal swipe on a vertically scrolling list).
    2. Require the scroll's pan to fail. Call yourPan.require(toFail: scrollView.panGestureRecognizer) (or wire it via the delegate). Now scrolling wins ties, and your gesture only takes over when the scroll view decides it isn't scrolling. Safer, but yields to scroll.
    3. Directional locking in the delegate. Inspect the initial translation/velocity in shouldBegin or shouldRecognizeSimultaneouslyWith and allow your recognizer only when the movement is in your axis — letting vertical drags scroll and horizontal drags hit your gesture.

    Two more knobs matter on the scroll view side: delaysTouchesBegan (hold touchesBegan briefly so the scroll view can decide first — usually leave it off, it feels laggy) and cancelsTouchesInView (when a recognizer fires, does it cancel the touches to the underlying view — leave true unless the view also needs the raw touches).

    A note on the "hand-rolled recognizer" apps

    You'll hear that apps like Telegram ship rich custom recognizers — a "ContextGesture" that combines a long-press with a pan so you can press-and-drag into a context menu in one fluid motion. That sounds like insider magic, but there's nothing you can't see here: it's a UIGestureRecognizer subclass driving state from touchesBegan/Moved/Ended, exactly like the example above, just with a richer decision tree (start a long-press timer, and if the finger moves before it fires, transition into pan-tracking). You don't need their source to build the same thing — the state machine is the whole trick, and you already have it.

    The foundation

    • gesture recognizer = a state machine that watches raw touches and decides whether they form its gesture, firing your target/action via state.
    • continuous vs discrete = continuous walks .possible → .began → .changed… → .ended; discrete jumps .possible → .recognized.
    • .failed / .cancelled / reset() = fail when touches can't be your gesture, cancelled when the system pulls it, then reset() returns to .possible.
    • UIKit.UIGestureRecognizerSubclass = the import that makes state settable and exposes the touchesBegan/Moved/Ended/Cancelled overrides.
    • driving state = you assert state in the touch callbacks; setting it (not calling the action) is what fires your handler.
    • delegate negotiation = shouldRecognizeSimultaneouslyWith, shouldRequireFailureOf, shouldBeRequiredToFailBy referee competing recognizers.
    • require(toFail:) = make one recognizer wait for another to fail (single-tap waits on double-tap) — at the cost of latency.
    • scroll-view competition = allow simultaneous recognition, require the scroll's pan to fail, or directional-lock in the delegate; tune delaysTouchesBegan / cancelsTouchesInView.

    08 — Building a Recycling List on UIScrollView

    Start here — the plain idea

    Open any chat app and scroll through ten thousand messages. It feels like all ten thousand rows exist at once, stacked in a tall column you glide along. They don't. At any instant only a screenful — maybe fifteen views — are actually alive. As a row slides off the top, UITableView quietly grabs it, wipes it clean, refills it with the data for a row about to appear at the bottom, and slots it back in. It is a stage crew of a dozen actors playing a cast of thousands, sprinting behind the curtain to change costumes. That trick is called cell recycling, and it is the single reason a list of ten thousand rows costs the same memory as a list of fifteen.

    UITableView and UICollectionView do this for you. But their recycling machine is welded to their layout, their data source, and their update animations. The moment you want something they don't offer — messages that grow upward from the bottom, a layout that reflows mid-scroll, an insertion above the viewport that must not jolt the content — you are fighting the framework instead of using it. This is exactly why serious chat and feed apps (Telegram's list is the famous example) throw out UITableView and hand-roll the whole thing on a bare UIScrollView.

    This lesson builds that machine from scratch. We start with the windowing math — figuring out which rows are visible from nothing but contentOffset and bounds — then add a reuse pool, then custom snapping, and finally the hard part that makes chat apps possible: inserting content above the visible area without the screen moving a single pixel. By the end you will understand not just how to build it, but why the apps that outgrow UITableView reach for this.

    The windowing math

    A UIScrollView gives you two numbers every frame: contentOffset (how far you've scrolled) and bounds.size (the size of the viewport). Everything else is arithmetic. If your rows have known heights, you keep a running array of y positions and binary-search for the first and last index that intersect the visible rectangle.

    struct RowLayout {
    var frames: [CGRect]          // absolute frame of every item in content space
    var contentHeight: CGFloat

    // First..last index whose frame intersects the visible window.
    func visibleRange(in rect: CGRect) -> Range<Int> {
        guard !frames.isEmpty else { return 0..<0 }
        // Binary search: first row whose maxY is below the window top.
        let lower = frames.partitioningIndex { $0.maxY > rect.minY }
        let upper = frames.partitioningIndex { $0.minY >= rect.maxY }
        return lower..<upper
    }
}

// Swift 6 std-lib helper; equivalent to a hand-rolled binary search.
extension Array {
    func partitioningIndex(where belongsInSecondPartition: (Element) -> Bool) -> Int {
        var low = 0, high = count
        while low < high {
            let mid = low + (high - low) / 2
            if belongsInSecondPartition(self[mid]) { high = mid } else { low = mid + 1 }
        }
        return low
    }
}

    The window is just CGRect(origin: contentOffset, size: bounds.size). Every time the offset changes you recompute the range, diff it against the range you currently have on screen, remove the views that fell out, and add the views that came in. You observe offset changes through the scroll view's delegate:

    final class RecyclingList: UIView, UIScrollViewDelegate {
    private let scrollView = UIScrollView()
    private var layout = RowLayout(frames: [], contentHeight: 0)
    private var visibleViews: [Int: UIView] = [:]   // index → live view

    func scrollViewDidScroll(_ sv: UIScrollView) {
        updateVisibleViews()
    }

    private func updateVisibleViews() {
        let window = CGRect(origin: scrollView.contentOffset, size: scrollView.bounds.size)
        let wanted = layout.visibleRange(in: window)

        // 1. Recycle anything no longer in the window.
        for (index, view) in visibleViews where !wanted.contains(index) {
            enqueue(view)
            visibleViews[index] = nil
        }
        // 2. Materialize anything newly in the window.
        for index in wanted where visibleViews[index] == nil {
            let view = dequeueOrMake(for: index)
            view.frame = layout.frames[index]
            configure(view, at: index)
            scrollView.addSubview(view)
            visibleViews[index] = view
        }
    }
}

    Keep scrollViewDidScroll allocation-free. It fires many times per frame at 120 Hz on ProMotion; a single heap allocation or Auto Layout pass in that path is how you drop frames. The diff above touches only the handful of indices that changed, never the whole list.

    A manual reuse pool

    The recycled views have to go somewhere when they leave the screen so the next arrival can grab one instead of allocating. That somewhere is a pool keyed by view type — because a chat has text bubbles, image bubbles, date separators, each a different class you cannot swap for another. You mimic dequeueReusableCell with your own enqueue/dequeue pair, and you call your own prepareForReuse to scrub stale state.

    protocol Recyclable: UIView {
    static var reuseKey: String { get }
    func prepareForReuse()
}

final class ReusePool {
    private var pools: [String: [any Recyclable]] = [:]

    func enqueue(_ view: any Recyclable) {
        view.removeFromSuperview()
        view.prepareForReuse()               // cancel image loads, clear text, reset transform
        pools[type(of: view).reuseKey, default: []].append(view)
    }

    func dequeue<T: Recyclable>(_ type: T.Type) -> T? {
        guard var bucket = pools[type.reuseKey], let view = bucket.popLast() else { return nil }
        pools[type.reuseKey] = bucket
        return view as? T
    }
}

    The discipline that matters is prepareForReuse. A recycled bubble still holds the previous message's text, its in-flight image download, and possibly a running animation. If you forget to cancel the download, a fast scroll leaves you with the wrong photo flashing into the wrong bubble — the classic recycling bug. Cancel async work and reset any mutable visual state there, never at dequeue time, so the view sits inert in the pool.

    Custom snapping with targetContentOffset

    When the finger lifts, the scroll view is about to fling into a decelerating glide toward some resting offset. scrollViewWillEndDragging(_:withVelocity:targetContentOffset:) hands you that resting offset as a mutable pointer — rewrite it and the deceleration curve retargets to your value. This is how you snap to an item boundary or build paging that the built-in isPagingEnabled (which only pages in full-viewport steps) can't express.

    func scrollViewWillEndDragging(
    _ sv: UIScrollView,
    withVelocity velocity: CGPoint,
    targetContentOffset target: UnsafeMutablePointer<CGPoint>
) {
    let proposed = target.pointee.y
    // Find the item whose top the projected offset lands nearest.
    let idx = layout.frames.partitioningIndex { $0.minY > proposed }
    let candidate = max(0, idx - 1)
    // Bias toward the next item when flinging hard, so a flick always advances.
    let snapIndex = (velocity.y > 0.3 && candidate + 1 < layout.frames.count)
        ? candidate + 1 : candidate
    target.pointee.y = layout.frames[snapIndex].minY
}

    The rewritten target must be reachable — clamp it into 0...(contentSize.height - bounds.height + adjustedContentInset) or the scroll view will snap and then rubber-band back, which reads as a stutter. Respect the sign of velocity so a deliberate flick is never overruled into snapping backward.

    Bidirectional insertion without jumps

    Here is the problem that forces chat apps off UITableView. You are reading history halfway up a conversation. A network fetch delivers fifty older messages that belong above everything on screen. If you naively insert them, every existing row's y shifts down by the inserted height, and because contentOffset stays fixed, the content lurches — the message you were reading rockets off the bottom of the screen. Unacceptable in a chat.

    The fix is a same-pass compensation. In one layout transaction you (1) grow contentSize by the inserted height, (2) shift every existing frame down by that height, and (3) add the same height to contentOffset.y. Because the offset moves exactly as much as the content grew, the visible rows stay pinned to the same screen pixels. Nothing appears to move; new content simply now exists above.

    func prepend(_ newItems: [Item]) {
    let insertedHeight = totalHeight(of: newItems)

    // Shift existing layout down and splice the new frames on top.
    let shifted = layout.frames.map { $0.offsetBy(dx: 0, dy: insertedHeight) }
    let newFrames = buildFrames(for: newItems, startingAt: 0)      // occupy [0, insertedHeight)
    layout.frames = newFrames + shifted
    layout.contentHeight += insertedHeight

    // Re-key the currently-live views to their new indices.
    visibleViews = Dictionary(uniqueKeysWithValues:
        visibleViews.map { (idx, view) in (idx + newItems.count, view) })

    // The atomic part: grow content and bump offset in the SAME pass.
    UIView.performWithoutAnimation {
        scrollView.contentSize.height = layout.contentHeight
        scrollView.contentOffset.y += insertedHeight   // cancels the visual shift exactly
        for (idx, view) in visibleViews { view.frame = layout.frames[idx] }
    }
    updateVisibleViews()
}

    The performWithoutAnimation wrapper matters: if contentSize and contentOffset land in separate runloop turns, the scroll view briefly clamps the old offset against the new size and you get a one-frame flash. Set them together.

    A more robust variant tracks a stable anchor instead of doing raw arithmetic. Before the mutation, pick a visible item (say the topmost fully-visible one) and record the delta between its frame's minY and the current contentOffset.y. After you rebuild the layout, find that same item's new frame and set contentOffset.y = newFrame.minY - savedDelta. This survives not just prepends but any reflow — a height change from an image finishing decode, a font size bump — because you are re-anchoring to content rather than assuming you know the exact inserted height. The same technique applies to top contentInset changes (a keyboard appearing, a growing compose bar): compensate the offset by the inset delta so the anchored message holds its position.

    struct Anchor { let itemID: Item.ID; let offsetFromTop: CGFloat }

func captureAnchor() -> Anchor? {
    let top = scrollView.contentOffset.y + scrollView.adjustedContentInset.top
    guard let (idx, _) = visibleViews.min(by: { abs($0.value.frame.minY - top) < abs($1.value.frame.minY - top) })
    else { return nil }
    return Anchor(itemID: items[idx].id, offsetFromTop: layout.frames[idx].minY - top)
}

func restore(_ anchor: Anchor) {
    guard let idx = items.firstIndex(where: { $0.id == anchor.itemID }) else { return }
    let newTop = layout.frames[idx].minY - anchor.offsetFromTop
    scrollView.contentOffset.y = newTop - scrollView.adjustedContentInset.top
}

    This is precisely the layer of control UITableView won't give you: it owns the offset during its own batch updates, and its "maintain position on prepend" behavior is heuristic, not guaranteed. Owning the scroll view yourself means the anchor is your code, exact and debuggable — which is why apps whose entire product is a scrolling conversation (Telegram is the canonical example, driving its own list from contentOffset rather than UITableView) invest in building this. They hand-roll windowing, reuse, and anchor-based compensation for total control over interruptibility and jump-free updates; the cost is that you now own every edge case UITableView had already solved.

    The foundation

    • Windowing = deriving the visible index range each frame from contentOffset + bounds, then adding/removing only the views that crossed the boundary.
    • Reuse pool = a per-type dictionary of dormant views; dequeue reuses one if present, else you allocate, so live-view count stays bounded by a screenful.
    • prepareForReuse = the scrub step that cancels async work and resets visual state when a view returns to the pool, preventing stale content flashing into recycled views.
    • targetContentOffset = the mutable resting-offset pointer from scrollViewWillEndDragging; rewrite it to retarget deceleration for custom snapping or paging.
    • Prepend compensation = growing contentSize and bumping contentOffset by the same inserted height in one non-animated pass so on-screen content never visibly moves.
    • Stable anchor = recording a content item's position before a mutation and restoring contentOffset relative to it afterward, surviving any reflow, not just fixed-height inserts.
    • adjustedContentInset = the system-plus-your inset the scroll view actually uses; anchor math must account for it or content lands offset by the safe area / keyboard height.
    • Hand-rolled list = trading UITableView's solved edge cases for full ownership of layout, reuse, and offset — the path apps like chats and feeds take when the framework's coupling gets in the way.

    09 — Custom Container View Controllers & Interactive Transitions

    Start here — the plain idea

    UINavigationController feels like a special, blessed piece of the system — the thing that gives you the back button, the swipe-to-go-back, the sliding push animation. It isn't special. It is an ordinary view controller that happens to keep an array of other view controllers, shows one of their views at a time, and animates the swap when you push or pop. Every capability it has is built from public API you can call yourself. A container view controller is just a manager: it holds children, mounts their views, and choreographs the move from one to the next.

    Think of it like a theater stage. The stage (your container) has one spotlight. Behind the curtain wait several performers (child view controllers), each with their own script and props (their own lifecycle, their own views). The stage director decides who is lit, and when the scene changes, how the outgoing performer exits and the incoming one enters — a hard cut, a slow fade, or a slide where the audience can grab the curtain and drag the change halfway before letting it snap shut. That last one — the audience driving the scene change with their own hand — is an interactive transition, and it is the whole reason apps that care about feel build their own containers.

    This lesson builds a container from the containment contract up, then a hand-rolled navigation stack, then the part that matters most: transitions a pan gesture drives frame by frame, that you can pause, reverse, and hand off to a spring. We finish by contrasting UIKit's standard transitioning API with the fully hand-rolled approach big apps use — and exactly what each buys you.

    The containment contract

    Adding a child view controller is not "add its view as a subview." UIKit tracks parent-child relationships so that lifecycle callbacks, trait propagation, safe-area insets, and rotation all flow correctly to the child. You must perform a precise handshake, and it is asymmetric: a specific order to attach, and the reverse to detach.

    // Attach a child.
func addChild(_ child: UIViewController, to container: UIView) {
    addChild(child)                              // 1. establishes parent link; fires willMove(toParent:) for you
    container.addSubview(child.view)             // 2. mount the view
    child.view.frame = container.bounds
    child.view.autoresizingMask = [.flexibleWidth, .flexibleHeight]
    child.didMove(toParent: self)                // 3. YOU must call this — signals containment complete
}

// Detach a child — exact reverse.
func removeChild(_ child: UIViewController) {
    child.willMove(toParent: nil)                // 1. YOU must call this — signals imminent removal
    child.view.removeFromSuperview()             // 2. unmount the view
    child.removeFromParent()                     // 3. tears down parent link; fires didMove(toParent: nil)
}

    The rule to memorize: addChild calls willMove(toParent:) for you, so you finish with didMove; removeFromParent calls didMove(toParent: nil) for you, so you begin with willMove. Get the order wrong and the child's viewWillAppear/viewDidAppear (see 01-view-controller-lifecycle) fire at the wrong time or not at all, and you get children whose viewDidDisappear never runs — a subtle leak. Prefer constraints over an autoresizing frame when the container reflows; the frame form above is fine for a full-bleed child.

    Building your own navigation stack

    With the contract in hand, a navigation controller is barely more than an array plus a push and a pop. The stack owns the children; showing a controller means mounting its view on top; hiding means detaching after the animation completes.

    final class MiniNavController: UIViewController {
    private(set) var stack: [UIViewController] = []

    func push(_ vc: UIViewController, animated: Bool) {
        let from = stack.last
        stack.append(vc)
        addChild(vc)
        vc.view.frame = view.bounds
        view.addSubview(vc.view)

        guard animated, let from else { vc.didMove(toParent: self); return }

        vc.view.transform = CGAffineTransform(translationX: view.bounds.width, y: 0)  // start offscreen right
        UIView.animate(withDuration: 0.35, delay: 0,
                       usingSpringWithDamping: 0.9, initialSpringVelocity: 0) {
            vc.view.transform = .identity
            from.view.transform = CGAffineTransform(translationX: -self.view.bounds.width * 0.3, y: 0)
        } completion: { _ in
            vc.didMove(toParent: self)     // containment completes AFTER the animation settles
        }
    }

    func pop(animated: Bool) {
        guard stack.count > 1 else { return }
        let outgoing = stack.removeLast()
        let incoming = stack.last!
        outgoing.willMove(toParent: nil)   // begin detach before animating out

        UIView.animate(withDuration: 0.35, delay: 0,
                       usingSpringWithDamping: 0.9, initialSpringVelocity: 0) {
            outgoing.view.transform = CGAffineTransform(translationX: self.view.bounds.width, y: 0)
            incoming.view.transform = .identity
        } completion: { _ in
            outgoing.view.removeFromSuperview()
            outgoing.removeFromParent()    // fires didMove(toParent: nil)
        }
    }
}

    Notice where the lifecycle calls sit relative to the animation. On push, didMove(toParent:) is deferred to the completion handler because containment isn't truly finished until the new controller is settled and interactive. On pop, willMove(toParent: nil) fires before the animation so the outgoing controller knows it is leaving while it slides away.

    Interactive, interruptible transitions

    A non-interactive animation is a closure that runs to completion. An interactive one is a function of progress: a pan recognizer emits a value from 0 to 1, and you set the animation to exactly that fraction complete. The tool that makes this possible is UIViewPropertyAnimator, which — unlike UIView.animate — lets you scrub its fractionComplete, pause, reverse direction, and then release it to finish on a spring.

    final class InteractivePop: NSObject {
    private var animator: UIViewPropertyAnimator?
    private weak var nav: MiniNavController?

    @objc func handlePan(_ gr: UIScreenEdgePanGestureRecognizer) {
        guard let view = gr.view else { return }
        let translation = gr.translation(in: view).x
        let progress = min(max(translation / view.bounds.width, 0), 1)

        switch gr.state {
        case .began:
            animator = buildPopAnimator()          // configures the from/to transforms
            animator?.pauseAnimation()             // hold at fraction 0, ready to scrub

        case .changed:
            animator?.fractionComplete = progress  // drive the frame directly off the finger

        case .ended, .cancelled:
            let velocity = gr.velocity(in: view).x
            // Decide the destination from position AND intent.
            let shouldFinish = progress > 0.5 || velocity > 800
            animator?.isReversed = !shouldFinish
            // Hand off to a spring: continue with a timing that carries the remaining distance.
            let remaining = shouldFinish ? (1 - progress) : progress
            let params = UISpringTimingParameters(dampingRatio: 0.85,
                                                  initialVelocity: CGVector(dx: velocity / view.bounds.width, dy: 0))
            animator?.continueAnimation(withTimingParameters: params, durationFactor: CGFloat(remaining))
        default:
            break
        }
    }
}

    Three things make this feel native. First, fractionComplete is set directly from the finger — no animation is "playing," the frame simply is wherever the touch is, so it tracks with zero lag. Second, the release decision blends position and velocity: past halfway or a hard flick commits, matching how the system's own edge-swipe behaves. Third, the handoff passes the finger's exit velocity into a UISpringTimingParameters so the spring picks up exactly the speed the finger had — no discontinuity between drag and settle. The interruptibility falls out for free: because the animator is paused and scrubbable, a second touch mid-flight can grab it and drag it back. This is where the spring math from springs becomes tangible — the release is a real spring solved from the current position and velocity, not a fixed-duration curve.

    Two roads: the standard API vs hand-rolling

    UIKit ships a formal transitioning API. You set a transitioningDelegate (or a UINavigationControllerDelegate), return a UIViewControllerAnimatedTransitioning object that performs the animation inside a supplied transitionContext, and for interactivity return a UIViewControllerInteractiveTransitioning — usually a UIPercentDrivenInteractiveTransition, which you feed update(_:), finish(), and cancel() as the gesture moves.

    final class SlideAnimator: NSObject, UIViewControllerAnimatedTransitioning {
    func transitionDuration(using ctx: UIViewControllerContextTransitioning?) -> TimeInterval { 0.35 }
    func animateTransition(using ctx: UIViewControllerContextTransitioning) {
        let container = ctx.containerView
        guard let to = ctx.view(forKey: .to) else { return }
        to.frame = ctx.finalFrame(for: ctx.viewController(forKey: .to)!)
        to.transform = CGAffineTransform(translationX: container.bounds.width, y: 0)
        container.addSubview(to)
        UIView.animate(withDuration: 0.35) { to.transform = .identity }
            completion: { ctx.completeTransition(!ctx.transitionWasCancelled) }
    }
}

    This is the right tool when you want your transition to plug into the system's navigation controller or modal presentation — you get the framework's plumbing (the container view, the correct lifecycle sequencing, adaptivity) for free, and you write only the animation. Its limit is that the system owns the timeline. UIPercentDrivenInteractiveTransition scrubs a CAAnimation's timeOffset, which is coarse: mid-flight interruption, retargeting to a different destination, or blending a second gesture into a running transition all fight the abstraction.

    The fully hand-rolled approach — the one apps like Telegram take — skips the transitioning API entirely. They keep their own array of children, run their own layout system, and drive the whole change with a UIViewPropertyAnimator or a raw display-link loop scrubbed directly by a pan, exactly as in the interactive section above. Nothing is delegated to the framework, so nothing has to be fought: the transition is interruptible at any instant, reversible, retargetable, and can be composed with the list-scrolling and layout systems the app already owns. The trade-off is real. The standard API is less code and stays correct as UIKit evolves (adaptivity, new presentation styles, accessibility); the hand-rolled path is more code and you re-implement lifecycle sequencing and edge cases yourself, but you get total, frame-exact control over feel and interruptibility. Choose the standard API when you are extending system navigation; hand-roll when the interaction is the product and the framework's ownership of the timeline is the thing standing in your way.

    The foundation

    • Containment contract = the ordered handshake (addChild → add view → didMove(toParent:), reversed as willMove(toParent: nil) → remove view → removeFromParent) that keeps a child's lifecycle, traits, and insets correct.
    • Custom navigation stack = an array of child VCs plus push/pop that mount/unmount views and animate the swap; a UINavigationController is exactly this and nothing more.
    • UIViewPropertyAnimator = the interruptible animator you can pause, set fractionComplete on, reverse, and continueAnimation(withTimingParameters:) — the engine of interactive transitions.
    • Progress-driven transition = mapping a pan's translation to a 0→1 fraction and setting the animator to it directly, so the change tracks the finger with no lag.
    • Velocity handoff = passing the gesture's exit velocity into UISpringTimingParameters so the settling spring continues at the finger's speed with no visible seam.
    • Standard transitioning API = UIViewControllerAnimatedTransitioning + UIViewControllerInteractiveTransitioning / UIPercentDrivenInteractiveTransition, which plug into system navigation but hand the timeline to the framework.
    • Hand-rolled transition = owning the children, layout, and animator yourself, bypassing the transitioning API for frame-exact interruptibility at the cost of re-implementing the framework's plumbing.
    • Commit decision = choosing finish vs cancel on release from both position (past halfway) and velocity (a hard flick), matching the system's own gesture behavior.

    10 — Layer Reparenting: Portal Views

    Start here — the plain idea

    Imagine a security desk with a wall of monitors. One monitor shows a live feed of the lobby camera. The lobby is still the lobby — nobody moved it, nobody photographed it — but its pixels now appear somewhere completely different, updating in real time. That live feed is exactly what a portal is for a view: a window into another view's rendered content, shown at a new location, staying live.

    You reach for this when one view's pixels need to appear somewhere else in the hierarchy without physically moving the original. Think of a tiny avatar inside a table view cell that appears to "fly up" and expand into a full-screen header during a push transition. The cell still owns that avatar. Detaching it, animating it, and re-inserting it is fiddly and error-prone — the cell might recycle, the layout might shift, the original might blink. A portal lets a second view mirror the avatar's live content while the real one stays exactly where it belongs.

    Contrast this with a snapshot, which is a photograph: a frozen copy of how the view looked at one instant. Snapshots are cheap, safe, and perfect when the source won't change during the animation. Portals are the live feed — more powerful, but with a catch we'll get to. Most of the time you want the photograph; occasionally you genuinely need the live feed, and knowing which is which is the whole skill here.

    The concept: mirror, don't move

    A portal mirrors a source layer's rendered content at another point in the tree. Three properties define it:

    • The source view is not reparented — it keeps its place, its constraints, its owner.
    • The content is not a static copy — it re-renders as the source changes.
    • The portal has its own frame, transform, and position in a different branch of the hierarchy, so it can be animated independently.

    The rendered output flows one way: source → portal. You animate the portal; the source is untouched.

    How Apple does it internally (private API — do not ship)

    Under the hood UIKit has a private class, _UIPortalView, backed by a CAPortalLayer. A CAPortalLayer holds a reference to a sourceLayer and draws that layer's tree wherever the portal layer sits. This is the machinery behind several system transitions, and third-party apps like Telegram have used it for cross-hierarchy morphs and glass-style live overlays.

    Conceptually it looks like this — shown only so you understand the mechanism:

    // PRIVATE API. This will get your app rejected. Illustration only.
// _UIPortalView is not declared in any public header.

let portalClass: AnyClass = NSClassFromString("_UIPortalView")!

// Instances are created via a source view; the initializer takes the
// view whose content should be mirrored.
let sel = NSSelectorFromString("initWithSourceView:")
let portal = (portalClass.alloc() as AnyObject)
    .perform(sel, with: sourceAvatarView)?
    .takeUnretainedValue() as? UIView

portal?.frame = fullScreenTargetFrame
transitionContainer.addSubview(portal!)
// The portal now shows the avatar's live pixels; animate portal.frame.

    The CAPortalLayer side (also private in its useful form) exposes properties like sourceLayer and flags controlling whether hidden/matched source content is drawn. Because none of this is in a public header, you are relying on symbol names and behavior that Apple can change or that static analysis will flag.

    Warning — App Store risk. _UIPortalView, CAPortalLayer.sourceLayer, and friends are private API. Shipping them risks automated rejection and runtime breakage across OS updates. Treat this section as "how the system works," never as a recommendation. The next section is what you should actually ship.

    Public, App-Store-safe alternatives (use these)

    Pick by whether you need live content or a frozen frame.

    1. Static snapshot — the default, covers most transitions. If the source won't visibly change during the animation, a snapshot is the right tool. It's a real, public view you can animate anywhere.

    // Frozen copy — cheapest, safest. afterScreenUpdates: false uses the
// currently-rendered content; true forces a layout pass first.
guard let snap = sourceAvatarView.snapshotView(afterScreenUpdates: false) else { return }
snap.frame = transitionContainer.convert(sourceAvatarView.bounds, from: sourceAvatarView)
transitionContainer.addSubview(snap)

sourceAvatarView.isHidden = true            // hide original during the move
UIView.animate(withDuration: 0.35) {
    snap.frame = fullScreenTargetFrame
} completion: { _ in
    snap.removeFromSuperview()
    sourceAvatarView.isHidden = false
}

    resizableSnapshotView(from:afterScreenUpdates:withCapInsets:) gives you a stretchable variant when the target size differs a lot from the source.

    2. Temporarily reparent the real view. When you truly need live content (a video, a spinner, an animating chart) and a snapshot would look dead, move the actual view into a transition/window-level container for the duration, then put it back. This is the honest, supported version of what a portal fakes.

    let originalSuperview = liveView.superview
let originalFrame = liveView.frame
let start = container.convert(liveView.bounds, from: liveView)

container.addSubview(liveView)              // reparent up
liveView.frame = start
UIView.animate(withDuration: 0.35) {
    liveView.frame = fullScreenTargetFrame
} completion: { _ in
    originalSuperview?.addSubview(liveView) // reparent back
    liveView.frame = originalFrame          // (or re-apply constraints)
}

    The tradeoff: if the source is under Auto Layout you must restore its constraints, and if it's inside a recycling cell you must guard against the cell being reused mid-flight.

    3. CAReplicatorLayer. When you want many mirrored copies of one sublayer tree (repeating chrome, reflections, particle-like effects), a replicator layer draws N transformed instances of its sublayers for free.

    4. Render to an image. layer.render(in:) or drawHierarchy(in:afterScreenUpdates:) into a UIGraphicsImageRenderer context gives you a bitmap you can place anywhere. Heavier than snapshotView and also static; useful when you need the pixels as an actual UIImage (sharing, blurring, masking).

    let renderer = UIGraphicsImageRenderer(bounds: sourceAvatarView.bounds)
let image = renderer.image { ctx in
    sourceAvatarView.drawHierarchy(in: sourceAvatarView.bounds, afterScreenUpdates: true)
}

    5. SwiftUI cousins. If you're in SwiftUI, matchedGeometryEffect(id:in:) and the zoom navigation transition (.navigationTransition(.zoom(...))) give you portal-like "one element morphs across screens" behavior with zero private API — the framework owns the live handoff for you.

    Choosing the right tool

    • Source is static during the move, or a one-frame flash is acceptable → snapshotView (default).
    • Source is genuinely live and must keep animating → temporarily reparent the real view.
    • You need N mirrored copies → CAReplicatorLayer.
    • You need the pixels as a UIImage → render(in:) / drawHierarchy.
    • You're in SwiftUI → matchedGeometryEffect or zoom transition.
    • You need a live mirror without moving the source and can't reparent → this is the only case portals uniquely solve, and there is no public API for it. Redesign so one of the above works, rather than shipping _UIPortalView.

    The foundation

    • Portal = a live, one-way mirror of a source layer's rendered content shown at another location; source is neither moved nor copied.
    • _UIPortalView / CAPortalLayer = Apple's private classes implementing portals; CAPortalLayer.sourceLayer names the mirrored layer. Private API — rejection and breakage risk.
    • Snapshot = a frozen, public copy of a view's pixels (snapshotView(afterScreenUpdates:), resizableSnapshotView); ideal when the source won't change mid-animation.
    • Reparenting = physically moving the real view to another superview (often a window-level container) for the transition, then restoring it — the supported way to animate live content across hierarchies.
    • CAReplicatorLayer = draws multiple transformed instances of its sublayers; use for repeated/mirrored copies, not single morphs.
    • layer.render(in:) / drawHierarchy(in:afterScreenUpdates:) = rasterize a view/layer into a bitmap context; static, heavier, produces a real image.
    • matchedGeometryEffect = SwiftUI's declarative element handoff across views; framework-managed, no private API.
    • Live vs. frozen = the core decision: need continuously updating pixels → portal/reparent; a single captured frame is enough → snapshot.

    11 — UIWindow, Window Levels & Scene Lifecycle

    Start here — the plain idea

    Think of your app's screen as a stack of transparent sheets on an overhead projector. The bottom sheet holds everything your users normally see — your whole view-controller hierarchy sits on it. That bottom sheet is your UIWindow. Almost every app you've ever written uses exactly one and never thinks about it again.

    But you can lay more sheets on top. Slide a fresh transparent sheet above the stack, draw a small toast on it, and it floats over your entire app — above navigation bars, above modals, above everything — without disturbing a single view controller underneath. When the toast fades, you lift that sheet off and the app below never knew it was there. That's the mental model for an overlay window: a second UIWindow, stacked higher, that you own for a moment and then throw away.

    The trick that makes it feel magical is that the extra sheet is mostly see-through to touch — taps pass straight through the empty areas to the app below, and only the toast itself is interactive. Get that hit-testing right and you have a global HUD, tooltip, or loading spinner that lives completely independently of whatever screen the user is on.

    UIWindow basics

    A UIWindow is a UIView subclass — the root of a view hierarchy rather than a leaf in one. Its rootViewController supplies the view that fills it. In the modern lifecycle a window doesn't attach to the screen directly; it attaches to a UIWindowScene.

    // The window your app already has, created for a scene:
final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(_ scene: UIScene,
               willConnectTo session: UISceneSession,
               options: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let window = UIWindow(windowScene: windowScene)   // bind to the scene
        window.rootViewController = RootViewController()
        window.makeKeyAndVisible()                          // key = receives events
        self.window = window
    }
}

    makeKeyAndVisible() does two things: makes the window visible and makes it the key window (the one that receives keyboard and other non-touch events). Touch events go to whatever window is topmost at the touch point, regardless of which is key.

    windowLevel — controlling the stack

    Every window has a windowLevel, a CGFloat-backed value that decides stacking order. Higher levels sit above lower ones. UIKit ships a few named constants:

    • .normal (0) — your app's root window.
    • .statusBar — around the status bar region.
    • .alert — where system alerts float.

    You can also use arbitrary values, including offsets from the named ones, to slot an overlay exactly where you want it.

    Overlay presentation without a view controller

    Here's the payoff: a global HUD that needs no place in your VC hierarchy. Create a lightweight window on the active scene, give it a passthrough root so touches fall through except on the HUD itself, show your content, then tear it down.

    First, a window whose hit-testing ignores empty space:

    final class PassthroughWindow: UIWindow {
    override func hitTest(_ point: CGPoint, with event: UIEvent?) -> UIView? {
        let hit = super.hitTest(point, with: event)
        // If the hit is the window's own root view (empty area), let the
        // touch fall through to windows below by returning nil.
        return hit === rootViewController?.view ? nil : hit
    }
}

    Then a tiny controller to own the overlay, and code to present it on the current scene:

    @MainActor
final class HUDPresenter {
    private var window: PassthroughWindow?

    func show(_ overlay: UIView, on scene: UIWindowScene) {
        let window = PassthroughWindow(windowScene: scene)
        window.windowLevel = .alert + 1            // above alerts
        window.backgroundColor = .clear
        let host = UIViewController()
        host.view.backgroundColor = .clear
        window.rootViewController = host
        window.isHidden = false                    // show without becoming key

        overlay.translatesAutoresizingMaskIntoConstraints = false
        host.view.addSubview(overlay)
        NSLayoutConstraint.activate([
            overlay.centerXAnchor.constraint(equalTo: host.view.centerXAnchor),
            overlay.bottomAnchor.constraint(equalTo: host.view.safeAreaLayoutGuide.bottomAnchor,
                                            constant: -24)
        ])
        self.window = window
    }

    func dismiss() {
        window?.isHidden = true
        window = nil                               // release → deallocated
    }
}

    Note isHidden = false rather than makeKeyAndVisible(): a passive overlay shouldn't steal key status (and keyboard focus) from your app. Setting the window to nil is how you tear it down — once nothing retains it, it deallocates and leaves the screen.

    Getting the active scene in a multi-scene world

    On iPad (and increasingly on iPhone via Stage Manager and external displays) an app can have several scenes alive at once. There is no single "the window" anymore — you must find the scene that's currently in the foreground and active.

    extension UIApplication {
    var activeWindowScene: UIWindowScene? {
        connectedScenes
            .compactMap { $0 as? UIWindowScene }
            .first { $0.activationState == .foregroundActive }
    }
}

    Prefer this over the deprecated UIApplication.shared.keyWindow / windows, which are meaningless when multiple scenes exist.

    Scene lifecycle

    UISceneDelegate (and its UIWindowSceneDelegate specialization) is where per-scene lifecycle lands. The states you'll handle most:

    func sceneDidBecomeActive(_ scene: UIScene) {
    // Foreground + interactive: resume timers, refresh, restart animations.
}
func sceneWillResignActive(_ scene: UIScene) {
    // About to become inactive (call, control center, app switcher): pause.
}
func sceneDidEnterBackground(_ scene: UIScene) {
    // Not visible: save state, release scarce resources.
}

    Each scene transitions through unattached → foreground-inactive → foreground-active → background independently, so two windows of your app can be in different states simultaneously. Scene-scoped work (which window to update, which overlay to present) belongs on the scene delegate, not on the app delegate, precisely because of this independence.

    The foundation

    • UIWindow = a UIView subclass that roots a view hierarchy; hosts a rootViewController and attaches to a UIWindowScene.
    • Key window = the window receiving keyboard/non-touch events; set via makeKeyAndVisible(). Touch events instead go to the topmost window at the touch point.
    • windowLevel = the CGFloat stacking order (.normal, .statusBar, .alert, or custom); higher floats above lower.
    • Overlay window = a second, higher-level UIWindow you create for transient UI (toast, HUD, spinner) and tear down by releasing it — no VC-hierarchy changes.
    • Passthrough hit-testing = overriding hitTest(_:with:) to return nil for empty areas so touches fall through to windows below, keeping only the overlay interactive.
    • UIWindowScene = the modern attachment point between a window and the display; one app can own several.
    • UISceneDelegate / UIWindowSceneDelegate = per-scene lifecycle callbacks (willConnectTo, sceneDidBecomeActive, sceneWillResignActive, sceneDidEnterBackground).
    • Active scene lookup = connectedScenes filtered to a UIWindowScene whose activationState == .foregroundActive; the multi-scene-correct replacement for keyWindow.

    12 — Keyboard Handling

    Start here — the plain idea

    Picture yourself typing in a chat app. You tap the text field, and the keyboard slides up from the bottom of the screen. But the keyboard is opaque and it's tall — if your composer bar were still glued to the bottom of the window, it would now be hidden behind the keyboard, and you'd be typing blind. So the composer has to lift up and ride exactly on top of the keyboard, matching its height, its slide-up timing, and its easing curve so precisely that the two feel welded together.

    Now make it harder: the user scrolls the message list and drags down to dismiss the keyboard. The keyboard doesn't snap away — it follows the finger, sliding down interactively. Your composer has to follow it down in lockstep, tracking the keyboard's live position frame by frame as the finger moves. Get any of this even slightly wrong and the composer visibly stutters, lags a frame behind, or briefly reveals a strip of empty background between itself and the keyboard.

    This is one of the most famously fiddly corners of UIKit, and Apple has shipped three generations of tooling for it: the old-school notification dance you had to hand-wire for years, the modern keyboardLayoutGuide that tracks the keyboard for you with almost no code, and the interactive-dismiss machinery that ties it all together. Here's the whole toolkit, oldest to newest.

    The classic notification dance

    Before iOS 15 there was exactly one way to do this, and every serious app hand-rolled it. UIKit posts notifications as the keyboard changes frame, and you read the geometry and animation parameters out of the userInfo dictionary.

    The key notification is keyboardWillChangeFrameNotification — it fires for show, hide, and height changes (like switching to an emoji keyboard or a taller autocorrect bar), so observing just this one covers every case. The userInfo keys you care about:

    final class ComposerViewController: UIViewController {
    @IBOutlet private var bottomConstraint: NSLayoutConstraint!  // composer bottom → view bottom

    override func viewDidLoad() {
        super.viewDidLoad()
        NotificationCenter.default.addObserver(
            self,
            selector: #selector(keyboardWillChangeFrame(_:)),
            name: UIResponder.keyboardWillChangeFrameNotification,
            object: nil
        )
    }

    @objc private func keyboardWillChangeFrame(_ note: Notification) {
        guard let info = note.userInfo,
              let endFrameValue = info[UIResponder.keyboardFrameEndUserInfoKey] as? NSValue,
              let duration = info[UIResponder.keyboardAnimationDurationUserInfoKey] as? Double,
              let curveRaw = info[UIResponder.keyboardAnimationCurveUserInfoKey] as? Int
        else { return }

        // The end frame is in SCREEN coordinates — convert into our view.
        let endFrameInWindow = endFrameValue.cgRectValue
        let endFrameInView = view.convert(endFrameInWindow, from: view.window)

        // How much of the keyboard actually overlaps our view (0 when hidden below).
        let overlap = max(0, view.bounds.maxY - endFrameInView.minY)
        let inset = overlap - view.safeAreaInsets.bottom

        bottomConstraint.constant = max(0, inset)

        // The system's own curve arrives as a *raw* value (7) outside the public
        // UIView.AnimationCurve enum. Shift it into the options bitfield to match exactly.
        let options = UIView.AnimationOptions(rawValue: UInt(curveRaw << 16))
        UIView.animate(withDuration: duration, delay: 0, options: options) {
            self.view.layoutIfNeeded()
        }
    }
}

    Three details trip everyone up. First, the frame is in screen coordinates — you must convert it into your view before comparing, or split-view and Stage Manager layouts will be wrong. Second, subtract the safe-area inset or you'll double-count the home-indicator gap and leave a dead strip. Third, the animation curve is a private raw value (7) that doesn't map to any public UIView.AnimationCurve case; the << 16 shift into the AnimationOptions bitfield is the well-worn trick to reproduce Apple's exact easing rather than a stock .easeInOut.

    The modern way — keyboardLayoutGuide

    iOS 15 introduced UIView.keyboardLayoutGuide, and it makes almost all of the above obsolete. It's a layout guide living on your view whose frame automatically tracks the keyboard. You pin your composer to its topAnchor and UIKit keeps them glued together — through show, hide, height changes, and animation curves — with no notifications, no coordinate conversion, no curve-decoding hack.

    composer.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(composer)

NSLayoutConstraint.activate([
    composer.leadingAnchor.constraint(equalTo: view.leadingAnchor),
    composer.trailingAnchor.constraint(equalTo: view.trailingAnchor),
    // Sit right on top of the keyboard. When the keyboard is down, the guide
    // collapses to the bottom safe area, so the composer rests above the home indicator.
    composer.bottomAnchor.constraint(equalTo: view.keyboardLayoutGuide.topAnchor)
])

    That's the whole thing. When the keyboard is dismissed, the guide automatically falls back to tracking the bottom safe-area edge, so the composer sits above the home indicator exactly as you'd want — no separate "keyboard hidden" branch to write.

    One property worth knowing: keyboardLayoutGuide.followsUndockedKeyboard. By default the guide only tracks the docked keyboard (pinned to the screen bottom). On iPad the user can undock or float the keyboard; setting followsUndockedKeyboard = true makes the guide chase it around the screen too. Leave it false (the default) if you want the composer to stay put when the keyboard floats free.

    Interactive dismissal

    Set scrollView.keyboardDismissMode = .interactive and the user can drag down through your message list to slide the keyboard away with their finger — the keyboard tracks the touch position live instead of snapping shut when the drag ends (which is what .onDrag does).

    tableView.keyboardDismissMode = .interactive

    Here's the caveat that bites people who are still on the classic notification approach: during an interactive drag, the willChangeFrame notifications do not fire continuously. They fire once at the start and once when the gesture resolves, but not for every intermediate position as the finger moves. So a composer wired purely to notifications will sit frozen at the top while the keyboard slides down under the finger, then jump to catch up at the end — visibly broken.

    This is the strongest single argument for keyboardLayoutGuide: it does track the keyboard continuously through an interactive drag, because it's driven by the same internal mechanism moving the keyboard, not by the coarse notification stream. If you want interactive dismissal to look right with minimal effort, pin to the layout guide and let it handle the live tracking.

    Building a composer that grows and rides the keyboard

    Putting it together: a real chat composer both grows vertically as the user types (a multi-line text view that expands up to some cap) and rides on top of the keyboard. The two concerns compose cleanly because they're independent — one drives the composer's own height, the other drives its bottom position.

    final class ChatComposer: UIView {
    let textView = UITextView()
    private var heightConstraint: NSLayoutConstraint!
    private let maxHeight: CGFloat = 120

    override init(frame: CGRect) {
        super.init(frame: frame)
        textView.translatesAutoresizingMaskIntoConstraints = false
        textView.isScrollEnabled = false            // let it grow instead of scrolling
        textView.font = .preferredFont(forTextStyle: .body)
        textView.delegate = self
        addSubview(textView)

        heightConstraint = textView.heightAnchor.constraint(equalToConstant: 40)
        NSLayoutConstraint.activate([
            textView.leadingAnchor.constraint(equalTo: leadingAnchor, constant: 12),
            textView.trailingAnchor.constraint(equalTo: trailingAnchor, constant: -12),
            textView.topAnchor.constraint(equalTo: topAnchor, constant: 8),
            textView.bottomAnchor.constraint(equalTo: bottomAnchor, constant: -8),
            heightConstraint
        ])
    }
    required init?(coder: NSCoder) { fatalError() }
}

extension ChatComposer: UITextViewDelegate {
    func textViewDidChange(_ textView: UITextView) {
        // Recompute the fitting height and clamp it.
        let fitting = textView.sizeThatFits(
            CGSize(width: textView.bounds.width, height: .greatestFiniteMagnitude)
        ).height
        let clamped = min(fitting, maxHeight)
        textView.isScrollEnabled = fitting > maxHeight   // scroll only past the cap
        if heightConstraint.constant != clamped {
            heightConstraint.constant = clamped
            UIView.animate(withDuration: 0.15) { self.superview?.layoutIfNeeded() }
        }
    }
}

    The composer's height comes from sizeThatFits on the text view, clamped and switched to scrolling past the cap. Its position comes from pinning composer.bottomAnchor to keyboardLayoutGuide.topAnchor as shown earlier. Neither knows about the other. For the full narrative on this design, watch WWDC21 "Your guide to keyboard layout" (which introduced keyboardLayoutGuide) and WWDC23 "Keep up with the keyboard" (which covers interactive tracking and the newer keyboard-scene APIs).

    The foundation

    • keyboardWillChangeFrameNotification = the single notification covering show, hide, and height changes; read geometry and animation params from its userInfo.
    • keyboardFrameEndUserInfoKey = the keyboard's final frame, in screen coordinates — always convert it into your view before use.
    • keyboardAnimationCurveUserInfoKey = a raw curve value (often 7) with no public enum case; shift it << 16 into AnimationOptions to match Apple's easing exactly.
    • keyboardLayoutGuide = a per-view layout guide (iOS 15+) whose frame tracks the keyboard automatically; pin to its topAnchor and skip the notification dance entirely.
    • followsUndockedKeyboard = property making the guide chase floating/undocked iPad keyboards too; default false keeps your UI still when the keyboard floats.
    • keyboardDismissMode = .interactive = drag-to-dismiss where the keyboard tracks the finger live; note that classic notifications go silent mid-drag, so the layout guide handles this far better.
    • sizeThatFits = the call that gives a text view its natural content height, letting a composer grow with typed text up to a cap before it starts scrolling.

    13 — Context Menus: UIContextMenuInteraction & UIMenu

    Start here — the plain idea

    Long-press a photo in Messages, a link in Safari, or an app icon on the Home Screen. The thing you pressed lifts off the surface, the background behind it blurs and dims, and a tidy menu of actions unfurls beside it — Copy, Share, Delete. This is the modern descendant of the old "peek & pop" 3D Touch feature: a preview of the content plus a menu of things you can do to it, presented with a little physical flourish where the item appears to float above everything else.

    The nice thing is that UIKit gives you almost all of that polish for free. You attach one interaction object to a view, hand back a description of the preview and the menu, and the framework handles the long-press recognition, the blur, the lift animation, the springy menu reveal, and the dismissal. You describe what; UIKit performs the how.

    The menu itself — UIMenu filled with UIActions — turns out to be a reusable currency across UIKit. The same menu type powers button pull-downs, the text selection edit menu, and navigation-bar overflow menus. Learn it once here and you've learned it everywhere.

    Attaching a context menu

    You add a UIContextMenuInteraction to any view and become its delegate. The delegate's job is to return a UIContextMenuConfiguration describing two things: an optional previewProvider (a view controller shown as the lifted "peek") and an actionProvider that builds the menu.

    final class PhotoCell: UICollectionViewCell {
    func installContextMenu() {
        let interaction = UIContextMenuInteraction(delegate: self)
        addInteraction(interaction)
    }
}

extension PhotoCell: UIContextMenuInteractionDelegate {
    func contextMenuInteraction(
        _ interaction: UIContextMenuInteraction,
        configurationForMenuAtLocation location: CGPoint
    ) -> UIContextMenuConfiguration? {
        UIContextMenuConfiguration(
            identifier: nil,
            previewProvider: { PhotoPreviewController(image: self.image) },
            actionProvider: { _ in
                let share = UIAction(title: "Share", image: UIImage(systemName: "square.and.arrow.up")) { _ in
                    // present share sheet
                }
                let favorite = UIAction(title: "Favorite", image: UIImage(systemName: "star")) { _ in }
                let delete = UIAction(title: "Delete",
                                      image: UIImage(systemName: "trash"),
                                      attributes: .destructive) { _ in }
                return UIMenu(title: "", children: [share, favorite, delete])
            }
        )
    }
}

    The previewProvider is lazy — the closure only runs if the interaction actually commits to showing a preview, so you don't pay to build a view controller on every touch. The actionProvider receives any suggested system actions and returns the final UIMenu. Returning nil from the top-level configuration method means "no menu here," which is how you conditionally suppress the menu on certain items.

    Nested menus and deferred elements

    A UIMenu's children array can contain other UIMenus, which render as inline groups or as submenus you drill into. And when part of a menu is expensive to build — say the list of albums to move a photo into — you can drop in a UIDeferredMenuElement that shows a spinner and fills itself in asynchronously, so the menu appears instantly instead of blocking on the slow work.

    let moveSubmenu = UIMenu(title: "Move to Album", image: UIImage(systemName: "folder"),
                         children: [
    UIDeferredMenuElement { completion in
        AlbumStore.shared.fetchAlbums { albums in
            let actions = albums.map { album in
                UIAction(title: album.name) { _ in album.add(self.photo) }
            }
            completion(actions)   // menu fills in when this fires
        }
    }
])

let root = UIMenu(children: [share, moveSubmenu, delete])

    UIDeferredMenuElement has an .uncached variant that re-runs the provider each time the menu opens, which matters when the underlying data changes between presentations.

    Targeted previews

    By default UIKit computes the lifted preview from the view you attached the interaction to, giving it a sensible rounded rectangle. When that default looks wrong — the view is an odd shape, or you want a different corner radius, or you want to preview a different region than the whole cell — you supply a UITargetedPreview. It pairs a view (the thing that lifts) with parameters describing its visible path and background.

    extension PhotoCell: UIContextMenuInteractionDelegate {
    func contextMenuInteraction(
        _ interaction: UIContextMenuInteraction,
        previewForHighlightingMenuWithConfiguration configuration: UIContextMenuConfiguration
    ) -> UITargetedPreview? {
        let params = UIPreviewParameters()
        params.backgroundColor = .clear
        // Lift only the rounded image, not the whole cell's bounds.
        params.visiblePath = UIBezierPath(roundedRect: imageView.frame, cornerRadius: 16)
        return UITargetedPreview(view: imageView, parameters: params)
    }

    func contextMenuInteraction(
        _ interaction: UIContextMenuInteraction,
        willPerformPreviewActionForMenuWith configuration: UIContextMenuConfiguration,
        animator: UIContextMenuInteractionCommitAnimating
    ) {
        // User tapped the preview itself — navigate to the full detail screen.
        animator.addCompletion {
            self.delegate?.openDetail(for: self.photo)
        }
    }
}

    The willPerformPreviewAction delegate method is the "tap-through" hook: when the user taps the floating preview (rather than a menu row), you commit to the full navigation. Adding it to the animator's completion lets your push ride the same dismissal animation smoothly.

    UIMenu everywhere

    The UIMenu you built for the context menu isn't special to context menus. The same object drives:

    // A button that shows a pull-down menu instead of firing an action.
button.menu = UIMenu(children: [sortByName, sortByDate, sortBySize])
button.showsMenuAsPrimaryAction = true

// The text selection edit menu (iOS 16+) — customize Copy/Look Up/etc.
let editInteraction = UIEditMenuInteraction(delegate: self)
textView.addInteraction(editInteraction)

    UIEditMenuInteraction replaced the old UIMenuController for text selection menus and speaks the same UIMenu/UIAction vocabulary. Once you're fluent in building menus, buttons, edit menus, and context menus all become the same job.

    When apps hand-roll it instead

    Here's the trade-off worth understanding. The system context-menu API gives you Apple's exact blur, lift physics, and dismissal for free — but you're locked into its choreography. You can't reorder items with a drag inside the open menu, you can't overlay a row of reaction emoji above the preview, and you can't fully retime the peek animation.

    So some apps deliberately hand-roll the whole thing. Messaging apps that show a reaction bar floating above the pressed bubble, with the menu below and a springy custom preview, typically build their own long-press-plus-pan gesture, render their own blurred snapshot of the background, and lay out their own preview and menu views. (This is an observation about what such interfaces do on screen — not a claim about any specific app's source code.) The payoff is total control over the peek animation, live reordering, and reactions. The cost is that you give up all the free system polish and now own the accessibility, the reduce-motion handling, the dark-mode blur, and every edge case yourself. Reach for the system API unless you specifically need something it structurally cannot express.

    The foundation

    • UIContextMenuInteraction = the interaction you add to any view to give it a long-press context menu; you become its delegate.
    • UIContextMenuConfiguration = the object your delegate returns describing the menu; return nil to suppress the menu for that item.
    • previewProvider = a lazy closure returning the view controller shown as the lifted peek; runs only if a preview is actually committed.
    • actionProvider = a closure that receives suggested actions and returns the final UIMenu.
    • UIMenu / UIAction = the reusable menu vocabulary; UIMenu.children can nest submenus, and UIDeferredMenuElement fills part of a menu in asynchronously.
    • UITargetedPreview / UIPreviewParameters = control the lifted preview's shape, corner radius, visiblePath, and background when the default is wrong.
    • willPerformPreviewAction = the tap-through hook fired when the user taps the preview itself; commit navigation via the animator's completion.
    • UIEditMenuInteraction = the modern text-selection edit menu (iOS 16+), built from the same UIMenu/UIAction types.

    14 — View Allocation Cost & Reuse Discipline

    Start here — the plain idea

    UIView() reads like it costs nothing. It's one line, it returns instantly, and in a demo with a dozen views you'll never notice a thing. So it's tempting to treat views like free scratch paper — wrap this in a container, nest that in a stack, add a decorative subview here and there. And for a dozen, sure. But a view is not a lightweight value type. Every single one drags a small entourage behind it.

    Each view is a heap-allocated Objective-C object. It creates and owns a backing CALayer. It registers a pile of Auto Layout constraints that the engine has to solve. And it claims a permanent seat in the render tree, meaning every layout pass, every hit test, and every compositing pass has to walk past it. One view: negligible. A thousand of them in a scrolling feed, rebuilt as you fling: now you can feel it — dropped frames, laggy scrolling, a warm phone.

    So the discipline that separates a smooth app from a janky one is treating views as the expensive, pooled resource they actually are: create as few as you can, reuse the ones you have, and draw instead of stacking whenever a view is just decoration. This lesson is about why views cost what they cost and the three habits that keep the cost down.

    Why a view is expensive

    Break down what happens when you instantiate and add one view:

    • Object allocation. A UIView is a real object on the heap with dozens of ivars — gesture recognizers array, subviews array, layout metadata, appearance state. Allocating and later deallocating thousands of these churns memory.
    • CALayer creation. Every view is backed by a CALayer it creates in init. That layer has its own properties, its own backing store when it draws, and its own node in the layer tree Core Animation composites.
    • Constraint setup. If you use Auto Layout, each view's constraints become variables and equations in the layout engine's solver. The solver's cost grows worse-than-linearly with constraint count, so deep constraint webs get expensive fast.
    • Tree participation. Layout, hit-testing, and compositing all traverse the view/layer hierarchy. A deep hierarchy means more nodes to walk on every pass, plus a higher chance of triggering offscreen compositing for effects like masks and shadows.

    None of these is catastrophic alone. The problem is multiplication: cost-per-view times view-count times passes-per-second.

    Reuse discipline

    The single biggest win is to stop re-creating views and start recycling them. This is exactly what UITableView and UICollectionView do under the hood — they keep a small pool of cells sized to what's on screen and hand the same objects back as you scroll, resetting their content instead of allocating fresh ones. When you build any list-like surface yourself (see 08-recycling-list-on-uiscrollview), you owe it the same treatment.

    final class TilePool {
    private var available: [TileView] = []

    func dequeue() -> TileView {
        if let reused = available.popLast() {
            reused.prepareForReuse()   // wipe old content, cancel image loads
            return reused
        }
        return TileView()              // allocate only when the pool is dry
    }

    func recycle(_ tile: TileView) {
        tile.removeFromSuperview()
        available.append(tile)
    }
}

final class TileView: UIView {
    func prepareForReuse() {
        imageView.image = nil
        imageTask?.cancel()
        titleLabel.text = nil
    }
}

    The rule of thumb: the number of view objects you allocate should track the number visible at once, not the total number of items in your data. A 10,000-row feed should still only own a few dozen live views.

    Flattening — draw instead of stack

    The second habit is reducing the view count itself. A lot of hierarchies are deeper than they need to be: a container holding a background view, holding an icon view, holding two labels and a separator line — five views where a single view drawing five elements would do.

    final class BadgeView: UIView {
    var title = "" { didSet { setNeedsDisplay() } }
    var count = 0  { didSet { setNeedsDisplay() } }

    override func draw(_ rect: CGRect) {
        // One view, one backing store — draw the pill, text, and dot directly.
        let pill = UIBezierPath(roundedRect: rect.insetBy(dx: 1, dy: 1), cornerRadius: rect.height / 2)
        UIColor.secondarySystemFill.setFill()
        pill.fill()

        (title as NSString).draw(at: CGPoint(x: 12, y: 6),
            withAttributes: [.font: UIFont.preferredFont(forTextStyle: .caption1),
                             .foregroundColor: UIColor.label])

        if count > 0 {
            UIColor.systemRed.setFill()
            UIBezierPath(ovalIn: CGRect(x: rect.maxX - 16, y: 6, width: 8, height: 8)).fill()
        }
    }
}

    Two flattening moves worth internalizing. First, draw composite content in one draw(_:) (or one custom CALayer) instead of assembling it from subviews, as above. Second, use plain CALayers for non-interactive decoration — a hairline separator, a gradient, a border, a static shape don't need to be UIViews at all. A CALayer skips the responder/gesture/Auto Layout machinery entirely:

    let separator = CALayer()
separator.backgroundColor = UIColor.separator.cgColor
separator.frame = CGRect(x: 0, y: bounds.maxY - 0.5, width: bounds.width, height: 0.5)
layer.addSublayer(separator)   // no UIView needed for a static line

    And simply delete unnecessary container views — a UIStackView wrapping a single arranged subview, or a "content view" that adds nothing but a level of nesting. Every level you remove is one fewer node on every traversal.

    Costs to watch, and how to measure them

    Beyond raw view count, a few specific things quietly force expensive offscreen rendering — the GPU has to render into a separate buffer and composite it back, which is far pricier than a straight draw:

    • Shadows without a shadowPath. layer.shadowOpacity with no explicit shadowPath makes Core Animation render the view offscreen to compute the shadow's shape from its alpha. Always set layer.shadowPath to a known path — it's the single most common offscreen-rendering culprit.
    • cornerRadius + masksToBounds on many views. Rounding that clips content forces an offscreen pass per view; a screenful of rounded, clipping cells adds up. Prefer a pre-rounded image or a shadowPath-style known shape where you can.
    • Masks (layer.mask). Any layer.mask forces offscreen compositing by definition.
    • shouldRasterize. A double-edged tool: it caches a layer's rendered output so static, complex content composites cheaply — but if the content changes every frame, you pay to re-rasterize plus the cache overhead, making it slower. Only rasterize genuinely static subtrees.
    • Blending and overdraw. Translucent views stacked over each other force per-pixel blending; large areas of overdraw (many layers painting the same pixels) waste fill-rate.

    To find these, don't guess — measure. In Instruments, the Core Animation template flags offscreen passes and shows frame rate under load, and Time Profiler shows where layout and drawing time actually goes. On device, the debugger's rendering options light up the problems visually: Color Blended Layers paints overdraw/blending red, and Color Offscreen-Rendered paints offscreen passes yellow. Turn them on, scroll your worst screen, and fix whatever glows.

    The foundation

    • View cost = object allocation + CALayer creation + constraint solving + a permanent node in the layout/hit-test/composite tree; negligible once, expensive at scale.
    • Reuse discipline = pool and recycle views via prepareForReuse so live view count tracks what's visible, not total item count (as UITableView/UICollectionView do).
    • Flattening = collapse deep hierarchies by drawing composite content in one draw(_:) and deleting needless container views.
    • CALayer for decoration = use plain layers for static, non-interactive visuals (separators, gradients, borders) to skip the full UIView machinery.
    • Offscreen rendering = an extra GPU buffer-and-composite pass triggered by shadows-without-shadowPath, masks, and cornerRadius+masksToBounds; far pricier than a direct draw.
    • shadowPath = an explicit shadow shape that avoids the offscreen pass a shadow otherwise forces; the highest-value single fix.
    • shouldRasterize = caches a subtree's render for cheap reuse when static, but costs more if the content changes each frame.
    • Measuring tools = Instruments (Core Animation, Time Profiler) plus the debugger's Color Blended Layers and Color Offscreen-Rendered overlays.
