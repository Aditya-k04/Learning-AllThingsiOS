    UIKit Workshop

    You already know Swift. Now let's build something with UIKit — the framework that still powers most of the apps on your phone.

    This is a hands-on course. Instead of long theory chapters, you get 9 independent, runnable labs. Each one is a focused mini-project: you spin up a fresh Xcode app, type out real multi-file code, hit Run, and watch the pieces click together on the simulator. Everything is programmatic UIKit — no storyboards, no drag-and-drop, no hidden magic. You'll see exactly where every view comes from.

    Every lab stands on its own. You can do them in order (recommended) or jump to the one you need today.

    How to use these labs

    Each lab is fully self-contained — its own tiny Xcode project.

    1. In Xcode, choose File ▸ New ▸ Project… ▸ iOS ▸ App.
    2. Pick Swift as the language and Storyboard as the interface (we'll delete it — it's just the least-fiddly starting template).
    3. Set it up programmatically: delete Main.storyboard, and clear the storyboard name from the scene manifest so UIKit doesn't try to load a storyboard that no longer exists. Lab 01 walks through every click of this — do that one first and you'll never have to think about it again.
    4. Type out the files for the lab, then ⌘R to run.

    Target for the whole course: iOS 26 / 27, Swift 6.x, Xcode 26.

    Type the code — don't paste it. Muscle memory is the point.

    01 — A Screen From Scratch (No Storyboard)

    by the end you'll have built a working screen — a title, a button, and a live counter — with zero storyboard, all in code.

    ⏱ ~20 min · Beginner

    What you'll build

    A single screen that shows a title label and a "Tap me" button; every tap bumps a counter label. Along the way you'll learn how a UIKit app actually starts — how a UIWindow gets a root view controller — without any storyboard doing it invisibly for you.

    Files in play

    TapCounter/
├── AppDelegate.swift          // app lifecycle (minimal)
├── SceneDelegate.swift        // builds the window + root VC in code
└── CounterViewController.swift // the screen: labels, button, counting logic

    You start from Xcode's iOS ▸ App template (Storyboard interface), then delete the storyboard. The two delegate files already exist — you'll trim them.

    Build it, file by file

    AppDelegate.swift

    The app's top-level lifecycle object. For a scene-based app it barely does anything — it just tells UIKit "use the default scene configuration." Leave it minimal.

    import UIKit

@main
final class AppDelegate: UIResponder, UIApplicationDelegate {

    func application(
        _ application: UIApplication,
        didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]? = nil
    ) -> Bool {
        return true
    }

    // Tells UIKit which scene configuration to use. The name here
    // ("Default Configuration") must match the one in Info.plist.
    func application(
        _ application: UIApplication,
        configurationForConnecting connectingSceneSession: UISceneSession,
        options: UIScene.ConnectionOptions
    ) -> UISceneConfiguration {
        UISceneConfiguration(name: "Default Configuration", sessionRole: connectingSceneSession.role)
    }
}

    @main marks this as the app's entry point. Notice there's no window here — in a scene-based app, the scene owns the window. That's the next file.

    SceneDelegate.swift

    This is where the magic normally hidden by a storyboard becomes visible. A scene connects, and you create the window and decide what's inside it.

    import UIKit

final class SceneDelegate: UIResponder, UIWindowSceneDelegate {

    var window: UIWindow?

    func scene(
        _ scene: UIScene,
        willConnectTo session: UISceneSession,
        options connectionOptions: UIScene.ConnectionOptions
    ) {
        // A UIScene arrives as a plain UIScene — cast to the window scene type.
        guard let windowScene = scene as? UIWindowScene else { return }

        // Create the window tied to THIS scene (not the old UIWindow() initializer).
        let window = UIWindow(windowScene: windowScene)

        // Pick what shows first. No storyboard = we say it explicitly.
        window.rootViewController = CounterViewController()

        // Show the window and make it the one receiving events.
        window.makeKeyAndVisible()

        // Keep a strong reference or the window deallocates and you get a black screen.
        self.window = window
    }
}

    The three load-bearing lines: UIWindow(windowScene:) creates the window, rootViewController chooses the first screen, and makeKeyAndVisible() puts it on screen. A storyboard would have done all three for you — now you own them.

    Deleting the storyboard. In the Project navigator, delete Main.storyboard (Move to Trash). Then open Info.plist, drill into Application Scene Manifest ▸ Scene Configuration ▸ Application Session Role ▸ Item 0, and delete the Storyboard Name row. If you skip this, the app crashes at launch trying to load a storyboard that's gone. (Some Xcode 26 templates also list a UIMainStoryboardFile key at the top level — delete that too if present.)

    CounterViewController.swift

    The actual screen. It creates its subviews in code, lays them out with Auto Layout inside a UIStackView, and increments a counter using a UIAction — the modern, closure-based way to handle a button tap.

    import UIKit

final class CounterViewController: UIViewController {

    // State: how many taps so far.
    private var count = 0 {
        didSet { countLabel.text = "\(count)" }   // update the label whenever count changes
    }

    // MARK: - Subviews (created lazily, configured once)

    private let titleLabel: UILabel = {
        let label = UILabel()
        label.text = "Tap Counter"
        label.font = .preferredFont(forTextStyle: .largeTitle)
        label.textAlignment = .center
        return label
    }()

    private let countLabel: UILabel = {
        let label = UILabel()
        label.text = "0"
        label.font = .systemFont(ofSize: 56, weight: .semibold)
        label.textAlignment = .center
        return label
    }()

    private lazy var tapButton: UIButton = {
        // UIButton.Configuration is the modern way to style a button.
        var config = UIButton.Configuration.filled()
        config.title = "Tap me"
        config.baseBackgroundColor = .systemGreen
        config.cornerStyle = .medium

        // UIAction attaches the tap handler right here — no @objc selector needed.
        let action = UIAction { [weak self] _ in
            self?.count += 1
        }
        return UIButton(configuration: config, primaryAction: action)
    }()

    // MARK: - Lifecycle

    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = .systemBackground
        layoutUI()
    }

    // MARK: - Layout

    private func layoutUI() {
        // A vertical stack keeps the three views centered and spaced with almost no code.
        let stack = UIStackView(arrangedSubviews: [titleLabel, countLabel, tapButton])
        stack.axis = .vertical
        stack.alignment = .center
        stack.spacing = 24

        // The one line every programmatic-layout beginner forgets:
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)

        // Pin the stack to the safe-area center.
        NSLayoutConstraint.activate([
            stack.centerXAnchor.constraint(equalTo: view.safeAreaLayoutGuide.centerXAnchor),
            stack.centerYAnchor.constraint(equalTo: view.safeAreaLayoutGuide.centerYAnchor)
        ])
    }
}

    The pieces worth staring at: the didSet on count means the label always mirrors the number — you never set the text manually. UIButton.Configuration.filled() gives you a modern styled button in three lines. And UIAction { ... } is the closure-based replacement for the old addTarget(_:action:for:) + @objc dance.

    Wire it up

    The chain of ownership, top to bottom:

    • AppDelegate (@main) boots the app and hands scene setup to UIKit.
    • UIKit connects a scene → calls SceneDelegate.scene(_:willConnectTo:).
    • SceneDelegate builds a UIWindow and sets CounterViewController as its rootViewController.
    • CounterViewController.viewDidLoad() builds and lays out the UI; the button's UIAction mutates count, whose didSet refreshes countLabel.

    No file imports another by name — they connect through UIKit's lifecycle and one direct reference (SceneDelegate → CounterViewController).

    Run it — you should see

    A clean screen with Tap Counter at the top, a big 0 in the middle, and a green Tap me button below. Each tap increments the number: 1, 2, 3… If you get a black screen, you almost certainly forgot self.window = window or makeKeyAndVisible(). If it crashes at launch, the storyboard name is still in Info.plist.

    Extend it (your turn)

    1. Add a second button, "Reset", that sets count back to 0. (Hint: another UIAction.)
    2. Make the count label turn .systemRed once count passes 10, and back to default below it — all inside the didSet.

    Common mistakes

    • Black screen at launch. You forgot self.window = window (the window deallocates) or window.makeKeyAndVisible(). Both are required.
    • Crash: "Could not find a storyboard named 'Main'". You deleted Main.storyboard but left Storyboard Name in the scene manifest (and/or UIMainStoryboardFile in Info.plist). Remove those entries.
    • Views pile up in the top-left corner. You forgot translatesAutoresizingMaskIntoConstraints = false. Without it, UIKit ignores your constraints and uses the old autoresizing frame instead.

    02 — Subclassing UIView: a Reusable Component

    by the end you'll have built your own AvatarView component — a ringed circular image with a name label — and reused it twice on one screen.

    ⏱ ~25 min · Beginner

    What you'll build

    A custom UIView subclass called AvatarView: a circular image with a colored ring around it and a name label underneath. It exposes a clean public method — configure(name:image:) — so the rest of your app never touches its internals. Then you'll drop two of them side by side in a view controller to prove the "build once, reuse everywhere" payoff.

    Files in play

    AvatarDemo/
├── AppDelegate.swift          // unchanged from Lab 01
├── SceneDelegate.swift        // unchanged from Lab 01 (roots ViewController)
├── AvatarView.swift           // the reusable component (the star of this lab)
└── ViewController.swift       // uses two AvatarViews in a stack

    Reuse the SceneDelegate from Lab 01 — just point its rootViewController at ViewController() instead of CounterViewController().

    Build it, file by file

    AvatarView.swift

    A UIView subclass that owns its own subviews and layout. The key pattern: both initializers funnel into one shared commonInit(), so the view sets itself up correctly whether it's created in code or (hypothetically) from a nib.

    import UIKit

final class AvatarView: UIView {

    // MARK: - Subviews (private — the outside world never touches these)

    private let imageView = UIImageView()
    private let nameLabel = UILabel()

    // MARK: - Init: both paths lead to commonInit()

    override init(frame: CGRect) {
        super.init(frame: frame)
        commonInit()
    }

    // Required even though we never load from a storyboard — the compiler insists.
    required init?(coder: NSCoder) {
        super.init(coder: coder)
        commonInit()
    }

    private func commonInit() {
        setupImageView()
        setupNameLabel()
        layoutSubviewsInStack()
    }

    // MARK: - Setup

    private func setupImageView() {
        imageView.contentMode = .scaleAspectFill
        imageView.clipsToBounds = true                 // clip the image to the circle
        imageView.backgroundColor = .secondarySystemBackground
        imageView.layer.borderColor = UIColor.systemGreen.cgColor
        imageView.layer.borderWidth = 4                // the colored ring
        imageView.translatesAutoresizingMaskIntoConstraints = false
    }

    private func setupNameLabel() {
        nameLabel.font = .preferredFont(forTextStyle: .headline)
        nameLabel.textAlignment = .center
        nameLabel.translatesAutoresizingMaskIntoConstraints = false
    }

    private func layoutSubviewsInStack() {
        let stack = UIStackView(arrangedSubviews: [imageView, nameLabel])
        stack.axis = .vertical
        stack.alignment = .center
        stack.spacing = 8
        stack.translatesAutoresizingMaskIntoConstraints = false
        addSubview(stack)

        NSLayoutConstraint.activate([
            // Fill our own bounds with the stack.
            stack.topAnchor.constraint(equalTo: topAnchor),
            stack.bottomAnchor.constraint(equalTo: bottomAnchor),
            stack.leadingAnchor.constraint(equalTo: leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: trailingAnchor),

            // Fixed-size square image, so we can make it a perfect circle.
            imageView.widthAnchor.constraint(equalToConstant: 96),
            imageView.heightAnchor.constraint(equalTo: imageView.widthAnchor)
        ])
    }

    // cornerRadius must be half the final size, so set it once we know our size.
    override func layoutSubviews() {
        super.layoutSubviews()
        imageView.layer.cornerRadius = imageView.bounds.width / 2
    }

    // MARK: - Public API (the ONLY way callers interact with this view)

    func configure(name: String, image: UIImage?) {
        nameLabel.text = name
        imageView.image = image
    }
}

    Three things make this a good component. Encapsulation: imageView and nameLabel are private, so no caller can reach in and break assumptions. The commonInit() pattern: both init(frame:) and init?(coder:) route through it, so setup happens exactly once regardless of how the view is born. A tiny public surface: callers only ever call configure(name:image:) — one clear entry point. Note the cornerRadius lives in layoutSubviews() because the view's real size isn't known until layout runs.

    ViewController.swift

    The consumer. It creates two AvatarView instances, configures each differently, and stacks them horizontally. Notice how little it knows about AvatarView's internals — that's the whole point.

    import UIKit

final class ViewController: UIViewController {

    private let leftAvatar = AvatarView()
    private let rightAvatar = AvatarView()

    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = .systemBackground

        // Same class, different data — reuse in action.
        leftAvatar.configure(name: "Ada", image: UIImage(systemName: "person.fill"))
        rightAvatar.configure(name: "Alan", image: UIImage(systemName: "person.fill"))

        let row = UIStackView(arrangedSubviews: [leftAvatar, rightAvatar])
        row.axis = .horizontal
        row.alignment = .center
        row.distribution = .equalSpacing
        row.spacing = 40
        row.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(row)

        NSLayoutConstraint.activate([
            row.centerXAnchor.constraint(equalTo: view.safeAreaLayoutGuide.centerXAnchor),
            row.centerYAnchor.constraint(equalTo: view.safeAreaLayoutGuide.centerYAnchor)
        ])
    }
}

    The view controller never sets a corner radius, never touches an image view, never lays out a label. It calls configure(...) and drops the view in a stack. That separation is what makes AvatarView reusable in the next screen, or the screen after that.

    Wire it up

    • SceneDelegate (reused from Lab 01) sets rootViewController = ViewController().
    • ViewController owns two AvatarView instances and arranges them in a horizontal UIStackView.
    • Each AvatarView is a self-contained UIView: it builds its own image view + label in commonInit(), sizes itself, and only accepts data through configure(name:image:).

    The connection between the two files is deliberately thin — ViewController depends on AvatarView's public API, not its guts.

    Run it — you should see

    Two identical circular avatars centered on screen, each with a green ring, a person silhouette inside, and a name ("Ada" and "Alan") below. Rotate the simulator or change to a larger device — the circles stay perfectly round because cornerRadius is recomputed in layoutSubviews().

    Extend it (your turn)

    1. Add a ringColor parameter to configure (e.g. configure(name:image:ringColor:)) so each avatar can have a different ring color.
    2. Add a third avatar and switch ViewController's outer stack to .vertical to see the component adapt to a new layout with no changes inside AvatarView.

    Common mistakes

    • The circle looks like a rounded square (or a full square). You set cornerRadius in commonInit() before the view had a real size. Set it in layoutSubviews() using bounds.width / 2, and make sure clipsToBounds = true.
    • Compiler error: "required initializer 'init(coder:)' must be provided". Every UIView subclass that overrides init(frame:) must also implement required init?(coder:). Add it and route it through commonInit().
    • The image spills outside the ring. clipsToBounds is false, or contentMode isn't .scaleAspectFill. Set both on the image view so the image is clipped to the circle.

    03 — A List with a Custom Cell

    by the end of this lab you'll have a smooth, scrolling list of people where every row is your own hand-built cell — an avatar circle, a name, and a subtitle — and you'll understand exactly why table views recycle cells.

    ⏱ ~30 min · Beginner → Intermediate

    What you'll build

    A single-screen app: a UITableView full of people, where each row is a custom UITableViewCell subclass laying out an avatar circle, a name, and a role subtitle with Auto Layout anchors. You'll learn the three moving parts every list depends on — reuse identifiers, dequeuing, and cell subclassing.

    Files in play

    UIKitWorkshop/
├─ SceneDelegate.swift          # reused from Lab 01 — sets root VC
├─ Person.swift                 # the model + sample data
├─ PersonCell.swift             # custom UITableViewCell subclass
└─ PeopleListViewController.swift  # owns the table, feeds it rows

    Build it, file by file

    Person.swift

    A tiny value type for the data each row shows, plus a handful of sample people so the list has something to render.

    import Foundation

struct Person {
    let name: String
    let role: String

    // Initials used for the avatar circle (e.g. "Ada Lovelace" -> "AL").
    var initials: String {
        let parts = name.split(separator: " ")
        let letters = parts.prefix(2).compactMap { $0.first }
        return String(letters).uppercased()
    }
}

extension Person {
    static let samplePeople: [Person] = [
        Person(name: "Ada Lovelace",     role: "Computing pioneer"),
        Person(name: "Grace Hopper",     role: "Compiler inventor"),
        Person(name: "Alan Turing",      role: "Mathematician"),
        Person(name: "Katherine Johnson", role: "NASA mathematician"),
        Person(name: "Dennis Ritchie",   role: "Created C"),
        Person(name: "Margaret Hamilton", role: "Apollo software lead"),
        Person(name: "Linus Torvalds",   role: "Kernel maintainer"),
        Person(name: "Barbara Liskov",   role: "Language designer")
    ]
}

    PersonCell.swift

    The star of this lab: your own cell subclass. It owns a static reuse identifier, builds its subviews once in init(style:reuseIdentifier:), pins them with anchors, and exposes a configure(with:) method to fill in a specific person.

    import UIKit

final class PersonCell: UITableViewCell {

    // A cell owns its own reuse identifier — register and dequeue with this.
    static let reuseID = "PersonCell"

    private let avatarView: UILabel = {
        let label = UILabel()
        label.textAlignment = .center
        label.textColor = .white
        label.font = .systemFont(ofSize: 16, weight: .semibold)
        label.backgroundColor = .systemGreen
        label.layer.cornerRadius = 22
        label.clipsToBounds = true
        return label
    }()

    private let nameLabel: UILabel = {
        let label = UILabel()
        label.font = .preferredFont(forTextStyle: .headline)
        label.adjustsFontForContentSizeCategory = true
        return label
    }()

    private let roleLabel: UILabel = {
        let label = UILabel()
        label.font = .preferredFont(forTextStyle: .subheadline)
        label.textColor = .secondaryLabel
        label.adjustsFontForContentSizeCategory = true
        return label
    }()

    // Designated initializer — this is where table cells get set up.
    override init(style: UITableViewCell.CellStyle, reuseIdentifier: String?) {
        super.init(style: style, reuseIdentifier: reuseIdentifier)
        accessoryType = .disclosureIndicator
        setupLayout()
    }

    @available(*, unavailable)
    required init?(coder: NSCoder) {
        fatalError("init(coder:) has not been implemented")
    }

    private func setupLayout() {
        let textStack = UIStackView(arrangedSubviews: [nameLabel, roleLabel])
        textStack.axis = .vertical
        textStack.spacing = 2

        // The golden rule of programmatic Auto Layout.
        avatarView.translatesAutoresizingMaskIntoConstraints = false
        textStack.translatesAutoresizingMaskIntoConstraints = false

        contentView.addSubview(avatarView)
        contentView.addSubview(textStack)

        NSLayoutConstraint.activate([
            avatarView.leadingAnchor.constraint(equalTo: contentView.layoutMarginsGuide.leadingAnchor),
            avatarView.centerYAnchor.constraint(equalTo: contentView.centerYAnchor),
            avatarView.widthAnchor.constraint(equalToConstant: 44),
            avatarView.heightAnchor.constraint(equalToConstant: 44),

            textStack.leadingAnchor.constraint(equalTo: avatarView.trailingAnchor, constant: 12),
            textStack.trailingAnchor.constraint(equalTo: contentView.layoutMarginsGuide.trailingAnchor),
            textStack.centerYAnchor.constraint(equalTo: contentView.centerYAnchor),

            // Give the cell enough height and let it breathe top/bottom.
            contentView.topAnchor.constraint(lessThanOrEqualTo: avatarView.topAnchor, constant: -8),
            contentView.bottomAnchor.constraint(greaterThanOrEqualTo: avatarView.bottomAnchor, constant: 8)
        ])
    }

    // Fill the recycled cell with one person's data.
    func configure(with person: Person) {
        avatarView.text = person.initials
        nameLabel.text = person.name
        roleLabel.text = person.role
    }
}

    PeopleListViewController.swift

    A view controller that owns a UITableView, registers the custom cell class against its reuse identifier, and answers the two required data-source questions: how many rows, and what goes in each one.

    import UIKit

final class PeopleListViewController: UIViewController {

    private let tableView = UITableView(frame: .zero, style: .plain)
    private let people = Person.samplePeople

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "People"
        view.backgroundColor = .systemBackground
        setupTableView()
    }

    private func setupTableView() {
        // Registering the class ties reuseID to PersonCell — dequeue can't fail.
        tableView.register(PersonCell.self, forCellReuseIdentifier: PersonCell.reuseID)
        tableView.dataSource = self
        tableView.rowHeight = UITableView.automaticDimension
        tableView.estimatedRowHeight = 64

        tableView.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(tableView)

        NSLayoutConstraint.activate([
            tableView.topAnchor.constraint(equalTo: view.topAnchor),
            tableView.leadingAnchor.constraint(equalTo: view.leadingAnchor),
            tableView.trailingAnchor.constraint(equalTo: view.trailingAnchor),
            tableView.bottomAnchor.constraint(equalTo: view.bottomAnchor)
        ])
    }
}

extension PeopleListViewController: UITableViewDataSource {

    func tableView(_ tableView: UITableView, numberOfRowsInSection section: Int) -> Int {
        people.count
    }

    func tableView(_ tableView: UITableView,
                   cellForRowAt indexPath: IndexPath) -> UITableViewCell {
        // Dequeue pulls a recycled cell off the queue (or makes one on demand).
        let cell = tableView.dequeueReusableCell(
            withIdentifier: PersonCell.reuseID,
            for: indexPath
        ) as! PersonCell
        cell.configure(with: people[indexPath.row])
        return cell
    }
}

    Wire it up

    Reuse the SceneDelegate from Lab 01 and set this list as the window's root. If you're starting fresh, the essential lines are:

    func scene(_ scene: UIScene,
           willConnectTo session: UISceneSession,
           options connectionOptions: UIScene.ConnectionOptions) {
    guard let windowScene = (scene as? UIWindowScene) else { return }
    let window = UIWindow(windowScene: windowScene)
    window.rootViewController = PeopleListViewController()
    self.window = window
    window.makeKeyAndVisible()
}

    Delete Main.storyboard, and remove the UISceneStoryboardFile / Main storyboard keys from Info.plist (or the scene manifest) so UIKit doesn't try to load a storyboard on launch.

    Run it — you should see

    A full-screen list of eight people. Each row shows a green circle with the person's initials, their name in headline weight, and their role in muted gray underneath, with a chevron on the right. Scroll up and down — it stays buttery smooth because the same few PersonCell instances are recycled as rows leave and enter the screen. Add a breakpoint or print inside init(style:reuseIdentifier:) and you'll see it fire only a handful of times, not once per row.

    Extend it (your turn)

    • Give the avatar a deterministic color derived from the name (hash the string into a hue) so each person gets a consistent tint.
    • Add a section header by adopting titleForHeaderInSection, or split people into "Pioneers" and "Modern" sections.
    • Load a real image into the avatar instead of initials, keeping the circular mask with contentMode = .scaleAspectFill and clipsToBounds = true.

    Common mistakes

    1. Forgetting translatesAutoresizingMaskIntoConstraints = false. Add subviews to contentView, set this to false on each, and your constraints will silently conflict with the autoresizing mask if you skip it — you'll get "Unable to simultaneously satisfy constraints" spam and a broken layout.
    2. Registering one identifier and dequeuing another. The string in register(_:forCellReuseIdentifier:) must match the one in dequeueReusableCell. Using the shared static let reuseID on both sides removes the typo risk entirely.
    3. Configuring in init instead of configure(with:). Cells are recycled, so any data you set once in the initializer will show stale content on the wrong row. Always reset every visible property inside configure(with:) (or prepareForReuse).

    04 — Navigation & Passing Data

    by the end of this lab your list becomes a two-screen app: tap a person and a detail screen slides in showing exactly that person — data handed over cleanly through the initializer, not a storyboard segue.

    ⏱ ~30 min · Intermediate

    What you'll build

    Build it, file by file

    GradientCardView.swift

    The whole point of this view is that effects live on the layer, not the view. A UIView is a thin wrapper around a CALayer (view.layer), and that layer is where corner radius, shadows, and sublayers like gradients actually render. We add a CAGradientLayer as a sublayer and then keep both it and the shadow path in sync inside layoutSubviews — because Auto Layout gives us our real bounds after init, and layers don't participate in Auto Layout.

    import UIKit

/// A rounded card with a gradient fill and a soft, performant shadow.
final class GradientCardView: UIView {

    // The gradient is a sublayer we own and resize ourselves.
    private let gradientLayer = CAGradientLayer()

    /// Colors of the gradient, top-to-bottom. Set this to reskin the card.
    var colors: [UIColor] = [
        UIColor(red: 0.16, green: 0.63, blue: 0.26, alpha: 1),   // #2ea043-ish
        UIColor(red: 0.10, green: 0.35, blue: 0.55, alpha: 1)
    ] {
        didSet { applyColors() }
    }

    override init(frame: CGRect) {
        super.init(frame: frame)
        commonInit()
    }

    required init?(coder: NSCoder) {
        super.init(coder: coder)
        commonInit()
    }

    private func commonInit() {
        // --- Gradient: insert it at the very back so content sits on top. ---
        gradientLayer.startPoint = CGPoint(x: 0.5, y: 0)
        gradientLayer.endPoint   = CGPoint(x: 0.5, y: 1)
        layer.insertSublayer(gradientLayer, at: 0)
        applyColors()

        // --- Corners: cornerRadius clips the view's own layer content. ---
        layer.cornerRadius = 20
        layer.cornerCurve  = .continuous   // the smooth "squircle" curve

        // --- Shadow: NOTE these are on `layer`, and masksToBounds must stay
        //     false or the shadow (which draws OUTSIDE bounds) gets clipped. ---
        layer.masksToBounds = false
        layer.shadowColor   = UIColor.black.cgColor
        layer.shadowOpacity = 0.35
        layer.shadowRadius  = 16
        layer.shadowOffset  = CGSize(width: 0, height: 8)
    }

    private func applyColors() {
        gradientLayer.colors = colors.map(\.cgColor)
    }

    override func layoutSubviews() {
        super.layoutSubviews()

        // Layers don't autolayout — we match the gradient to our bounds here,
        // every time the size changes (rotation, size class, etc.).
        gradientLayer.frame = bounds
        gradientLayer.cornerRadius = layer.cornerRadius   // clip gradient to corners

        // WHY shadowPath: without it, Core Animation renders the shadow by
        // reading every pixel of the layer's alpha channel on each frame —
        // expensive, and it stutters during animation. Handing it an explicit
        // path lets it skip that work entirely. Match the rounded rect.
        layer.shadowPath = UIBezierPath(
            roundedRect: bounds,
            cornerRadius: layer.cornerRadius
        ).cgPath
    }
}

    EffectsViewController.swift

    This controller places the card, drops a UIVisualEffectView blur strip across its top, and wires a tap that springs the card. The one rule with UIVisualEffectView that trips everyone up: you add your content to its contentView, not to the effect view directly — subviews added straight to the blur view won't render correctly.

    import UIKit

final class EffectsViewController: UIViewController {

    private let card = GradientCardView()

    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = UIColor(white: 0.10, alpha: 1)

        // --- The card, centered, fixed size. ---
        card.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(card)
        NSLayoutConstraint.activate([
            card.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            card.centerYAnchor.constraint(equalTo: view.centerYAnchor),
            card.widthAnchor.constraint(equalToConstant: 260),
            card.heightAnchor.constraint(equalToConstant: 200)
        ])

        // --- Blur header strip, pinned to the top of the card. ---
        let blur = UIVisualEffectView(effect: UIBlurEffect(style: .systemThinMaterialDark))
        blur.translatesAutoresizingMaskIntoConstraints = false
        // Match the card's top corners so the strip doesn't overflow them.
        blur.layer.cornerRadius = 20
        blur.layer.cornerCurve  = .continuous
        blur.layer.maskedCorners = [.layerMinXMinYCorner, .layerMaxXMinYCorner]
        blur.clipsToBounds = true
        card.addSubview(blur)
        NSLayoutConstraint.activate([
            blur.topAnchor.constraint(equalTo: card.topAnchor),
            blur.leadingAnchor.constraint(equalTo: card.leadingAnchor),
            blur.trailingAnchor.constraint(equalTo: card.trailingAnchor),
            blur.heightAnchor.constraint(equalToConstant: 52)
        ])

        // A title label — added to the blur's CONTENT VIEW, not the blur itself.
        let title = UILabel()
        title.translatesAutoresizingMaskIntoConstraints = false
        title.text = "Profile"
        title.font = .preferredFont(forTextStyle: .headline)
        title.textColor = .white
        blur.contentView.addSubview(title)
        NSLayoutConstraint.activate([
            title.leadingAnchor.constraint(equalTo: blur.contentView.leadingAnchor, constant: 16),
            title.centerYAnchor.constraint(equalTo: blur.contentView.centerYAnchor)
        ])

        // A name label lower down on the card body.
        let name = UILabel()
        name.translatesAutoresizingMaskIntoConstraints = false
        name.text = "Ada Lovelace\nTap the card"
        name.numberOfLines = 0
        name.textAlignment = .center
        name.textColor = .white
        name.font = .preferredFont(forTextStyle: .body)
        card.addSubview(name)
        NSLayoutConstraint.activate([
            name.centerXAnchor.constraint(equalTo: card.centerXAnchor),
            name.topAnchor.constraint(equalTo: blur.bottomAnchor, constant: 24)
        ])

        // --- Tap to pop. ---
        let tap = UITapGestureRecognizer(target: self, action: #selector(cardTapped))
        card.addGestureRecognizer(tap)
        card.isUserInteractionEnabled = true
    }

    @objc private func cardTapped() {
        // Squash-then-spring: shrink instantly, spring back to identity.
        card.transform = CGAffineTransform(scaleX: 0.94, y: 0.94)
        UIView.animate(
            withDuration: 0.5,
            delay: 0,
            usingSpringWithDamping: 0.45,   // lower = bouncier
            initialSpringVelocity: 0.8,
            options: [.allowUserInteraction]
        ) {
            // Animating `transform` is cheap — it's a GPU-side matrix, and it
            // doesn't invalidate layout, so shadowPath keeps working.
            self.card.transform = .identity
        }
    }
}

    Build it, file by file

    DraggableCardView.swift

    Everything gesture-related lives inside the card itself, so the host controller stays dumb. We add two recognizers in commonInit and use target-action — each recognizer calls a method on us and we read its state.

    The pan handler is the heart of it. During .changed we read translation(in:) (how far the finger has moved since the gesture began) and offset our center by it, then immediately call setTranslation(.zero, in:) so the next callback's translation is relative to now, not the start. On .ended we read velocity(in:) and feed it into a spring so a hard fling bounces harder.

    import UIKit

final class DraggableCardView: UIView {

    /// Where the card lives when it's not being dragged. Set by the host.
    var homeCenter: CGPoint = .zero

    private var isLiked = false
    private let heart = UILabel()

    override init(frame: CGRect) {
        super.init(frame: frame)
        commonInit()
    }

    required init?(coder: NSCoder) {
        super.init(coder: coder)
        commonInit()
    }

    private func commonInit() {
        backgroundColor = UIColor(white: 0.17, alpha: 1)
        layer.cornerRadius = 16
        layer.cornerCurve  = .continuous

        // A label so the card isn't blank.
        let title = UILabel()
        title.text = "Drag me"
        title.textColor = .white
        title.font = .preferredFont(forTextStyle: .headline)
        title.translatesAutoresizingMaskIntoConstraints = false
        addSubview(title)
        NSLayoutConstraint.activate([
            title.centerXAnchor.constraint(equalTo: centerXAnchor),
            title.topAnchor.constraint(equalTo: topAnchor, constant: 20)
        ])

        // The heart we toggle on tap.
        heart.text = "♡"
        heart.textColor = UIColor(red: 0.16, green: 0.63, blue: 0.26, alpha: 1)
        heart.font = .systemFont(ofSize: 28)
        heart.translatesAutoresizingMaskIntoConstraints = false
        addSubview(heart)
        NSLayoutConstraint.activate([
            heart.centerXAnchor.constraint(equalTo: centerXAnchor),
            heart.bottomAnchor.constraint(equalTo: bottomAnchor, constant: -16)
        ])

        // --- Recognizers: target-action back to us. ---
        let pan = UIPanGestureRecognizer(target: self, action: #selector(handlePan))
        addGestureRecognizer(pan)

        let tap = UITapGestureRecognizer(target: self, action: #selector(handleTap))
        addGestureRecognizer(tap)
    }

    @objc private func handlePan(_ gr: UIPanGestureRecognizer) {
        switch gr.state {
        case .began, .changed:
            // How far the finger moved since we last reset. Apply, then reset.
            let t = gr.translation(in: superview)
            center = CGPoint(x: center.x + t.x, y: center.y + t.y)
            gr.setTranslation(.zero, in: superview)

        case .ended, .cancelled:
            // Velocity is in points/second — convert to the spring's
            // "initial velocity" (fraction of remaining distance per second).
            let v = gr.velocity(in: superview)
            let dx = homeCenter.x - center.x
            let dy = homeCenter.y - center.y
            let distance = max(1, hypot(dx, dy))
            let initialVelocity = hypot(v.x, v.y) / distance

            UIView.animate(
                withDuration: 0.6,
                delay: 0,
                usingSpringWithDamping: 0.55,
                initialSpringVelocity: initialVelocity,
                options: [.allowUserInteraction]
            ) {
                self.center = self.homeCenter
            }

        default:
            break
        }
    }

    @objc private func handleTap() {
        isLiked.toggle()
        heart.text = isLiked ? "♥" : "♡"

        // A quick pop so the toggle feels alive.
        heart.transform = CGAffineTransform(scaleX: 1.6, y: 1.6)
        UIView.animate(
            withDuration: 0.4,
            delay: 0,
            usingSpringWithDamping: 0.4,
            initialSpringVelocity: 0.8
        ) {
            self.heart.transform = .identity
        }
    }
}

    The host just creates one card, sizes it, and tells it where "home" is. We set homeCenter in viewDidLayoutSubviews because that's the first point where the view's bounds are final.

    Common mistakes

    1. Never resetting the translation. If you skip gr.setTranslation(.zero, in:), every .changed reports the cumulative distance from the start, so you add it again and again and the card rockets off screen. Reset it every frame, or (the alternative) store the start center once in .began and always offset from that.
    2. Reading translation/velocity in the wrong coordinate space. Pass the superview (or view) you're actually moving within — passing self gives you values in the card's own moving frame and the motion feels wrong.
    3. Tap and pan fighting, or isUserInteractionEnabled off. A view built in code has interaction on by default, but if you disable it (or add the recognizers to the wrong view) nothing responds. Both recognizers can live on the same view; UIKit sorts a tap from a drag by whether the finger moves.

    RatingControl.swift

    Why subclass UIControl instead of gluing a UITapGestureRecognizer onto a plain view? Because UIControl is the target-action machine. It already knows how to hold a list of registered actions and fire them by event type — we just call sendActions(for: .valueChanged) and every addTarget/addAction observer runs. That's the same contract UISlider and UISwitch honor, so our control drops into existing code with zero surprises.

    State lives in one property, rating, with a didSet that re-skins the stars and fires the event in one place. And we override intrinsicContentSize so Auto Layout knows how big the row wants to be without us hand-coding width/height constraints.

    import UIKit

final class RatingControl: UIControl {

    private let starCount = 5
    private var buttons: [UIButton] = []
    private let stack = UIStackView()

    /// The current rating (0...starCount). Setting it updates the stars and,
    /// crucially, tells everyone who's listening.
    var rating: Int = 0 {
        didSet {
            rating = min(max(rating, 0), starCount)   // clamp
            updateStars()
            sendActions(for: .valueChanged)           // <-- the whole point
        }
    }

    override init(frame: CGRect) {
        super.init(frame: frame)
        commonInit()
    }

    required init?(coder: NSCoder) {
        super.init(coder: coder)
        commonInit()
    }

    private func commonInit() {
        stack.axis = .horizontal
        stack.spacing = 8
        stack.translatesAutoresizingMaskIntoConstraints = false
        stack.isUserInteractionEnabled = true
        addSubview(stack)
        NSLayoutConstraint.activate([
            stack.leadingAnchor.constraint(equalTo: leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: trailingAnchor),
            stack.topAnchor.constraint(equalTo: topAnchor),
            stack.bottomAnchor.constraint(equalTo: bottomAnchor)
        ])

        for index in 0..<starCount {
            let button = UIButton(type: .system)
            button.setTitle("☆", for: .normal)
            button.titleLabel?.font = .systemFont(ofSize: 32)
            button.tintColor = UIColor(red: 0.16, green: 0.63, blue: 0.26, alpha: 1)
            // Each star knows its 1-based value via `tag`.
            button.tag = index + 1
            button.addAction(
                UIAction { [weak self] _ in
                    self?.rating = button.tag
                },
                for: .touchUpInside
            )
            buttons.append(button)
            stack.addArrangedSubview(button)
        }

        updateStars()
    }

    private func updateStars() {
        for button in buttons {
            let filled = button.tag <= rating
            button.setTitle(filled ? "★" : "☆", for: .normal)
        }
    }

    // Auto Layout asks the control how big it wants to be. Answer with the
    // stack's natural size so the host never needs width/height constraints.
    override var intrinsicContentSize: CGSize {
        stack.systemLayoutSizeFitting(UIView.layoutFittingCompressedSize)
    }
}

    ViewController.swift

    The host treats RatingControl like any stock control: add it, register an action for .valueChanged, and read control.rating inside the handler. Notice there's no delegate protocol and no knowledge of stars — just the control's public API.

    import UIKit

final class ViewController: UIViewController {

    private let ratingControl = RatingControl()
    private let label = UILabel()

    override func viewDidLoad() {
        super.viewDidLoad()
        view.backgroundColor = UIColor(white: 0.10, alpha: 1)

        label.text = "Rating: 0 of 5"
        label.textColor = .white
        label.font = .preferredFont(forTextStyle: .title3)
        label.textAlignment = .center

        let column = UIStackView(arrangedSubviews: [ratingControl, label])
        column.axis = .vertical
        column.spacing = 24
        column.alignment = .center
        column.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(column)
        NSLayoutConstraint.activate([
            column.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            column.centerYAnchor.constraint(equalTo: view.centerYAnchor)
        ])

        // The payoff: our control behaves like UISwitch/UISlider here.
        ratingControl.addAction(
            UIAction { [weak self] _ in
                guard let self else { return }
                self.label.text = "Rating: \(self.ratingControl.rating) of 5"
            },
            for: .valueChanged
        )
    }
}

    Extend it (your turn)

    • Add "tap the same star again to clear to zero" by comparing the tapped value with the current rating.
    • Support half-stars by tracking touch location within a star (beginTracking(_:with:)) instead of per-button taps.

    Common mistakes

    1. Firing .valueChanged from the wrong place. Put sendActions(for: .valueChanged) inside the rating didSet, not in the button handler. Then every path that changes the value — taps, programmatic sets, tests — notifies listeners, and you can never forget it.
    2. Skipping intrinsicContentSize. Without it a code-built control reports a zero content size, so Auto Layout may collapse it and the stars vanish. Report the stack's fitting size (or set explicit constraints).
    3. Reaching for a delegate protocol. For a value-emitting control, target-action is the idiomatic API — it's what addAction/addTarget expect. A custom delegate here just reinvents what UIControl already gives you for free.

    08 — Structure It: MVVM-lite + Async Load

    by the end, you'll have a list screen that shows a spinner, fetches its rows off the main thread with async/await, and swaps in the results — all split into clean, single-responsibility files.

    ⏱ 35 min · Intermediate

    What you'll build

    A single-screen app that loads a list of people asynchronously: you'll see a spinner, wait about a second, and then the table fills with rows — with the model, the fetching, the state, and the view each living in its own file.

    Files in play

    MVVMAsyncLab/
├─ AppDelegate.swift          // untouched from the template
├─ SceneDelegate.swift        // sets the root view controller in code
├─ Person.swift               // the model
├─ PeopleService.swift        // async data source (simulated network)
├─ PeopleViewModel.swift      // @MainActor state machine
└─ PeopleViewController.swift // table + spinner, owns the view model

    Build it, file by file

    Person.swift

    A plain value type. No UIKit, no logic — just the data the screen needs. Keeping the model in its own file (and import-free of UIKit) is the first act of structure: the model doesn't know a screen exists.

    import Foundation

struct Person: Identifiable, Hashable, Sendable {
    let id: UUID
    let name: String
    let role: String

    init(id: UUID = UUID(), name: String, role: String) {
        self.id = id
        self.name = name
        self.role = role
    }
}

    Sendable matters here: this value is going to cross an actor boundary (it's produced off the main actor and consumed on it), and marking it Sendable is your promise to the compiler that it's safe to hand across threads. A struct of value types earns that for free.

    PeopleService.swift

    The service is the only thing that knows how data arrives. Today it fakes a network call with Task.sleep; tomorrow you could swap in a real URLSession and nothing else in the app would change. That's the whole point of giving it a seam.

    import Foundation

struct PeopleService: Sendable {
    /// Simulates a network fetch: waits ~1s, then returns sample data.
    func fetchPeople() async throws -> [Person] {
        // Pretend we're waiting on the network. `Task.sleep` suspends
        // without blocking a thread — the CPU is free to do other work.
        try await Task.sleep(for: .seconds(1))

        return [
            Person(name: "Ada Lovelace",     role: "Mathematician"),
            Person(name: "Alan Turing",      role: "Computer Scientist"),
            Person(name: "Grace Hopper",     role: "Rear Admiral"),
            Person(name: "Katherine Johnson", role: "Aerospace Engineer"),
            Person(name: "Margaret Hamilton", role: "Software Engineer"),
            Person(name: "Dennis Ritchie",   role: "Language Designer")
        ]
    }
}

    Note the throws: real fetches fail, so the signature says so. Task.sleep can throw CancellationError if the surrounding task is cancelled — the try covers that, and it flows straight up to the caller.

    PeopleViewModel.swift

    The view model holds the screen's state and knows how to move between states. It never touches a UITableView or a UILabel — it just publishes "here's what should be on screen right now" and lets the view figure out the pixels.

    It's marked @MainActor so every property and method runs on the main thread. That's a deliberate choice: the view model is read by the view (which must be on main), so pinning it to the main actor removes a whole category of data races. The slow work still happens off-main — it's tucked inside service.fetchPeople(), which suspends at the await.

    import Foundation

@MainActor
final class PeopleViewModel {
    enum State {
        case loading
        case loaded([Person])
        case failed(String)
    }

    private(set) var state: State = .loading {
        didSet { onChange?() }
    }

    /// The view sets this to learn when it should re-render.
    var onChange: (() -> Void)?

    private let service: PeopleService

    init(service: PeopleService = PeopleService()) {
        self.service = service
    }

    func load() async {
        state = .loading
        do {
            // `await` suspends here. We're on the main actor, but the
            // main thread is released while the service does its work —
            // the UI stays responsive.
            let people = try await service.fetchPeople()
            state = .loaded(people)
        } catch {
            state = .failed(error.localizedDescription)
        }
    }
}

    The didSet on state is the "MVVM-lite" glue: any assignment to state automatically fires onChange, so the view only has to register one callback and re-render whenever it's called. (Reach for @Observable once you're on the SwiftUI side of the fence; for a UIKit view a plain closure is smaller and just as clear.)

    Why is this correct even though service.fetchPeople() runs elsewhere? Because assigning to state happens after the await resumes — and a @MainActor method always resumes back on the main actor. So the didSet, the onChange, and everything the view does in response are guaranteed to be on the main thread. See the main thread for why UIKit insists on that, and Concurrency for how await hands the thread back.

    PeopleViewController.swift

    The view. It owns the table and the spinner, owns the view model, kicks off the load, and renders whatever state the view model reports. It does not know that data comes from a sleep, or a socket, or a file — it just draws states.

    import UIKit

final class PeopleViewController: UIViewController {

    private let viewModel = PeopleViewModel()

    private let tableView = UITableView(frame: .zero, style: .plain)
    private let spinner = UIActivityIndicatorView(style: .large)
    private let messageLabel = UILabel()

    private var people: [Person] = []

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "People"
        view.backgroundColor = .systemBackground

        setUpTable()
        setUpSpinner()
        setUpMessageLabel()
        bindViewModel()

        // Fire the load. The Task inherits the main actor from the VC,
        // so `await viewModel.load()` runs the view model on main —
        // exactly where its state lives.
        Task { await viewModel.load() }
    }

    private func setUpTable() {
        tableView.dataSource = self
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: "cell")
        tableView.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(tableView)
        NSLayoutConstraint.activate([
            tableView.topAnchor.constraint(equalTo: view.topAnchor),
            tableView.leadingAnchor.constraint(equalTo: view.leadingAnchor),
            tableView.trailingAnchor.constraint(equalTo: view.trailingAnchor),
            tableView.bottomAnchor.constraint(equalTo: view.bottomAnchor)
        ])
    }

    private func setUpSpinner() {
        spinner.hidesWhenStopped = true
        spinner.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(spinner)
        NSLayoutConstraint.activate([
            spinner.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            spinner.centerYAnchor.constraint(equalTo: view.centerYAnchor)
        ])
    }

    private func setUpMessageLabel() {
        messageLabel.textColor = .secondaryLabel
        messageLabel.textAlignment = .center
        messageLabel.numberOfLines = 0
        messageLabel.isHidden = true
        messageLabel.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(messageLabel)
        NSLayoutConstraint.activate([
            messageLabel.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            messageLabel.centerYAnchor.constraint(equalTo: view.centerYAnchor),
            messageLabel.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 32),
            messageLabel.trailingAnchor.constraint(equalTo: view.trailingAnchor, constant: -32)
        ])
    }

    private func bindViewModel() {
        // Called on the main actor whenever state changes — safe to touch UIKit.
        viewModel.onChange = { [weak self] in
            self?.render()
        }
    }

    private func render() {
        switch viewModel.state {
        case .loading:
            people = []
            messageLabel.isHidden = true
            tableView.isHidden = true
            spinner.startAnimating()

        case .loaded(let loaded):
            people = loaded
            spinner.stopAnimating()
            messageLabel.isHidden = true
            tableView.isHidden = false
            tableView.reloadData()

        case .failed(let message):
            people = []
            spinner.stopAnimating()
            tableView.isHidden = true
            messageLabel.text = "Couldn't load people.\n\(message)"
            messageLabel.isHidden = false
        }
    }
}

extension PeopleViewController: UITableViewDataSource {
    func tableView(_ tableView: UITableView, numberOfRowsInSection section: Int) -> Int {
        people.count
    }

    func tableView(_ tableView: UITableView,
                   cellForRowAt indexPath: IndexPath) -> UITableViewCell {
        let cell = tableView.dequeueReusableCell(withIdentifier: "cell", for: indexPath)
        let person = people[indexPath.row]
        var config = cell.defaultContentConfiguration()
        config.text = person.name
        config.secondaryText = person.role
        cell.contentConfiguration = config
        return cell
    }
}

    Wire it up

    No storyboard, so set the root view controller in SceneDelegate.swift. Wrap it in a nav controller so the title bar shows.

               willConnectTo session: UISceneSession,
               options connectionOptions: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let window = UIWindow(windowScene: windowScene)

    Run it — you should see

    1. The screen opens with a large spinner dead-center, table hidden.
    2. After about a second, the spinner disappears and six rows fade in — name on top, role beneath.
    3. Scroll: the rows are a normal table.

    To watch the error path, change PeopleService.fetchPeople() to throw after the sleep (e.g. throw URLError(.timedOut)), run again, and you'll get the centered failure message instead of rows.

    Extend it (your turn)

    • Pull to refresh. Add a UIRefreshControl to the table; on .valueChanged, start a new Task { await viewModel.load() } and call endRefreshing() when .loaded/.failed arrives.
    • Retry button. In the .failed branch, show a "Try Again" button that re-runs load().
    • Real data. Swap the sleep-and-array in PeopleService for a URLSession call that decodes JSON into [Person]. Notice nothing above the service needs to change.
    • Cancel on disappear. Store the Task and call .cancel() in viewDidDisappear — then watch Task.sleep throw CancellationError into your .failed branch.

    Common mistakes

    1. Updating UIKit from a background context. If you move the fetch to a detached task or a non-@MainActor type, remember the view still must be touched on main. Here the view model is @MainActor, so resumption lands back on main automatically — don't "optimize" that away by dropping the annotation.
    2. Forgetting [weak self] in onChange. The view controller owns the view model, and the closure captures the view controller. Capture self strongly and you get a retain cycle that leaks the whole screen. Use [weak self].
    3. Blocking the main thread instead of awaiting. Thread.sleep(forTimeInterval:) or a synchronous network call freezes the spinner (it can't even animate). The point of await/Task.sleep is that the main thread stays free to render.

    09 — Capstone: Drop In a SwiftUI Island

    by the end, you'll have a UIKit profile screen with a live SwiftUI "stats card" embedded inside it — data flowing in, a tap flowing back out, and the card sizing itself to its content.

    ⏱ 30 min · Intermediate

    What you'll build

    A programmatic UIKit profile screen that hosts a SwiftUI StatsCard via UIHostingController: you pass the stats in as a value, hand it a closure so a tap inside SwiftUI runs UIKit code, and let it size itself. This is the capstone — the bridge that lets you adopt SwiftUI one island at a time inside a UIKit app.

    Files in play

    SwiftUIIslandLab/
├─ AppDelegate.swift          // untouched from the template
├─ SceneDelegate.swift        // sets the root view controller in code
├─ StatsCard.swift            // the SwiftUI island + its model
└─ ProfileViewController.swift // UIKit screen that embeds the island

    Build it, file by file

    StatsCard.swift

    The island. It's an ordinary SwiftUI View — it has no idea it's living inside UIKit. It takes a value (Stats) to display and a closure (onTap) to call when the button is pressed. That's the entire contract: data in, event out. Keeping the model right next to the view makes the file self-contained.

    import SwiftUI

struct Stats: Hashable, Sendable {
    let posts: Int
    let followers: Int
    let following: Int
}

struct StatsCard: View {
    let stats: Stats
    let onTap: () -> Void

    var body: some View {
        VStack(spacing: 16) {
            HStack {
                stat("Posts", stats.posts)
                Divider().frame(height: 40)
                stat("Followers", stats.followers)
                Divider().frame(height: 40)
                stat("Following", stats.following)
            }

            Button(action: onTap) {
                Text("Say hello")
                    .font(.headline)
                    .frame(maxWidth: .infinity)
                    .padding(.vertical, 10)
            }
            .buttonStyle(.borderedProminent)
        }
        .padding(20)
        .background(.regularMaterial, in: RoundedRectangle(cornerRadius: 16))
    }

    private func stat(_ title: String, _ value: Int) -> some View {
        VStack(spacing: 4) {
            Text(value.formatted())
                .font(.title2.bold())
                .monospacedDigit()
            Text(title)
                .font(.caption)
                .foregroundStyle(.secondary)
        }
        .frame(maxWidth: .infinity)
    }
}

    Two things to notice. The card is driven entirely by its inputs — pass a different Stats and it redraws. And onTap is how SwiftUI talks back to UIKit: the button just calls the closure, and it's the UIKit side's job to decide what that means.

    ProfileViewController.swift

    The UIKit host. This is where the bridge actually happens, in three moves you'll use every time you embed SwiftUI: make the hosting controller, run the containment dance (addChild → add its view + constraints → didMove(toParent:)), and set the sizing option so the card reports its natural height back to Auto Layout.

    import UIKit
import SwiftUI

final class ProfileViewController: UIViewController {

    private let nameLabel = UILabel()

    private let stats = Stats(posts: 128, followers: 4_820, following: 312)

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "Profile"
        view.backgroundColor = .systemBackground

        setUpHeader()
        embedStatsCard()
    }

    private func setUpHeader() {
        nameLabel.text = "Ada Lovelace"
        nameLabel.font = .preferredFont(forTextStyle: .largeTitle)
        nameLabel.adjustsFontForContentSizeCategory = true
        nameLabel.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(nameLabel)
        NSLayoutConstraint.activate([
            nameLabel.topAnchor.constraint(
                equalTo: view.safeAreaLayoutGuide.topAnchor, constant: 24),
            nameLabel.leadingAnchor.constraint(
                equalTo: view.leadingAnchor, constant: 20)
        ])
    }

    private func embedStatsCard() {
        // 1. Build the SwiftUI view, passing data IN and a closure OUT.
        let card = StatsCard(stats: stats) { [weak self] in
            self?.sayHelloTapped()
        }

        // 2. Wrap it in a hosting controller — a UIViewController whose
        //    view IS the SwiftUI content.
        let host = UIHostingController(rootView: card)

        // 3. Ask the host to size itself to the SwiftUI view's ideal size.
        //    Without this, Auto Layout has no idea how tall the card is.
        host.sizingOptions = .intrinsicContentSize
        host.view.backgroundColor = .clear

        // 4. Containment: adopt the child controller.
        addChild(host)
        host.view.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(host.view)
        NSLayoutConstraint.activate([
            host.view.topAnchor.constraint(
                equalTo: nameLabel.bottomAnchor, constant: 24),
            host.view.leadingAnchor.constraint(
                equalTo: view.leadingAnchor, constant: 20),
            host.view.trailingAnchor.constraint(
                equalTo: view.trailingAnchor, constant: -20)
        ])
        // 5. Tell the child it now has a parent.
        host.didMove(toParent: self)
    }

    private func sayHelloTapped() {
        // This runs when the SwiftUI button is pressed — pure UIKit.
        let alert = UIAlertController(
            title: "Hello from UIKit 👋",
            message: "The tap came out of the SwiftUI island.",
            preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "Nice", style: .default))
        present(alert, animated: true)
    }
}

    The containment dance (addChild … didMove(toParent:)) is not optional decoration — it's how UIKit's view-controller hierarchy stays in sync with the view hierarchy. Skip addChild and the hosting controller never receives lifecycle events (appearance callbacks, trait changes, size-class updates), so its SwiftUI content can misbehave. Skip didMove(toParent:) and you've told UIKit "I'll finish adopting this child later" and never did.

    The sizing note is the other classic gotcha. A UIHostingController's view doesn't automatically hand its intrinsic size to Auto Layout. Setting sizingOptions = .intrinsicContentSize makes it publish its SwiftUI ideal size as its intrinsic content size — so pinning three edges (top/leading/trailing) is enough and the card takes exactly the height its content needs. That's why there's no bottom or height constraint above.

    2. Below it, a rounded material card — three stat columns (Posts / Followers / Following) with a divider between each — sized snugly to its content, not stretched to fill the screen.

    Extend it (your turn)

    • Live updates. Store the UIHostingController and, on a UIKit button, set host.rootView = StatsCard(stats: newStats, onTap: …) to push fresh data into the island.
    • Two-way state. Give the card an @State counter and report changes out through a second closure — watch UIKit and SwiftUI stay in sync.
    • Go the other direction too. Recall Lab 08's approach: this containment pattern is the same one you'd use to embed any child view controller, SwiftUI or not.

    Common mistakes

    1. Forgetting didMove(toParent:). addChild alone leaves the containment half-finished. Always pair them: addChild(host) before you add the view, host.didMove(toParent: self) after. (When removing, the order flips: willMove(toParent: nil) → remove view → removeFromParent().)
    2. Skipping sizingOptions. Without .intrinsicContentSize, the hosting view has no intrinsic size, so a three-edge constraint set collapses it to zero height and the card vanishes. Set the option, or pin a fourth edge / explicit height yourself.
    3. A retain cycle in the onTap closure. The controller owns the card (via the host), and the card's closure captures the controller. Capture self strongly and the whole screen leaks — use [weak self].
